# BOSS v9.4.9

**Release Date:** 2026-08-15

A plugin-reliability release. Closing a laptop lid no longer convicts every plugin at once and leaves them silently inert, a panel now tells you which build of a plugin it is actually running and can uninstall it, and the focus-mode quick actions move into the right rail where there is one.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **A sleeping laptop no longer disables every plugin.** The watchdog measured heartbeat age against the wall clock, so a 48-second suspend aged every plugin's heartbeat by 48 seconds and convicted 24 of them inside 6ms - the watchdog's own check loop was frozen for the same 48 seconds, which is proof the plugins were never at fault. What the "restart" then did was worse than the false positive: it replaced the sandbox scope while every component built in `register()` went on holding the cancelled one, and a cancelled scope swallows `launch()` without running it and without throwing. The plugin went quietly inert - a Codebase folder stuck on "Loading...", nothing in any log, and a toast saying the restart succeeded (#171)
- **A panel says which build of a plugin it is running, and can uninstall it.** The manifest version cannot tell you: a locally built jar and the released one carry the same `version`, and an in-place hot reload rewrites neither the manifest nor `installed.json`. The tag reads `1.0.3-debug` for bytes the store never vetted and `1.0.3-debug+<millis>` once they were replaced under the running plugin, sits next to the panel name and on plugin tabs, and clicking it offers to install the store build. "Restart Panel" is gone, since it only recreated the panel component from the already-registered factory and looked like it picked up a new jar without ever doing so (#169)
- **Focus-mode quick actions go in the right rail when there is one.** Settings, Search and Sign Out have floated in the content area's bottom-right corner since v9.4.8; where the right sidebar is on screen there is already a strip of icon chrome with empty space at the bottom, so they land there as ordinary sidebar icons under a divider. That is the default configuration on Windows, which is also the platform the floating cluster was built for. The cluster stays as the fallback for when focus mode has cleared the sidebar too (#172)
- **Settings opens or raises, instead of silently doing nothing.** Every Settings affordance assigned `showSettingsDialog = true`, and assigning true to a flag that is already true changes nothing, so with the settings window open behind the main one, clicking Settings was a dead button (#172)

## Features

- **panel**: a build tag on panels and plugin tabs, plus a clickable version row in the overflow menu that offers the store build. Both facts behind it come from signals already on disk, so nothing new is tracked at runtime: a `<jar>.sig` sidecar means the store vetted those exact bytes, and a jar whose mtime beats the stamp recorded at its last load was overwritten in place. The verdict persists in three new nullable fields on `InstalledPluginEntry` rather than in `version` itself, which feeds `isNewerVersion` and the `pluginId|version|sha256` signing anchor - without persistence the mtime comparison alone would report a hot-reloaded plugin as a fresh install and the tag would vanish on relaunch (#169)
- **panel**: uninstall from the panel overflow menu, running through `DynamicPluginManager.uninstallPlugin` so it inherits tab teardown before the classloader closes, the dependency veto and the crash-quarantine release, then deleting the jar, its sidecar and its `installed.json` row. `removeInstalledPlugin` had zero production callers before this, so every uninstall left a row pointing at a file that may already be gone. Deletion hangs off a hook the shared unload path deliberately cannot reach, since reload, the api hot swap and the update bridge all call `uninstallPlugin(force = true)` and are about to load that jar again (#169)
- **panel**: a bottom section on `BossRightSideBar` for the quick actions, reserving `SidebarIconRail.bottomSectionHeight` outside the budget `computeSlotIconLimits` hands the plugin slots. The placement is decided from the settings, not from `reveal.showRightSidebar`: that flag reads false on every window's first composition, so keying off it would create and dispose a native always-on-top window on every window open (#172)

## Bug Fixes

- **plugins**: the watchdog now compares a monotonic clock against the wall clock and discards any tick that overran. A machine suspend shows up as the wall clock running ahead of the monotonic one (neither macOS nor Linux counts suspend in the monotonic clock); a freeze while awake - a long GC, a breakpoint - shows up as both running ahead of the check interval. After either, checks pause for one unhealthy window so the plugins' own heartbeat jobs, overdue for the same reason, get to run before anything is judged (#171)
- **plugins**: the scope handed to plugins is created once and never replaced. A restart cancels its children and gives it a fresh Job, so in-flight work still dies but the scope a plugin captured at `register()` keeps working, with the dispatcher indirecting through a swappable delegate so the thread pool can still be replaced underneath it. The same fix repairs disable-then-enable, which left the scope cancelled and the pool shut down with nothing to revive them (#171)
- **plugins**: a restarted plugin gets its `register()` subscriptions back. The scope fix keeps work a user starts afterwards running, but nothing could bring back what a plugin subscribed to once inside `register()` itself - the Toolbox's realtime channel and update-prompt loop, terminal-tab's approval collector, tool-creator's event job, analytics' pipes. The manager now unregisters, re-registers and refreshes any open panel, on `Dispatchers.Main` so no frame observes the plugin with its panels missing, detached onto the manager's own scope because the callback arrives inside the watchdog coroutine that disabling the plugin cancels (#171)
- **plugins**: `restartAttempts` survives a restart, so `maxRestartAttempts` is reachable at all. It was zeroed the moment `restart()` returned and the in-process restart cannot fail, so every attempt in the logs said "attempt=1". The counter is now cleared after a sustained run of healthy checks, which is the only thing that actually evidences recovery (#171)
- **plugins**: the error boundary's Restart button never re-registered anything. Both boundaries called `sandbox.restart()` directly, which notifies no listener, so nothing re-ran `register()` - on the path a user reaches *after* noticing a plugin is wedged. With the surviving counter it was worse: three presses of the button offered as the remedy pushed a plugin to `maxRestartAttempts`. Both sites now go through the manager, which restarts only the sandbox that owns the panel (sandboxes are per-window, so restarting everywhere cancelled healthy in-flight work in other windows) and then clears the budget (#171)
- **plugins**: a cancelled restart no longer strands the sandbox in `RESTARTING`. `restart()` suspended in the executor teardown between setting `RESTARTING` and setting `RUNNING`, and `RESTARTING` is the one state the watchdog skips outright, so nothing would ever restart that plugin, nothing would mark it unhealthy, and the error boundary showed no fallback because the state was not `DISABLED`. Everything that moves the sandbox out of the transient state now runs without suspending, and the old pool is retired after the sandbox is already `RUNNING` on the new one (#171)
- **plugins**: a sandbox listener that threw killed the plugin's watchdog for the session. `PluginSandboxManagerImpl.notifyListeners` called the action bare while `DynamicPluginManager`'s copy has always wrapped it, an asymmetry that only became load-bearing when `onPluginRestarted` started doing real work. Caught as `Throwable`, not `Exception`, since these listeners reach plugin code and Compose dispatchers (#171)
- **plugins**: a chronically slow host no longer mutes the watchdog permanently. Every stalled tick re-armed the suppression, so a host that is always late rather than briefly frozen meant health checks never ran again for the life of the watchdog. Past a configurable bound it checks anyway and logs WARN, degrading to late detection rather than none - and the bound counts ticks that did not reach `checkHealth`, whatever the reason, so a stall every other tick cannot slip past it the way a consecutive-stall counter allowed (#171)
- **plugins**: a failed re-registration is marked `DISABLED` instead of leaving the plugin with zero registrations, state `LOADED`, no fallback UI and an open panel drawing its pre-restart component over an empty registry (#171)
- **panel**: the store swap could download onto the running jar. The name is deterministic `<id>_<version>.jar` and the swap promoted onto it *before* unloading, so the second store install of one plugin moved onto a jar held open by a live classloader - a hard failure on Windows - and then discarded the running plugin's own file on the way out. Reachable in one sitting: install the store version, hot reload over it, click again. A failed swap is also a no-op from the user's side now, where both failure branches used to return past the force-unload leaving no plugin installed until relaunch (#169)
- **panel**: a store-installed plugin could be tagged DEBUG. The premise was that local builds simply have no `.sig` sidecar, which does not hold during the signature rollout - enforcement defaults off, an unsigned store row warns and allows, and persisting a null signature *deletes* the sidecar. The verdict is now two independent facts: signed bytes still rule a hot reload out, while a recorded `sourceUrl` only suppresses the DEBUG half, so overwriting a store-installed plugin's jar in place is still reported (#169)
- **panel**: both store flows launched on `rememberCoroutineScope`, so closing a window mid-swap cancelled between the unload and the load. They now run detached and coalesced per plugin id on `KeyedDetachedJobs`, as the dependency installer already does (#169)
- **settings**: a deep link now navigates a window that is already open. `SettingsContent` initialises its selected section through an unkeyed `remember`, so raising the window brought it to the front still showing whatever page the user last picked. An unresolvable deep link does nothing to an open window rather than defaulting it to FLUCK - reachable from any plugin, since `SettingsProviderImpl.openSettings` forwards an arbitrary string straight through, so a plugin deep-linking to its own page while that page is disabled or RBAC-hidden yanked the user elsewhere (#172)
- **settings**: deiconify lands before `toFront`. Writing `WindowState.isMinimized` only mutates snapshot state, which Compose applies in a later pass, so `toFront` on the next line still ran against an iconified frame - the exact no-op the code existed to avoid. The frame's `ICONIFIED` bit is cleared directly, and `WindowState` is still written so Compose's model agrees (#172)
- **panel**: the rail's icon budget no longer moves when the top bar is hover-revealed. The reserve was computed from the rendered list, whose size drops to zero the instant the top bar shows, which under the default ADAPTIVE icon limits handed about three rows back to the plugin slots and took them away again on every hover, popping icons in and out of the More menu (#172)
- **panel**: the bottom section can no longer be pushed off the rail. The reserve is advisory - `computeSlotIconLimits` returns early in FIXED mode and never reads it - and the section sat after a weighted spacer, so it was what lost on a crowded rail. In this placement the content that goes missing is Settings, Search and Sign Out with no floating cluster behind it. The slots now carry the weight and clip; the section is measured first, and the customize button renders outside the clipped region, matching where its height is reserved (#172)

## Improvements

- **plugins**: `MAX_SKIPPED_CHECKS` moves to `SandboxConfig` alongside `stallGraceMs` and `healthyChecksToClearRestarts`. It is counted in ticks, so its wall-clock meaning is entirely the heartbeat interval, and plugins do declare their own config: a hardcoded 6 gave a plugin asking for 500ms a 3 second ceiling and one asking for 60s six minutes of a watchdog that is not watching (#171)
- **plugins**: the restart budget is read from the config each sandbox was created with, rather than the manager's `defaultConfig`. Consolidating the duplicated give-up check exposed the difference: the copy that used to win stopped the sandbox *without* disabling it, landing on `STOPPED`, where the error boundary synthesises no fallback and no listener is notified (#171)
- **panel**: recording a build upserts the `installed.json` row, which closes a second gap - a hand-copied jar and a Toolbox install wrote no row at all, and `setPluginEnabled` updates an existing row and silently does nothing when there is none, so exactly those plugins could not be disabled persistently. The write returns early when the merged row equals the one already there, and declines to create a row for a jar that is gone (#169)
- **panel**: `ContextMenuItem` gains an `enabled` flag so uninstall can be shown greyed out for system plugins instead of hidden, mapped through to `NativeMenuNode.Item.enabled` as well, or the macOS NSMenu path would render an item that looks live (#169)
- **panel**: `StoreVersionInstaller` and `PluginArtifactCleanup.Hooks` are extracted so the download, promotion and manifest vetting are reachable from a test. The store bridge had duplicated all of it from `StoreMissingDependencyInstaller` without its hooks seam, and it also gains the `NOT_USER_INSTALLABLE` check its sibling has - the one that keeps an api-jar hot swap out of a two-button dialog (#169)
- **settings**: `SettingsWindowState` replaces three loose flags with one holder whose fields are `private set`, so `open()` and `close()` are the only ways in. The raise signal is a counter rather than a flag, because a flag would fail the same way on the third click, and the section request is a second counter, since keying on the section value would navigate once and ignore every later request for the same page. The desktop window's own `isOpen` flag is gone: two sources of truth for "is this window up" is the bug this branch fixes waiting to happen (#172)
- **tests**: the branches with the most consequence now have coverage behind them - the watchdog's budget exhaustion driven through a real watchdog rather than a direct call (the first version passed against the bug, because the self-cancellation only exists inside the watchdog's coroutine), a cancelled restart widened with a latch-blocked pool thread, an alternating stall, listener containment, the build-verdict matrix with real jars and real sidecars, the `installed.json` round trip, and seven cases for the settings deep-link resolver including a built-in section winning over a plugin page claiming the same id (#169, #171, #172)

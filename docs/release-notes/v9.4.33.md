# BOSS v9.4.33

**Release Date:** 2026-08-25

Three changes, all about surfaces that knew something and did not say it: a settings section that said "isn't loaded yet" whatever the real reason, a sidebar icon whose right-click menu offered one row out of a dozen, and a split map that stayed empty until the first split - the one moment it could have done the most. Three build dependencies moved; the browser engine did not.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **A settings section can offer to install the plugin it needs.** `Settings → AI Providers` belongs to secret-manager, and `Editor` and `Language servers` both belong to editor-tab; all three said "isn't loaded yet" for every reason there was no panel, which is true of exactly one of them. A plugin that was never installed, or that the user switched off, does not arrive however long they look at it, and nothing on the screen said so or offered a way out. The notice now tells the cases apart and offers an Install button in the one case where that is the answer (#255)
- **Right-clicking a plugin's sidebar icon opens the plugin's own menu.** The rail icon is the only handle a plugin has while its panel is closed, and it offered exactly one row, "Sidebar settings" - reload, check for updates, install the store version, open the evolver, report an issue, uninstall and whatever the plugin itself contributes all lived behind the panel header's kebab, which meant opening the panel first just to reach them. One definition now builds the kebab, the header's right-click menu and the icon's, so the three cannot drift (#253)
- **The split map is a target before there is a split, and a new tab can say which pane it opens in.** The map needed two panes to say anything, so the foot of the bar was empty until the first split - and splitting was a right-click on a pane in a map that was not being drawn. An unsplit window gets the same frame turned into a target: the centre is the pane you have, four trapezoids cut from the corners are where a new one would go. The new-tab dialog gained the same choice as five chips, and a split can finally go left or up (#254)
- **The drag ghost sits on the pointer instead of 27px off it.** Under `HARDWARE` the ghost is its own cursor-tracking window and it was placed 16px below-right of the cursor, so a 22dp sidebar icon rode diagonally away from the pointer supposedly carrying it - while the lightweight path centred the same icon exactly on it. The heavyweight path is what every platform has run since #128 (#253)

## Features

- **settings**: `PluginSettingsUnavailableNotice` distinguishes never installed, switched off, binary incompatible, inaccessible for lack of permission, still starting, and installed-but-serving-no-panel, with a sentence for each. It leans on `MissingPluginOffer` rather than adding a second install path, so the press raises the host's own `MissingDependencyDialog`, which names the plugin **from the store** and shows the id it will install by - resolving an id against the store, downloading the jar and loading it are the host's to do, none of which a plugin can do for itself. Observing `pluginStates` is what makes the notice self-clearing: the install lands and the section swaps to the real panel without reopening Settings (#255)
- **sidebar**: the rail's menu is `panelMenuItems()` with its actions from `panelMenuActions()`, both shared with the panel header. Two rows stay per-site because they depend on where the menu was opened rather than on the plugin: the rail offers "Open as Tab" - through `requestOpenAsTab`, so an already hosted plugin is focused rather than promoted twice - and no "Minimize", since the icon's own click already toggles the panel and this menu opens just as often with the panel closed. "Sidebar settings" survives, after a divider (#253)
- **panel**: an unsplit window's split map is a click target. The centre names the pane you have, as it is named on the real map, and four corner trapezoids are where a new pane would go; clicking one splits that way (#254)
- **tabs**: the new-tab dialog carries a destination picker - this pane, or a new one on a given side - as five chips next to Cancel and Create, each drawing the window with the new tab's half filled, the way a group header draws which pane its tabs belong to, so it reads without the labels. **Both** new-tab dialogs carry it, the window's and a pane's own "+", because a picker in one and not the other reads as a bug in whichever you meet first (#254)
- **panel**: a split can go left or up. `SplitOrientation` says only which way the divider runs and every caller before this got the new pane second, so the side is now carried by `SplitDirection` and applied by `splitPanel`'s `placeBefore` - at the pane it names, rather than at the branches the recursion walks past (#254)
- **tabs**: right-clicking the empty space after a pane strip's last chip opens what the vertical bar offers on its own empty space - New Tab, Tab Bar Position, Favorite Workspace - plus an entry that hides the strip. One function builds it for both surfaces rather than a copy each; the strip has no `TabBarState` to borrow from, because in LEFT position the window owns the single bar and the panel deliberately builds none. Only "New Tab" differs and it is a parameter, so from a background pane's strip it lands in **that** pane rather than in whichever one the bar happens to lead (#254)
- **settings**: "Only in Split Windows" qualifies the pane tab strip, under the toggle it belongs to and disabled with it. The strip was split-only by rule, on the reasoning that a single pane's tabs are already listed by name in the sidebar - which holds only while the sidebar is expanded, and it collapses to the rail on its own when a panel is narrow, collapses deliberately by chevron, and the top bar is hidden by default now, so a one-pane window could reach a state with no tab titles anywhere on screen. It defaults **on**, so nothing changes on upgrade and the new field needs no migration step (#254)

## Bug Fixes

- **settings**: `PluginState.DISABLED` is not one state, and the first cut of the notice hit its own defect inside its own DISABLED branch. `DynamicPluginManager` writes DISABLED for a user switching a plugin off, for a registration that failed as binary incompatible, and for a plugin hidden because the user lacks access - so "enable it in the Toolbox" was advice that cannot work in two of those three. `pluginSectionAbsence` now takes the crash registry's `isIncompatible` and the manager's `getInaccessiblePlugins()` alongside the state, and its **order is load-bearing twice**: permissions are asked first, because an inaccessible plugin is recorded DISABLED as well and telling that user to switch it on points at a row not listed for them; and incompatible and disabled are asked before installed, because `MissingPluginOffer.isInstalled` counts both as installed and an Install button cannot fix either. All three orderings are mutation-verified - reversing each one fails a named test (#255)
- **settings**: the permission case reaches all three sections. It used to be a parameter only one section passed, so a user who could not access editor-tab was told to go and enable it; it is derived from the plugin id like everything else now, which removes the last caller of `LlmProviderAPIAccess.rememberMissingPermissions` and its hardcoded plugin id (#255)
- **overlays**: the ghost's placement gap was defensive rather than measured. The JVM has no portable click-through, so a window under the pointer was assumed to swallow the drag moving it - measured on macOS with a Robot-driven drag, that is not what happens to a ghost appearing **after** the press: the source window holds the implicit mouse grab, a 22x22 always-on-top window centred on the cursor received nothing, and the source kept all 121 drag events and the release. Both of BOSS's ghosts appear after a long press or a drag threshold, so the case the gap protected does not arise. `OverlayGhost` takes a cursor hotspot now and both callers state the placement their lightweight path already draws (#253)
- **overlays**: the ghost window moves with `setLocation` rather than `WindowState.position`, which is only applied by the next frame - a frame of lag on top of the frame the cursor read is already old (#253)
- **overlays**: the clamp is asked only when the ghost would land where there is no screen, rather than always pinning it inside the monitor the cursor is on. Clamping at a seam between two adjacent displays dragged a tab card up to 45px off the pointer and snapped it back on the other side, for a spill that costs nothing (#253)
- **overlays**: and the screen rects are full display bounds rather than working areas. A working area answers "where may a window be placed", and a drag ghost is not being placed; subtracting the dock and menu-bar insets made those strips read as "no screen here", so a card whose far corner reached into the strip above the display next door counted as off the desktop and was yanked onto the cursor's monitor - the seam artifact back again, in a band the height of a menu bar along the top and bottom of every display (#253)
- **menu**: an all-disabled plugin contribution left an orphan divider. The rule was decided from the raw entry list while the disabled items were dropped inside the loop, so the header grew a stray line above Minimize and the rail got two rules and then "Sidebar settings" - the orphan satisfied the trailing rows' own "anything to separate" guard. Filtered before the divider is decided, and the trailing guard now also refuses to follow a rule with a rule (#253)
- **menu**: Reload Panel and Check for Updates were gated on the window but not on the plugin, while every handler in `BossAppMenuActionEffects` resolves the panel's plugin and returns quietly when it cannot - so a panel with no resolvable plugin got two rows that did nothing at all. Gated on the plugin too, as Uninstall already was (#253)
- **menu**: `panelMenuItems` took `windowId` as a parameter while `panelMenuActions` read `LocalWindowId` itself. Two sources for one window is how the built-in rows and the contributed rows end up addressed at different windows, so it reads the local too. The rail's menu also reads `currentItem` throughout rather than mixing it with `item`, so a native menu outliving its composition cannot act on two different panels from one open menu (#253)
- **panel**: clicking a trapezoid or a dialog chip does not split on the click. It records the request and the split happens once the tab exists, because a pane created empty is closed again about 50ms later by `checkAndCloseEmptyPanels` - the path the pane menu's Split entries already took, so the dialog is a view over the same pending split, which is what lets a trapezoid open the dialog with its direction already chosen (#254)

## Improvements

- **sidebar**: a rail icon's menu is built on the right-click, not on every pass. The rail attached an eagerly-built menu to every plugin icon, so ~15 plugins meant ~75 registry subscriptions where there had been five, every MCP tool registration recomposed every icon, and each plugin loading at startup re-queried every other plugin's contributed items for panels nobody had opened. `Modifier.contextMenu` takes a provider now, composed only while the menu is up, so the rail pays nothing until someone right-clicks and the plugin-facing "`items()` must be cheap" contract goes back to meaning what it did. The evolver rows could not survive composition dying with the menu - they launched on a `rememberCoroutineScope` and the menu closes on the very click that starts the MCP call - so they dispatch on a supervised scope that outlives it (#253)
- **panel**: `BossPanelTopBar` takes `PanelMenuActions` as a type instead of taking the actions apart and putting them back together, which is the drift this work removes, one layer down - a field added to `PanelMenuActions` reached the rail and not the header. Ten pass-through parameters go, `pluginId` and `updateAvailable` gain a reader, and the badge and trailing controls move into their own composables, which is what keeps the function inside detekt's length limit without re-baselining it (#253)
- **panel**: `rememberPanelMenuActions` is renamed `panelMenuActions`. It builds fresh lambdas every pass, so the `remember-` prefix promised a memoisation nothing was getting (#253)
- **plugins**: the RPA family is attributed to the risa organisation in the store. LLM RPA, RPA Recorder and RPA Engine still sat on the boss organisation, where the original backfill put every plugin row; a later migration fixed that for newly created plugins but deliberately does not re-derive ownership when a new *version* is published, so no amount of CI activity moves an existing row. The three move together because they are one product in three pieces - the recorder captures, LLM RPA plans, the engine runs - and showing one product under two owners is the thing to avoid. Named rather than derived: `author_name` already reads "Risa Labs" on all three and that is free text written at publish time, not an ownership record. Nothing changes for a reader; all three are public and published, and `user_can_view_plugin_row` short-circuits before it looks at `org_id` (#249)
- **tests**: `PanelMenuItemsTest` asserts the menu's structure as a list - order, the orphan divider, the disabled uninstall row, no double rule - where a "does this row exist" check cannot see it; the all-disabled case was verified to fail against the previous shape. `PanelMenuActionsTest` covers the gating half directly, including the evolver rows against real MCP registrations. `SidebarIconMenuTest` gains a resolvable plugin, the no-resolvable-plugin case, and a pin that Open as Tab focuses an already-hosted panel rather than promoting a second copy over the same cached component (#253)

## Known Limitations

- **The consent dialog opens over the main window, not the Settings window.** `SettingsWindow` is composed inside the main window's subtree and opts its own dialogs out of heavyweight overlay routing precisely so they do not open centred on the main window - but the dependency dialog is raised through `PluginDependencyEventBus` and composed by `BossAppDialogs`, outside that opt-out. It is always-on-top so it is not lost, just not where the press happened; routing it means the prompt carrying a window id (#255)
- **A raised offer is not a shown dialog.** `PluginDependencyEventBus.report` drops silently when a prompt for that plugin is already queued, so `offerIfMissing` returning true is not proof anything appeared. The press logs whatever happens, matching the bookmarks shelf's call site (#255)
- **`null` from `isInstalled` is not an offer.** It means the question cannot be answered here - no active manager, no injected installer factory - so the section falls back to the neutral wait rather than offering to install something that is already there (#255)
- **No per-platform hotspot inset on Windows or Linux, deliberately.** A few pixels of gap does not prevent what it would be insurance against: the ghost is repositioned each frame, so any pointer move larger than the gap lands inside the stale rect whatever its size, which was as true of the old 16px as of 4 - and both platforms use the same implicit-capture model the macOS measurement relies on (`SetCapture` on Win32, a passive pointer grab on X11) (#253)
- **The pane tab strip's Settings helper has to stay above the next `SettingsSection` in the file.** `SettingsSearchIndexDriftTest` attributes a label to whichever section precedes it textually, so a helper placed at the end of the file indexes its rows under the last group on the page. This cost a red build (#254)
- **The pane strip stays out of the `ChromeBar` family.** Its members get a View-menu checkbox and a Settings row from iterating the entries; the strip already has its own Settings toggle, and it is per-pane content chrome that exists only in a split window in LEFT position rather than one of the window's four edges (#254)

# BOSS v9.4.13

**Release Date:** 2026-08-16

A release about surfaces that looked finished and were not. The home screen had had no functional change since the first public release and silently failed at part of what it advertised, the bars' right-click menu offered two actions the app does not have, Google's AI Mode left the browser pane permanently blank, and overlay windows came up opaque on macOS after the app had been backgrounded once.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **The home screen is rebuilt, and its actions now do something.** `DashboardEventBus` - window scoped, IPC bridged, documented for exactly this - had nine emit functions, nine handlers and **zero emitters anywhere in the repo**, while the screen took 12 action callbacks that each mount point had to re-supply; the browser's `about:blank` surface passed 11 of them as `{ /* No-op */ }`. `HomeScreen` takes no action callbacks at all now, builds its own `HomeActions` from `LocalWindowId` and emits on the bus, so one code path serves both mounts (#185)
- **Tools on that screen are derived rather than listed.** `TabRegistry.getAllTabTypes()` plus the panel registry supply every installed tool with its own icon, and plugins the user does not have come from `PluginRepository.listPlugins()` with an Install tile, so the grid doubles as discovery. An earlier revision used a hardcoded plugin-id-to-icon table, which is stale by construction; icons come from `plugins.icon_url` now, so populating that column is enough with no client release (#185)
- **Right-clicking a bar showed "Edit" and "Save".** Both were placeholders committed with the bar and never wired up - `onClick = { /* Handle edit action */ }` and its twin - so the one menu a user was most likely to find by accident promised two actions that do not exist. Three working entries replace them, and the same menu now reaches the bottom bar and both sidebar strips, which had none (#187)
- **Google's AI Mode left the pane blank and it stayed blank.** The document loads completely and stays interactive - DOM complete, layout correct, timers firing - but `requestAnimationFrame` never fires once. Ruled out by measurement: not raster, not Graphite, not the GPU path, not CSS, not filters or animations, not a renderer swap. What repairs it is the view leaving and re-entering composition, so a beacon after each main-frame commit reports whether a frame has been served and two consecutive "no" readings re-attach the view (#183, #186)
- **Overlay windows came up opaque on macOS.** Measured, not eyeballed: exactly #999999 across the whole window, which is the 40% dialog scrim over pure white. Every Java-visible flag was already correct on a window that was visibly grey, so the opacity lives below AWT - re-activation is when AppKit re-applies a window's level and style bits and resets `NSWindow.isOpaque` behind AWT's back, and every overlay here is `alwaysOnTop` (#184)

## Features

- **home**: the tool grid wraps into as many columns as fit instead of a horizontally scrolling strip that stranded most tools past the right edge, and both reflow decisions are pure functions so they are pinned without a display. Arcade was already reachable from the New Tab dialog and missing here only because nothing asked (#185)
- **home**: Install on a discovery tile reuses `StoreMissingDependencyInstaller` rather than adding a second download path - AGENTS.md records five separate defects found in review of that method which a new one would have to re-solve (#185)
- **ui**: the bar context menu carries Hide `<bar>`, Enter/Exit Focus Mode and Appearance settings, and attaches to the bar container rather than the blank spacer, so the whole strip answers while each icon's own menu still wins on the icon itself. `VerticalBar` gained the `modifier` parameter `HorizontalBar` already had (#187)
- **settings**: the four bars are persisted flags on `WindowAppearanceSettings` beside `showTitleBar`, with matching checkboxes under View and toggles in Settings, so hiding one has a way back. All default true and the manager decodes with `ignoreUnknownKeys`, so an existing settings file reads back unchanged; none of the `FocusModeSettings.decodeWithDefaults` machinery is needed, because that exists for defaults that differ per platform and these do not (#187)
- **workspace**: with no project selected, everything that needed a directory reached for `user.home`. On macOS that is the worst available default - the first `ls`, or any agent started there, walks into `~/Desktop`, `~/Documents` and `~/Downloads`, and TCC puts a permission prompt in front of the user for each one. `DefaultWorkingDirectory` resolves to `~/BossProjects` instead, which BOSS already owns and macOS does not guard, and is the one place that decides for all eight call sites. It does not select a project: "No Project" stays "No Project" (#182)
- **browser**: the frame-stall repair is deliberately narrow, since it is a recovery for a fault inside the JxBrowser widget rather than a cure. Only http(s) main-frame commits are watched, only under `HARDWARE_ACCELERATED`, only while the view is on screen, and a failed beacon read counts as "not stalled" - treating a raced round-trip as a stall would flicker healthy pages (#183)

## Bug Fixes

- **home**: panel tiles dropped the click when the plugin had not registered yet. `panelToggleEvents` looked the panel up once; it waits via `awaitRegistryCondition` now, as `panelOpenEvents` already did (#185)
- **home**: all 11 event-bus cards failed silently when `LocalWindowId` was null, each wrapped in `windowId?.let { }`. Reported now (#185)
- **home**: "Open in New Window" opened the project in the *wrong* window. Project state is per window, so selecting after `createNewWindow()` applied it to the window the user clicked in; it uses `createNewWindowWithProject`, as the two other callers of that flow already do (#185)
- **home**: opening a recent file never updated its recency, so it slid down the very list it was clicked in. Routed through `FileEventBus`, the only recording path (#185)
- **home**: the X on a suggested site did nothing and "Clear" could not remove them - 17 hardcoded promos live in no persisted list. Dismissals are persisted and save immediately rather than through the 5s debounce, so a dismissal followed by a quit is not lost (#185, #188)
- **home**: "Clear" on Recent pages was hidden in exactly the case it was added for - gated on `recentPages.isNotEmpty()`, so a fresh install with no history and seventeen suggested sites on screen had no Clear at all (#185)
- **home**: three of seven shortcut hints were invented; there is no `FILE_OPEN`, `PROJECT_OPEN` or `TERMINAL_NEW` action at all. Labels resolve from the live keymap and are omitted where no binding exists (#185)
- **home**: "Open File" stopped landing on the File tab. The call site it replaced set `selectedTabType = TabType.FILE`; the handler it now routes through only opened the dialog (#185)
- **home**: a failed install made a plugin vanish from the grid. `rememberHomeTools` passed `exists = { true }` and omitted `isIncompatible`, reducing `installedAndOnDisk` to `LOADED || true`, so a plugin whose install failed as binary-incompatible counted as installed, was filtered out of the discovery half, and having registered nothing had no ready tile either - with no way to retry from the surface that exists to offer it. Both predicates are supplied now, identical to `MissingDependencyReporter.forManager` (#185)
- **home**: the discovery half was a cold-start race. The home screen is what an empty panel renders, so it can compose before `PluginStoreSetup` has a repository: `LaunchedEffect(Unit)` read null, `.orEmpty()` swallowed it, and nothing re-ran the effect. `HomeCatalogAccess` is a `StateFlow` now and the fetch is keyed on it (#185)
- **home**: tool ids used only half of `TabTypeId` / `PanelId`, so two plugins registering the same id string lost a tile - the same collision this change fixed on the event side. `TabTypeId` is a data class over `(typeId, pluginId)`, so rebuilding the key from `typeId` alone does not equal what a plugin registered and the lookup misses in silence (#185)
- **home**: installing the last available plugin while AVAILABLE was selected hid the chips over an empty grid with no control to get back. Falls back to ALL whenever the chips are hidden (#185)
- **home**: `addTab` after a successful lookup did nothing and said nothing when there was no active tabs component - the last silent branch in the handler (#185)
- **files**: recent files that no longer exist stayed on screen and opened empty editors; `fileExists` had no callers. They are pruned from the display now (#185)
- **files**: the prune was persisted, which its KDoc denied. `saveImmediately` serialises whatever the flow holds and `recordFileOpen` / `removeFile` / `clearAll` all schedule a save, so the first file opened after launch rewrote `recent-files.json` from the filtered list - recent files on an unmounted volume or a disconnected share were permanently deleted by the act of opening one local file. `File.exists()` is false for a disconnected share, which is normal at login. The recorded list and the displayed list are separate flows now: `_allFiles` is persisted, `recentFiles` is `visibleFiles(_allFiles)` (#188)
- **plugins**: the home store installer captured one window's plugin manager. `register` runs per window and `HomeCatalogAccess` keeps the first provider, whose installer closed over that window's `DynamicPluginManager` - closing that window disposes the manager, so every other window's Install tile then loaded into a dead manager and reported success having put the plugin somewhere nothing renders. Resolved per install from `anyActiveManager()` now (#188)
- **plugins**: `dispose` cancelled a manager but never removed it from `liveManagers`, relying on the WeakReference being collected, so a disposed manager stayed in `activeManagers()` for an unbounded time while `isPluginKnown`, `jarPathOf` and the api hot swap all assume "live" (#188)
- **plugins**: `PluginIconLoader.load` wrapped suspending work in `runCatching` and cached the result either way, so it also caught `CancellationException` - and the `LaunchedEffect` behind a tile is cancelled routinely by a filter change, a reflow or a remount, each writing a permanent "no icon" for a perfectly reachable URL. Cancellation is rethrown before anything is cached (#188)
- **plugins**: `MAX_BYTES` on icon fetches was checked after `readRawBytes()`, so it bounded nothing its KDoc claimed. `Content-Length` is checked first (#185)
- **ui**: Sign Out could have become unreachable. Settings, Search and Sign Out live only in `BossTopRightBar`, and the cluster that re-homes them read `topBarGone && !showTopBar` - but `showTopBar` is `FocusModeEdgeRevealState.shown`, which is permanently true whenever focus mode is off. So in the default configuration, hiding the top bar evaluated `true && !true`, the bar went away and nothing replaced it; the native View menu carries Settings but neither of the other two. The two absences are not symmetric and the predicate now says so: a standing preference suffices alone, focus mode keeps its `!showTopBar` pairing (#187)
- **ui**: `focusQuickActionsRailRows` deliberately ignores `showTopBar`, so it returned three while the placement said NONE - the rail reserved three icon rows and rendered nothing in them (#187)
- **ui**: hover strips were laid over live content. `FocusModeHoverStrips` gated only on `settings.hides(edge)`, against its own KDoc - a bar hidden by preference is not coming back on hover, so its strip was a dead band, and sweeping the top edge flipped `shown` and took the quick-action cluster away without putting the bar back (#187)
- **ui**: "Customize Sidebar..." force-reveals the strip so the click has somewhere to land, but only set the focus-mode flag, which the new conjunction is no longer enough on its own. It clears the preference as well, since you cannot customise a bar you have hidden (#187)
- **ui**: `rememberBarContextMenuItems` read a composed snapshot of the settings and wrote it back on click, which could revert a concurrent write from Settings or another window. It reads `currentSettings.value` at click time now, matching the two neighbouring writers (#187)
- **overlays**: the native non-opaque flag is re-issued once the overlay is on screen, at `windowOpened`, `windowActivated` and `windowDeiconified` - an overlay already open across a background-then-foreground transition gets no second `windowOpened`, and the New Tab dialog can sit open indefinitely. The assignment has to pass through an opaque colour, because both layers below short-circuit on the Java value already being right: `Window.setBackground` returns early on an equal colour and `LWWindowPeer.setOpaque` is guarded on the flag already matching, so driving it true then false is the only route that runs `updateOpaque()`. Both land in one EDT turn, so no frame paints between them and there is no flash (#184)
- **overlays**: a half-completed cycle manufactures the very bug it repairs. `Window.setBackground` applies `super.setBackground` first and then throws - `IllegalComponentStateException` for a full-screen window, `UnsupportedOperationException` where per-pixel translucency is unavailable - both before `setLayersOpaque(this, false)` and before `peer.setOpaque(false)`, leaving the layered, root and content panes opaque from the first assignment while `window.background` already reads alpha 0. That is an opaque content pane filling before Skia draws, which *is* the #FFFFFF mechanism. Refused up front when the configuration cannot do it, and unwound in `onFailure` with the ancestor chain logged (#184)
- **overlays**: `EnsureOverlayWindowTransparent` is deleted rather than moved. It tested `window.background.alpha`, but Compose applies `transparent = true` through skiko's `transparentWindowBackgroundHack`, which returns `Color(0,0,0,0)` for every host except Windows-with-Direct3D - so on macOS that branch was unreachable, and the assignment was a no-op even when reached. On Windows without Direct3D it fired on every overlay open, logged a WARN, and overwrote a null skiko sets deliberately. Its KDoc offered "the absence of the warning is itself the signal that the diagnosis was wrong" as its falsification test, and that test was met (#184)
- **overlays**: the repair is not inert off macOS by accident. The retained background check ran in a `SideEffect` before the repair's listener and normalised the value the repair reads, so the "cannot regress" argument was circular, and the skiko reading behind it was backwards. `shouldReassertTransparency` gates on macOS explicitly and makes it true by construction (#184)
- **browser**: the two-reading confirmation on the frame-stall probe did not exist. The beacon arms lazily at read time, so the first call always returned "0" whatever the page was doing - the rAF callback cannot have run before the call that registers it - and the decision rested on a single reading while the KDoc claimed two. The first call is named `ARM_DELAY_MS` now and two real readings follow it; a commit whose arm read fails bails rather than silently demoting the next reading into the arm (#183)
- **browser**: the probe blocked the EDT. `readFrameBeacon` ran `executeJavaScript` on `Dispatchers.Main` with no timeout, against a renderer already suspected of misbehaving, on every http(s) commit. It runs on a dedicated single daemon thread raced with `withTimeoutOrNull` now, with only the generation bump hopping to Main (#183)
- **browser**: `viewComposed` was a plain boolean on the one effect this codebase documents as order-unsafe. It rode the same `DisposableEffect` as `visitTracker.setVisible`, which is ref-counted precisely because a tab moving between windows tears down one composition while building another in an order the effect does not control - so dragging a tab to another window landed it on false while the tab was on screen and the watchdog was dead for that tab. It fails safe, which is what makes it nasty: no spurious re-attaches, no signal, just no fix. An `AtomicInteger` surface count now, same remedy as the neighbour (#183)
- **browser**: the visibility gate means on screen, not merely composed. A minimized window keeps its composition alive, so its foreground tab passed a composed-only gate while Chromium was legitimately not painting it - and the cost of that false positive is a view rebuild, which drops keyboard focus and IME state (#183)
- **browser**: a timed-out post-repair read was recorded as a recovery. `isStalled(null)` is false, so `recovered = !isStalled(readFrameBeacon())` came out true whenever the probe failed to answer - right polarity for the *decision*, exactly wrong for the *outcome*, because it cleared the ineffective run in the one case the give-up cap exists for. A renderer wedged badly enough to stop answering probes is one re-attaching will not fix, yet the cap never tripped and the tab would flicker once per cooldown forever while the log claimed "re-attached and painting". A tri-state `repairOutcome` - painting, still blank, unknown - credits only an observed recovery (#183)
- **browser**: attempts are booked pessimistically and upgraded on confirmation. `claim()` consumed the slot but the outcome was recorded a beat later, so a fresh commit superseding the job, the view leaving composition, or a probe that never answers left the attempt unaccounted for (#183)
- **browser**: the probe cancel only covered the timeout path - the one case its comment did not claim. `withTimeoutOrNull` swallows only its own `TimeoutCancellationException`, so when the enclosing job was cancelled instead, `probe.await()` rethrew and unwound straight past the `if (reading == null) probe.cancel()` that followed. Concretely: commit A arms a probe that blocks on the single-thread executor, commit B supersedes A, and A's probe later runs against B's document, arming B's beacon ahead of B's own `ARM_DELAY_MS`. Moved into a `finally` (#186)
- **browser**: a stall inside the cooldown was left blank and unlogged. The decision point is 2500ms after a commit and the cooldown is 10s, so two stalling commits less than about 7.5s apart left the second unrepaired, silently - and AI Mode is a page people iterate on, so a follow-up query put the user straight back in the original bug with nothing to explain it. `FrameStallPolicy.remainingCooldownMs` lets the job wait out the remainder and claim once, honouring the rate limit rather than shortening it, and re-judges after the wait (#186)
- **browser**: a retired tab was deferred anyway, and could be silently un-retired. `claim` tests the give-up cap before the cooldown, so `GIVEN_UP` came back while `lastReattachAt` was still recent; asking for the decision and the leftover cooldown as two separate calls could not tell those apart, so an abandoned tab burned the remaining wait and one more probe, and if the page happened to paint during it had its ineffective run cleared. `claimOrDefer` answers with the reason attached in one synchronized call, which also removes a boundary race where the remainder could reach 0 between the two reads (#186)
- **browser**: same-document navigations are no longer probed. The beacon arms once per document and latches at painted, so probing a `pushState` or fragment navigation read the flag the original load left behind - not evidence about that navigation, and it reached `recordHealthyNavigation` and cleared a legitimate ineffective run on a stale reading (#186)
- **browser**: `frameStallScope` had no `CoroutineExceptionHandler` though `contextMenuScope` forty lines below carries one, so an escaping failure landed on the default handler and printed to stderr, bypassing `BossLogger` (#183)
- **workspace**: `mkdirs()` returns false when someone else won the race - it reports "I created it", not "it exists". This change deliberately adds a second concurrent creator, the startup warm-up racing the first window's `resolve()`, with `validateProjectLocation` as a third; interleaved on a cold first launch the loser fell through to the home-directory fallback, putting the TCC prompts back on exactly the launch this exists to fix. `Files.createDirectories` is idempotent by contract (#182)
- **workspace**: the resolved path was baked into saved layouts. `workingDirectory` used to be null with no project, and `WorkspaceApplier` reads null as "wherever the project is at restore time", so persisting `~/BossProjects` verbatim froze it - re-applying a layout saved with no project, this time with a project selected, would open the terminal in the projects folder. `WorkspaceExtractor` writes null for a terminal sitting in the default (#182)
- **workspace**: the failure that actually happens was silent. Only `SecurityException` was logged, which needs a security manager nobody installs; a read-only home, a quota, or a file at the path made `mkdirs()` return false and returned null with no line at all (#182)
- **workspace**: `getDefaultProjectsDirectory()` built `"$userHome/BossProjects"` with a literal forward slash while `path()` returns `File(...).path`, which Windows normalizes to a backslash - nothing is broken today because both sides of the comparison come from `path()`, but a future caller would have silently never matched there (#182)

## Improvements

- **home**: `Dashboard.kt`, `ActionCard.kt` and `EmptyContentScreen.kt` are deleted, the last being 312 lines of a second, unreachable home screen with no call site. `onActivatePlugin` and `onNewTerminal` were dead on both ends and go with the 26-line four-layer callback thread behind them; `DashboardEventBus.activatePlugin` and its handler follow, having become a dead emitter with no IPC consumer either. Net 1,474 lines removed against 3,234 added, most of the latter being 30 new tests in a package that previously had one (#185, #188)
- **home**: three shared definitions were extracted rather than copied - `satisfiesVersionFloor`, `formatShortcutLabel` and `HomeToolAccess` on the existing `ACCESS_GATED` list (#185)
- **home**: the store listing was re-fetched on every mount, and the screen remounts whenever a panel's last tab closes. Cached for the session; failures are not cached, so a transient outage retries (#185)
- **plugins**: `pluginStates` was collected at window-scaffold scope, so every plugin state transition invalidated the scaffold and re-ran its `CompositionLocalProvider` body - dozens of times during startup with 33 plugins. The local carries the flow now and `rememberHomeTools` collects it, confining that to the one screen that reads it (#185)
- **plugins**: `dismissedSuggestions` grew without bound - `removePage` recorded a key for every page ever dismissed, though a removed page is already excluded by being removed. Recorded only for the padding suggestions now, which bounds it to that list, and intersected on load so an existing file self-trims (#185)
- **plugins**: `HomeCatalogAccess.initialize` claimed first-wins and assigned unconditionally, and moved out of `PluginLoaderDelegateImpl`'s constructor to `PluginLoaderDelegateSetup.register`, beside the other process-wide wiring where a reader would look for it (#185)
- **plugins**: two dead fields dropped - `HomeTool.description` and `HomeToolLaunch.Install.version`, the latter doubly dead since `install()` takes only an id. `PluginIcons.cache` was typed `Result<Painter?>` but only ever stored `Result.success`, reading as though failures were `failure`; a small holder says what it means (#185, #188)
- **browser**: the cap and cooldown are a lock-guarded `FrameStallPolicy` with the clock injected, following `EngineWedgeDetector` rather than only citing it. Inline it was five `@Volatile` fields testable only by driving a real browser; extraction also removed a non-atomic read-modify-write on counters a superseded job could still touch, and moved the cooldown onto a monotonic source where an NTP step cannot stretch it. The give-up run decays on any navigation that paints unaided, so three ineffective attempts spread across hours of healthy browsing no longer retire a tab as if they had been consecutive (#183)
- **browser**: the deferral logs at INFO. At DEBUG it was invisible in a shipped build while leaving the page blank for up to another 10s with nothing to explain it, and `notePaintedUnaided` is shared by both paths so the revival line cannot go missing on one of them (#186)
- **overlays**: the transparency sampling stays, at DEBUG, so a recurrence does not have to be re-instrumented from scratch - turn it up with `BOSS_LOG_LEVEL=DEBUG`. It is gated on the effective log level, because `logger.debug(cat, msg, mapOf(...))` builds its map eagerly, so the demotion alone saved nothing: every overlay open still paid three times for a tree walk, reflection and a `String.format` per ancestor, on the EDT. Reflective handles are cached (#184)
- **overlays**: the sample walks the superclass chain rather than matching `org.jetbrains.skiko.SkiaLayer` by exact class name - Compose instantiates the layer as its own subclass, so the first live run reported `layerFound=false` on every overlay of a build that was demonstrably rendering. It also skips a window that is no longer displayable, since a context menu dismissed within one EDT turn made the deferred sample find no layer and report `willPaintOpaque=true`, indistinguishable in the log from the failure being hunted (#184)
- **workspace**: `DefaultWorkingDirectory.nominalPath()` answers where the directory would be without creating it. The extractor never needed it to exist - `persisted()` only compares strings - so passing `path()` bought a `createDirectories` syscall on the composition thread for nothing, and that producer re-runs on every panel split and close and on every browser title update, not just on save. It also closes an edge: `path()` answers with the home directory when creation fails, so a transient failure at extract time would freeze the resolved default into the saved layout, which is exactly what `persisted()` exists to prevent (#182)
- **workspace**: `WorkspaceApplier` resolved per tab, so restoring an N-tab workspace asked N times; the resolve is hoisted into `applyWorkspace`. `SystemUtils.getDefaultProjectPath()` is deleted rather than repointed - it had no callers and returned the process working directory, which for a packaged `.app` is `/` (#182)
- **plugins**: dismissing everything is permanent, and its KDoc now states that as a property rather than leaving it implied. It is deliberate - the alternative left seventeen undismissable promo cards - but "there is no way back short of editing the json" should be written down (#188)
- **tests**: 30 new tests on the home screen, including `HomeActionRoutingTest` as the guard for the original defect (it fails if a future mount point can be handed an inert home screen), `HomeInstalledPredicateTest` on the adapter layer where the vanishing-plugin defect lived, and a check that every event flow is collected by a handler - an emitter with no handler is as dead as the handler with no emitter this change found on the bus (#185)
- **tests**: `RecentFileVisibilityTest` names both halves of the prune bug in sequence and says plainly which half is structural rather than tested. `FrameStallPolicyTest` covers `claimOrDefer` granting, deferring and refusing, that a given-up tab is refused even with cooldown left to read, and that the deferred wait is exactly what makes the next claim succeed (#186, #188)
- **tests**: the bar tests assert reachable inputs. `steadyStateShowTopBar` derives `showTopBar` the way `EdgeRevealEffects` does rather than letting each case pick its own, which is the gap that let the Sign Out bug through - the old tests passed by asserting `showTopBar = false`, an input the scaffold cannot produce in that configuration. Verified by reverting the predicate: six tests fail against the old one (#187)
- **tests**: `WorkspaceExtractorTest`'s thirteen `extractCurrentWorkspace` calls had started creating `~/BossProjects` on every machine that ran the suite, the exact thing `DefaultWorkingDirectoryTest`'s seam exists to avoid. They go through a wrapper that supplies a fake (#182)

## Known Limitations

- **A frame stall that begins after a document has already painted is invisible.** The beacon arms once per document and latches, so if Google ever serves the AI Mode transition client-side this stops firing, silently. Catching it would need a liveness beacon - a rolling rAF timestamp against wall time - rather than a latch, which is a different design from the one the measured failure asked for (#186)
- **`overlayWillPaintOpaque` is not a health check.** It read false on a window that was visibly grey, and that disagreement with the screen is what produced the diagnosis. It describes one layer's clear colour and nothing more (#184)
- **The dependent of a newly installed plugin is not reloaded**, and the home screen's Install tile inherits that: with two windows open, the window that installs may not be the one that shows the change until relaunch (#185)
- **`newWindow()` from the home screen does not carry the current project.** That is parity with the card it replaces, left as a separable decision (#185, #188)
- **Accessibility labelling of the new tiles and chips matches surrounding house style** rather than being improved here; it is better as one pass over the app than piecemeal (#185, #187)
- **Dropping the stats strip leaves `DashboardStatsManager` with four writers and no reader.** Left in place rather than deleted under this change (#185)

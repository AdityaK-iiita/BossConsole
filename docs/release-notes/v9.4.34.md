# BOSS v9.4.34

**Release Date:** 2026-08-26

Two changes, and between them the window opens differently: all four bars are hidden by default, so a fresh window is its content plus the vertical tab bar and nothing else. That is only a safe default because of where those bars' contents went - a Tools launcher that reaches every plugin panel the icon strips used to hold, and a footer under the split map carrying Sign Out, Settings, Tools and Search. The bar's own width is now a drag on its trailing edge rather than a slider in Settings. No dependency moved.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **A Tools launcher, so a window with no icon strip still reaches every plugin.** A plugin was reached by clicking its icon in the left or right strip, both strips can be switched off, and with the top bar hidden a window could end up with no way to open a plugin at all: no menu, no palette, nothing that lists them. One app-grid button appears wherever there is chrome to put it and opens a searchable grid of every tool, matched on label and id, deliberately **not** filtered by the sidebar's hidden set - this dialog is the reachability backstop, so a plugin someone hid from a strip is exactly the one they will come here to find (#263)
- **A window opens as content plus its tab bar.** Top bar, bottom bar and both icon strips default to hidden; the status line stays, because nothing replaces it - the current URL, memory and transient status messages are reachable from no menu and no launcher, and it costs one 30dp row where a strip costs 41dp of width. A fresh install is 62dp of vertical chrome and 205dp horizontal. The host actions are Sign Out, Settings, Tools, Search in that order everywhere they are drawn, from one list feeding the rail, the floating cluster, the tab bar's footer and the top bar (#263)
- **macOS keeps the traffic lights clear without a full-width title row.** The window sets `apple.awt.fullWindowContent`, so close / minimise / zoom are drawn over the content and the title row existed only to hold them; reserving the full width to protect one 78dp corner is the wrong shape. The clearance now lands on whatever chrome is topmost - the update banner, else the top bar, else both leftmost columns - and falls back to the title row when nothing there is wide enough. `macTrafficLightInset` is a pure decision with a test per case, because every wrong answer is a visible defect only visible on macOS (#263)
- **Drag the vertical tab bar's edge to resize it.** The width had a slider in Settings, which is the wrong place to be when the thing you are judging is on screen next to it. The trailing edge is a 6dp grab strip, overlaid on the bar's own painted chrome rather than laid out beside it, and the drag previews while only the release persists (#256)

## Features

- **tabs**: the vertical tab bar's trailing edge is a 6dp drag strip. The width is recomputed from where the drag started plus total travel rather than accumulated delta by delta - identical until the width hits either end of its range, and then not, since an accumulator goes on taking deltas the width cannot follow and dragging back does nothing until the pointer returns past wherever it stopped tracking. `BarResizeTest` pins the sums, since that one is only ever felt. Disabled while the bar is collapsed to its rail, whose width is a different number (#256)
- **tools**: the launcher's placement is a pure function of what is drawn. Both strips on and it appears nowhere, since every plugin is already one click away; left strip off and it joins the right strip below its slots; right strip off and it joins the left; neither, and it sits beside Settings wherever Settings currently is. The dialog shows tiles rather than rows, reusing `homeToolColumns` so the two grids in the app wrap on one rule (#263)
- **tools**: it answers the keyboard like a launcher rather than a dialog with a filter in it. The search field has focus the moment it opens, so the first keystroke filters rather than being swallowed; Enter takes the top match; Escape closes. Both keys are handled on the **preview** pass, because the focused text field consumes them and a bubbling handler would never see either. Enter with nothing matching does nothing, rather than closing as though it had opened something (#263)
- **tabs**: the FAVORITES label opens the Bookmarks panel, which is where the rest of them are. It goes through `MenuActionsHandler.triggerRevealPlugin`, the same event the View menu's Reveal Plugin raises, so there is one path rather than a second. The label is only clickable where there is something to open: not installed, or installed and not serving its API, and it is inert rather than clickable-and-silent, since each of those states already carries its own explanation and its own Install button (#263)
- **panel**: double-click a pane's tab-bar group header to show it alone. The split map already zoomed a pane on double-click and the header names the same pane, which made the gesture a property of the map rather than of panes - and the header is the one you are already looking at when you want a pane bigger. Both are `combinedClickable` with the same pair now, and the tooltip says so, since a double-click is not discoverable otherwise (#263)
- **tabs**: hovering a tab in the pane strip reveals a cross to close it. The cross takes real width while shown, so chips to its right shift over: a 20dp chip has no room to overlay a target anyone could hit, and reserving the width permanently would cost the strip about a third of the tabs it can show. The pointer is over the favicon when the cross appears to its right, so the chip under the pointer never moves out from under it, and hover is tracked on the row around both rather than on the chip, where it would drop the instant the pointer crossed onto the cross. The collapsed rail deliberately passes none (#263)
- **tabs**: the hover drawer carries the same chrome as the pinned bar. It had the tabs and the split map but neither the project and workspace pickers nor Sign Out, Settings, Tools and Search - and while the drawer is open it is the only bar on screen, so those controls were reachable from the pinned bar and from nowhere at all once it was collapsed. Both slots come from the same values the pinned bar gets, and neither is rendered twice (#263)
- **tabs**: the revealed drawer takes the host actions back from the corner. Three states where there had been two: an expanded left bar has a foot for them, a collapsed one draws its rail and nothing else so they float in the corner, and a collapsed bar whose drawer is open has a foot again for as long as the drawer is up. `verticalBarHasFoot` is pure and pinned per state, because two of the three look identical in the settings and differ only in a transient flag, and both ways of being wrong are silent: the actions render twice, or nowhere (#263)
- **settings**: "Only in Split Windows" now defaults **off**, so a one-pane window gets the favicon strip too. That is the window most likely to need it - the top bar is hidden by default and the sidebar collapses to its rail on its own when a panel is narrow, so a single pane could end up with no tab titles anywhere on screen. Switching the option on restores the split-only behaviour every earlier build had (#263)

## Bug Fixes

- **tabs**: the resize band overlays the bar instead of taking width beside it. As a 6dp strip laid out between the bar and the content, where the divider had been 1dp, it pushed the bar's contents 5dp further from the boundary and read as a margin down its right edge. It is an overlay on the bar's own trailing edge now, costing no layout width, landing on the horizontal padding every row already carries so it sits over space rather than over a tab's close button. It has to overlay the **bar** rather than the content: JxBrowser composites its surface above the Compose scene, so a band over a browser pane would never see the pointer (#263)
- **tools**: the launcher decided it was not needed whenever both strips were *preferred* on, even with focus mode clearing both - which is a window with no way to open a tool at all, the exact hole the launcher exists to close, reachable by turning focus mode on. `asDrawn` is now the one notion of what is on screen, and it reads the standing focus-mode state rather than the reveal flag, so a bar hover-revealed for a few seconds does not move the launcher. It only ever subtracts: a preference of "off" stays off whatever focus mode does (#263)
- **tools**: the dialog vanished about 200ms after opening, from the floating cluster only. The cluster is a heavyweight always-on-top window and `FocusModeQuickActions` swaps it for an in-place rendering the moment the main window loses focus, which opening a dialog does - so the subtree holding `showDialog` was disposed, taking the dialog with it. The state is on `BossAppState` and the dialog is composed in `BossAppDialogs`, with the strips taking a callback rather than a flag (#263)
- **tabs**: the Favorites header was inert. `BossDraggableComponent.activatePlugin` matches on `pluginContentId.panelId`, so passing `BOOKMARKS_PLUGIN_ID` matched nothing and returned silently - the parameter was called `pluginId` while its own KDoc said "The panel ID", and the two ids for this plugin even look alike. It passes `PanelIds.BOOKMARKS` now, the parameter is `panelId` in both `activatePlugin` and `triggerRevealPlugin`, and a miss is logged rather than swallowed: every route in is a user action, so "no match" means a click did nothing at all and nothing else would have said so (#263)
- **tools**: tiles are a fixed size. A Row stretches its children to the tallest of them, so one two-line label made its whole row taller than the rows above and below and the grid lost its rhythm at exactly the tile the eye was on. The tile sets its own height and the label always occupies two lines. The scroll bound is a whole number of rows rather than a round number of dp, since a dp bound cut whichever tile straddled it and a half-drawn tile reads as a broken layout (#263)
- **macos**: the window's appearance follows the BOSS theme, set before AWT starts. The first attempt set `apple.awt.windowAppearance` as a per-window client property, which this JDK does not read, so it looked like a fix and changed nothing. What decides the lights is `apple.awt.application.appearance`, read once when AWT creates the NSApplication: the build passed `=system`, so a light BOSS theme under macOS dark mode got a dark-appearance window whose **inactive** lights are drawn pale and vanish against light chrome. It is set from the persisted theme now, directly under logging in `main()`, because it has to run before anything touches AWT (#263)
- **macos**: the traffic lights clear the top bar and both left columns. The lights are a box about 78dp wide, not a band across the top, and insetting "whichever column is leftmost" got both halves of that wrong: the top bar spans the full width at y=0, so whenever it is on it is what the lights land on and its first control sat under the green button; and the box is wider than one column, so a 40dp strip left the second half of it over the tab bar's Favorites header. The top bar is asked about before the columns, asserted, because it sits above them (#263)
- **macos**: a collapsed bar falls back to the title row, and the hover drawer clears the lights. A collapsed rail is 36dp against a 78dp box, so insetting it covers a third of the corner and leaves the rest over a browser pane, which cannot be inset at all - the columns are used only when they actually reach the box. Two rails together are 72dp and still short by six, pinned as a number because it is the one case the eye cannot judge. The drawer is its own always-on-top window, so its region starts below the clearance rather than padding inside itself (#263)
- **macos**: the rule measures the drawn strip width rather than the density floor. At 36dp a strip plus a rail computed 72dp and fell back to the full-width title row, where Comfortable draws 40dp each and 80dp fits. The width is passed in (#263)
- **updater**: the update banner clears the traffic lights, and takes the clearance instead of adding to it. The banner is the topmost chrome when there is no title row, so "Downloading..." started underneath the lights - and once it indented itself the columns below kept their own 28dp top inset, opening an empty band above the Favorites shelf for lights that were no longer there. `TrafficLightInset` gains `BANNER`, which replaces `TOP_BAR` and `LEFT_COLUMNS` and only those, since `NONE` and `CONTENT` both draw the title row above the banner. Whether a banner is up feeds the decision via `UpdateState.drawsBanner()`, exhaustive with no `else` so a new state cannot silently default, and the indent reaches all five banner states through one padding helper rather than five copies (#263)
- **tabs**: the bar's foot dropped an action at narrow widths. It was a Row, and the bar resizes to 120dp while four 32dp buttons with their gaps need 156dp - measured, the Row did not clip an icon, it handed its **last** child zero width, so Search came back as a 0x0 rect while the other three drew normally. It is a FlowRow now, so they wrap (#263)
- **tabs**: the host's actions could render in none of the four places. `verticalBarHasFoot` was fed the collapse *preference*, but a bar also rails itself when the window is too narrow - so on a narrow window with the new defaults the placement said footer, the floating cluster stood down, and the in-flow bar drew a rail with no foot: no Sign Out, Settings, Search or Tools at all. `SplitViewPanel` reports the measured rail state up now, the way it already reports the drawer, and the traffic-light rule takes it too (#263)
- **tabs**: a collapsed bar's hover drawer had no way out of full screen. It builds its own `WindowVerticalTabBar` and never passed `zoomed` / `onExitZoom`, so its map drew as an ordinary arrangement with no signal border and nothing clickable - and on a collapsed bar that drawer is the only map there is (#263)
- **tabs**: the project and workspace pickers follow a focus-cleared top bar. They live in the top bar and nowhere else, and the vertical bar's footer already took them when it was switched off - but it read the preference, so focus mode clearing the bar left them unreachable, which is the state a window is in most of the time once focus mode is on (#263)
- **tools**: the Tools icon sat below its neighbours in the floating cluster. `ToolLauncherButton` wrapped itself in 4dp of vertical padding, making it 8dp taller than Sign Out, Settings and Search in a top-aligned row. The padding belongs to whoever arranges the buttons, and both rails add it through one shared `RailToolLauncher` so they cannot space it differently from each other (#263)
- **tools**: the launcher's tooltip opened off-window in two of its three hosts. One lambda baked in a bottom hint direction and handed it to all three, including the two that sit on a bottom edge and hint upwards, and a hardcoded 32dp made it the odd button out in the floating cluster. Both come from whichever host draws it now. The rail launcher also drew smaller than the icons above it, falling back to `BossActionButton`'s intrinsic ~28dp while the rail reserved a 40dp row (#263)
- **tabs**: the cross meets the favicon instead of floating beside it. A 1dp gap made them read as a chip and a separate button that happened to be adjacent; they are one control while the pointer is on them, so the chip squares its trailing edge while the cross is out and the cross mirrors it, closing a single pill rather than leaving a corner-to-corner seam. The cross carries the chip's background rather than starting transparent (#263)

## Improvements

- **settings**: `encodeDefaults` is pinned by a test. Three chrome flags were flipped by changing their class defaults, which reaches an existing install only because default-valued fields are never written - nothing said so, and a migration KDoc 150 lines away asserted the opposite. A test fails if the flag is ever switched on (#263)
- **perf**: the scaffold no longer recomposes on every download tick. Reading `updateState` at the top to answer "is the banner visible" put a continuously-emitting progress float in the recompose scope of the parent of every bar, strip and content wrapper; it collects the bit now, via `map` + `distinctUntilChanged`, with the banner keeping its own full-state read beside it (#263)
- **panel**: `SplitViewPanel` and `TabFaviconChip` came out at detekt's length ceiling, so the drawer's call, the split tree slot, the chip's drag gesture and its optional context menu are named now. The tree is a `remember` rather than a fresh lambda, since `WindowBarRow` is not skippable and a new identity each pass would recompose the whole bar. The drag takes `windowPosition` as a lambda: it is read when the drag starts and the chip is measured after the modifier is built, so a captured value would be the position from the previous frame, which is where the ghost would appear (#263)
- **macos**: one startup line records the theme id, its `isLight` and the appearance chosen. The failure mode is invisible from inside the app, since the lights are drawn by macOS, so there was no way to tell "the theme was read too early" apart from "macOS ignored the property" - which is exactly what those two cases differ by (#263)
- **tests**: two tests were not testing. `without either it floats` was a character-for-character copy of the test above it, so the case its name described went uncovered; and the test cited as what keeps the focus quick-action count at three looped over a variable it never passed, with the one input value that makes the assertion unreachable. Three fixtures that were leaning on the old chrome defaults now state what they mean instead (#263)
- **cleanup**: a mislabelled test whose two halves were the identical call; a duplicate `hoverable` on one interaction source; a guard repeating a flag it already implied; a dead `-Dapple.awt.application.appearance` the theme now overrides; a comment claiming to be the first theme initialisation; a dangling KDoc link; the overlay's click-swallowing bound reserving a fourth button in the common three-button case; two placement helpers made internal to match their neighbours; two test tags that no test read given a consumer; and `isSelected` wired at all three launcher hosts instead of sitting unused (#263)

## Known Limitations

- **Somebody who deliberately switched a strip on cannot be told from somebody who never touched it.** The new defaults reach existing installs through the decode default, which works because the settings file is written without defaults - so a file that does not mention a bar picks the new one up, and no migration step is needed. The cost is that a value equal to the *old* default was never stored either, so both users look the same and both lose the strip. Nothing can tell them apart; it was never recorded (#263)
- **Switching themes at runtime does not move the macOS traffic lights.** `apple.awt.application.appearance` has been read by the time any window exists and there is no supported way to change an NSAppearance from Java afterwards. It takes a restart (#263)
- **While a bar is hover-revealed, the traffic lights can sit over its first icon.** `asDrawn` reads the standing focus-mode state rather than the reveal flag, on purpose: moving the launcher and the clearance for the few seconds a bar is revealed is worse churn than the overlap (#263)
- **The floating cluster is torn down and rebuilt on each hover reveal.** It is a native always-on-top window, and the alternative is a cluster in the corner while a bar with room for it is open on the left, or two copies on screen at once (#263)
- **The title row appears and disappears on narrowing or entering focus mode.** Closing that properly means a transparent clearance region over content rather than a row above it; it is documented where the decision is made (#263)
- **The bar's own auto-rail on a narrow *panel* is decided during layout while the traffic-light rule is decided from settings**, so that one case can still overlap. The measured rail state closed the window-width half of this; the panel-width half needs the decision moved to where the layout is known (#263)
- **The new chrome defaults depend on the Tools launcher and the tab bar's footer existing.** Before either did, this same default made plugins unreachable and took Sign Out off screen with the top bar. If either is removed, the default has to move back with it - the test says so, where it will be read (#263)

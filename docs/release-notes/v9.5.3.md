# BOSS v9.5.3

**Release Date:** 2026-08-28

Three changes. A transient mail-server rejection no longer dead-ends the sign-in and no longer prints a request dump under the email field, the two-finger swipe-back gesture works in the browser again - it never actually worked in either rendering mode, which is not what this repo claimed - and `Settings > Default Apps` is now reachable from the Help menu, with the older `Settings > Browser` card taught to tell the same story about the same machine.

## Highlights

- **A single mail-server hiccup ended the sign-in.** Supabase hands the magic-link email to SMTP inside the `/otp` request and does not retry that hop, so when Gmail answered a send with `451 4.3.0 Mail server temporarily rejected message` on 2026-08-24, GoTrue returned 500 `unexpected_failure` and there was nothing to do but start over - while the identical request six minutes later went through untouched. A 5xx is now retried once, within a 15s budget measured from the first attempt (#276)
- **The error under the email field was a request dump.** supabase-kt builds `RestException.message` out of the error code, the request URL and the whole request header list, and that string was being rendered verbatim to the user. It now says one sentence; the raw exception still reaches the log (#276)
- **The two-finger swipe-back gesture is back, and the story about it was wrong.** Two places in this repo said `HARDWARE_ACCELERATED` took the gesture away and `OFF_SCREEN` gave it back. Measured, it never worked in either mode: `enableOverscrollHistoryNavigation` is a touchscreen feature and a trackpad wheel is not a touch gesture. Detection moved into the page, where the renderer always sees the wheel, as a port of Chrome's own recognizer (#277)
- **Nothing pointed at `Settings > Default Apps`.** It has shipped since 9.5.2 and a user who wanted BOSS to open their links and files had to know the section existed. It is now `Help > Default Apps...`, beside the two setup wizards (#274)

## Features

- **browser**: a two-finger horizontal trackpad swipe navigates back and forward on macOS, detected inside the page (`BrowserSwipeNavScript` + `swipe-nav.js`) because under `HARDWARE_ACCELERATED` the browser is a native surface and neither Compose nor AWT sees the wheel. The page is also the only place that can answer the question separating a swipe over a carousel from a swipe that means "go back": would this scroll have gone to something on the page? A Safari-style chevron tracks the swipe in a closed shadow root and fills in past the commit threshold; the host answers with `goBack()` / `goForward()` behind a 400ms debounce, and pushes navigability into the page rather than letting it ask, which would park the renderer's JS thread on the browser thread. Host-side, so every embedded browser view gets it rather than only the browser plugin (#277)
- **settings**: `Settings > Browser > Trackpad` switches the gesture off, stored in `~/.boss/swipe-nav.json`, with `BOSS_BROWSER_SWIPE_NAV=false` (also `0` / `no` / `off`) overriding it - and the row says the environment wins. It is published as a **system property**, because the browser plugin draws the home surface, lives in another repo, and `PluginContext.settingsProvider` reads nothing, so both halves of the gesture read one key. Republished on change rather than only at startup, since it is read per gesture, and deliberately not folded into `ChromiumFlagsSettings`, which is restart-scoped by construction (#277)
- **menus**: `Help > Default Apps...` opens `Settings > Default Apps`. The section is named by `SettingsSection.DEFAULT_APPS.name` rather than a string literal, so a rename is a compile error rather than a menu item that quietly raises the window and does nothing - which is what `SettingsDeepLink.Unresolved` means for an already-open Settings window. The label names its destination the way the neighbouring "Keyboard Shortcuts" does, instead of reading like the click claims the types (#274)

## Bug Fixes

- **auth**: a 5xx from the magic-link send is retried once, waiting 2s, and only while under a 15s budget measured from the first attempt. The failure worth retrying is fast - Supabase answered the 2026-08-24 one in 6.4s - and a send that burns the full 30s request timeout has already outlasted the spinner, so a second attempt would only double it. The wait also clears Supabase's `smtp_max_frequency` (1s), so a retry cannot turn a transient failure into a rate-limit failure. A 4xx is a settled answer and is never retried: asking again would only spend more of the sender's hourly email budget. Applied to **both** implementations - the in-process client the app signs in with, and the out-of-process `boss-service-auth` client behind the microkernel (#276)
- **auth**: `CancellationException` is rethrown rather than retried or swallowed, in the send loop and in `verifyMagicLinkToken` / `verifyEmail`, so a closed screen no longer keeps work running (#276)
- **auth**: the raw supabase-kt dump reached three surfaces, not one. `signInWithEmailPassword` shipped it one function above the magic-link fix and the magic-link *verification* screen had an identical `else -> e.message` branch; all of them share one mapping now, parameterised on the 5xx wording since a failed password sign-in is not about email. An unrecognised code falls back to the server's own description, which reads fine alone ("Error sending magic link email"), rather than to the dump (#276)
- **auth**: `over_email_send_rate_limit` no longer says "wait a few minutes". It is an hourly budget and `MagicLinkWaitingScreen`'s resend cooldown tops out at 600s, so the old wording invited a retry that would fail again. `over_request_rate_limit` keeps it, being a genuinely short window (#276)
- **browser**: swipe recognition is a port of Chrome's `history_swiper.mm` rather than the single ratio that was there first, which refused any gesture whose vertical passed half its horizontal. Chrome uses three cancellation tiers and the binding one is *looser* than that, taking a swipe until vertical reaches about 0.77 of horizontal - so ordinary slightly-sloped swipes were being thrown away, which is what "hit and miss" was. The asymmetry matters as much as the numbers: vertical is measured as a **path length**, so wobble accumulates against the gesture, and horizontal as **net displacement**, so a reversal spends progress rather than adding to it (#277)
- **browser**: swiping twice in a row left two chevrons on screen. The overlay was built per gesture and removed on a timer after a 220ms exit, while a gesture ends after 120ms of quiet - so the second gesture built its own element while the first was still fading, and a run of quick swipes stacked a run of chevrons. There is one element per document now, shown and hidden rather than built and destroyed, and it dies with the document (#277)
- **browser**: the root scroller skipped the overflow test entirely. `el === scroller` alone was treated as scrollable because the root computes `overflow-x: visible` on an ordinary page - so `html { overflow-x: hidden }` with wide content reported `scrollWidth > clientWidth`, claimed it could scroll, and killed the forward swipe on such pages with no affordance to explain it (#277)
- **browser**: an environment value the app cannot parse no longer claims the key. Anything non-blank disabled the Settings row and suppressed the publish, while the resolver parsed the same value to null and quietly used the stored setting - so the row announced a decision the environment had not made, the system property was never written, and the plugin half fell back to its own default. The host could then be off while home was on, the one divergence sharing this key exists to prevent. Ownership is "parses", not "present" (#277)
- **browser**: the setting is live on the host half too. `isEnabled()` is read at injection, so switching the gesture off left the detector running on every open page until each navigated - including the tab the user changed it to test. The flag rides along with the navigability state and is pushed to open pages on change, which is what the KDoc already claimed (#277)
- **browser**: a fast flick is no longer abandoned outright. The mouse-wheel size bound now only disqualifies a gesture that is wheel-shaped from its first event, because a hard swipe carries deltas that large too - the old rule meant the harder you swiped, the less likely it was to work (#277)
- **settings**: `SwipeNavSettings` writes with `encodeDefaults`. `enabled = true` is the default, so kotlinx omitted it and choosing "on" wrote `{}` - which round-trips only until the default changes, at which point every stored file silently flips with it (#277)
- **settings**: `Files.move(REPLACE_EXISTING, ATOMIC_MOVE)` replaces `File.renameTo` in the swipe-nav settings write. This repo shipped the `renameTo` bug once already, in the favicon cache, and the destination exists from the second write onward (#277)
- **settings**: `Settings > Browser` reads the three-way `DefaultHandlerState` instead of a `Boolean?`, which cannot tell "Safari holds http" from "a BOSS component holds http" - the two states that type exists to separate, and the second is what every install created before the branded engine stopped declaring `CFBundleURLTypes`. So the card said "BOSS is not your default browser" to somebody who had set it while `Settings > Default Apps` reported the same machine as `OurEngine` and offered a Repair. It now renders all three states, offers **Repair** on the `OurEngine` path (the same claim call relabelled, because setting and repairing are the same work) and explains which of the two identical BOSS entries to pick. Help routing people to the newer screen is what made the older one the likelier thing to contradict it (#274)
- **default apps**: Windows counted no schemes, on either side. `web-links` is schemes with no extensions and `WindowsFileTypeHandler` read only the per-extension `UserChoice` keys, so that row reported `Other` on every Windows machine - including one where BOSS did hold http and https - and `register` returned early on "no extensions" without writing the `StartMenuInternet` entry that puts BOSS in the browser list its own settings page sends the user to. Both sides consult `schemesFor` now, through `WindowsDefaultBrowserHandler.schemeState` and `registerAsBrowserCandidate` rather than a second copy of those registry reads and writes (#274)
- **docs**: two files claimed `OFF_SCREEN` restored the two-finger swipe-back on macOS - this file's KDoc and the Settings copy for the off-screen rendering mode, which promised the user "regains the two-finger swipe-back gesture". A build launched with `BOSS_RENDERING_MODE=OFF_SCREEN`, overscroll history navigation on as it always is, and the in-page detector switched off does not navigate on a two-finger swipe. The gesture never worked in either mode and the rendering mode was never what cost it (#277)

## Improvements

- **settings**: the mount, Refresh and the post-set read in `DefaultBrowserSection` share one `refresh()`. It was three copies of the same fold, which is how the "assume `Ours` on success" line got out of step with what the OS actually holds; it re-reads instead (#274)
- **auth**: the KDoc now states why this diverges from `SessionRecoveryPolicy`, which retries a bare transport failure where this does not. A refresh is idempotent, so re-asking after a dropped connection costs nothing, whereas a send that died mid-flight may already have reached SMTP. The practical limit is that a connection reset is not a `RestException` and so is not retried here (#276)
- **auth**: every attempt asks for another email, so the retry ceiling has to stay under the project's `rate_limit_email_sent` - which lives in the Supabase dashboard rather than in this repo. That coupling is written down next to the constant, with what a sweep of the full 29-day log retention window actually measured: exactly one transient failure and no rate-limit rejections at all (#276)
- **docs**: `SUBSYSTEMS.md`'s Default Apps block listed key files and no entry points, which is the same discoverability gap one level up. It names all three, including why the menu path matters - `DefaultAppsOffer` persists `promptShown` the moment the dialog appears, so a force quit counts as asked, and its own KDoc rests on "Settings > Default Apps is always there" being reachable (#274)
- **tests**: the retry loop had none, and the previous mutation run said so - a never-retry mutant passed everything except the message mapping. The send and the clock are parameters now, so `runTest` drives the whole loop in virtual time and `TestTimeSource` reaches the budget. `boss-service-auth` had no `src/test` at all, so the copy that ships to the microkernel was the copy nothing checked; it has one now, and because composeApp cannot depend on that module both suites assert the same literal strings and say so in a header comment. One test pins the property the logging decision rests on: the minted request carries a real bearer token and the raw exception we keep logging must not contain it (#276)
- **tests**: `scripts/test/test-swipe-nav.js` drives the real `swipe-nav.js` against a fake DOM and a fake clock in `build.yml`, and every threshold is checked by a mutation that must flip a named assertion - reverting the chevron fix fails the new stacking check, which reports 2. The tests that asserted the overlay was *absent* after a gesture now assert it is not *showing*, which is both what the change makes true and the thing a user can tell apart (#277)
- **tests**: `SettingsSectionLiteralsTest` scans commonMain and desktopMain for literals passed to `triggerOpenSettings` or `settingsWindow.open` and asserts each resolves to a `SettingsSection`. Scanning the source is the right instrument rather than a proxy: the literal in the source *is* the thing that drifts, and a test naming today's three strings would be a fourth copy that keeps passing after someone edits the real one. Reverse-verified, and it self-checks the scanner on a fixture because "found nothing" would otherwise pass while proving nothing. Nothing was actually stale (#274)
- **tests**: `BrowserHandlerStateTest` pins the two identity mappings extracted from the process calls (Windows ProgId, Linux desktop entry): case-insensitive, `BOSS.md` is not the browser, and the reduce still means "both schemes or it is not ours". Mutation-verified - making either mapping case-sensitive fails a named test. The Windows scheme work cannot be tested where `reg` does not exist, so what is pinned is the data fact underneath it, in `FileTypeCategoriesTest` (#274)

## Dependencies

- **tests**: `io.ktor:ktor-client-mock` is added as a test-only dependency to composeApp and `boss-service-auth`. supabase-kt's auth exceptions carry the `HttpResponse` that produced them, so asserting on what a failed sign-in tells the user means minting a real response, and `MockEngine` is the supported way to get one without a socket. `kotlinx-coroutines-test` joins composeApp's desktop test set for the same reason - `runTest` skips the retry backoff in virtual time, so the send loop runs end to end without the test waiting 2 seconds (#276)

## Known Limitations

- **A connection reset is not retried.** The retry keys on a `RestException`, so a send that dies mid-transport - as opposed to one the server answers with a 5xx - still reaches the user as a failure (#276)
- **The swipe gesture is macOS only.** Detection is in-page and so is portable, but nothing enables it elsewhere; on Windows and Linux the trackpad row does not apply (#277)
- **The error mapping is duplicated.** composeApp cannot depend on `boss-service-auth`, since `modules/` is excluded on Windows-ARM64, so the in-process and out-of-process clients hold two copies of the same strings. Both suites assert the same literals, which is what keeps them together (#276)
- **No test asserts the Help menu item itself.** A Compose `MenuBar` item cannot be exercised without a real window, and a regex over the file would prove the literal is present rather than that the menu shows it. Both of its destinations are covered (#274)
- **The Help item is not gated on `DefaultAppsManager.isSupported()`.** Where Launch Services or the type resource is unavailable the section says so in a sentence; a greyed-out or absent menu item would replace that explanation with nothing (#274)

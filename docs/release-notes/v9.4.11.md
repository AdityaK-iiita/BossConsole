# BOSS v9.4.11

**Release Date:** 2026-08-15

A plugin-platform release. The AI Gateway can be updated and removed again - an optional dependency was vetoing its provider's unload - and a plugin can now open another plugin's panel as a main-area tab, carrying that panel's state with it.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **The AI Gateway could not be updated or removed from the Toolbox.** Update cleared the spinner and changed nothing, with no error anywhere. `checkCanUnload` counted any plugin that named the target in its manifest dependencies, including declarations marked `optional: true` - jupyter-notebook, flow-tab and llmrpa all declare the gateway optional, so between them they vetoed its unload permanently, and because the Toolbox updates a plugin by uninstalling and reinstalling it, the veto landed on the Update button (#178)
- **A plugin can open another plugin's panel as a main-area tab**, through `SplitViewOperations.openPanelAsTab`. The host has done this for itself for a while - the panel header's "Open as Tab", and dragging that header onto the centre - but every piece of it was internal, so a plugin could only reveal a panel in the sidebar, and the Toolbox reached the panel-host constructor reflectively and had to accept losing the panel's state (#179)
- **The two readers of `dependencies` now agree on what `optional` means.** The same declaration that the install prompt words as "works without it, but some of its features need it" was a hard veto at unload time. `blockingDependentsOf` sits next to `missingFor` so the two cannot drift again, and it drops a manifest that names itself, which would otherwise make that plugin permanently unremovable (#178)
- **A refused unload is now visible in the log.** `uninstallPlugin` logs `Uninstalling plugin` before it decides, and the delegate reduces `Result<Unit>` to a `Boolean`, so the reasons naming the plugins in the way were dropped at that boundary and the log simply stopped mid-sequence (#178)

## Features

- **plugins**: `SplitViewOperations.openPanelAsTab` (api 1.0.77) routes to the existing `requestPromoteToTab` rather than reimplementing the promote, which is what makes it a move rather than a copy: the cached component carries the panel's state into the tab, the hosted-as-tab bookkeeping makes the sidebar icon focus that tab instead of opening a second copy, and the sidebar collapse goes through `closePanelForItem`, which only hides. That last point is the one a plugin could not have - the close it can reach drops the cached component (#179)
- **plugins**: the request travels over `PanelEventBus`, the same window-filtered path `PanelEventProvider`'s open and close take, because `SplitViewOperationsImpl` holds only a `SplitViewState` and a window id while the promote trigger lives on that window's `BossDraggableComponent`. No replay on that flow, deliberately: `panelOpenEvents` replays to cover a startup race for a panel that should end up open, but a replayed promote would give every window opened afterwards its own tab over the one cached component (#179)

## Bug Fixes

- **plugins**: an optional dependency no longer blocks its provider's unload. `blockingDependentsOf` counts only non-optional declarations, so a plugin three consumers list as optional is removable and updatable again; a required dependent still blocks and is still named (#178)
- **plugins**: a *disabled* dependent no longer vetoes either. `disablePlugin` unregisters the tracking context and flips the state to `DISABLED` but never calls `pluginLoader.unloadPlugin`, so a disabled plugin is still in `getLoadedPlugins()` and went on refusing on behalf of something that is not running. The predicate takes an `isDisabled` argument with **no default**, so a new call site has to answer, and it fails closed - `PluginState` has more members than LOADED and DISABLED, and treating "not exactly LOADED" as "not running" would drop real dependents (#178)
- **plugins**: `openPanelAsTab` resolves the incoming `PanelId` against the registry instead of matching by data-class equality. `PanelId` carries a `defaultOrder` that a plugin addressing another plugin's panel has no way to look up - the api's own `AiAvailability` guesses `PanelId(TOOLBOX_PANEL_ID, 0)` against a panel registered as order 6 - so the request reached `getOrCreateComponent`, found nothing and returned silently, while `openPanel` with the identical id worked because that handler has always matched on `panelId + pluginId`. One shared function now, since two paths disagreeing about what names a panel gets discovered as "Open does nothing for this one tool" (#179)
- **tabs**: the single-instance rule moves into `requestOpenAsTab`, applied by every caller not already gated on the panel being visible in the sidebar. Nothing downstream enforces it: `BossTabsComponent.addTab` does not dedupe on `TabInfo.id`, so a second promote left two tabs rendering one cached component and `ProcessPendingFocusHostedTab` stopped its scan at the first. The header drag-out had this inline and now shares it (#179)
- **tabs**: the panel-host factory reads the panel id with a checked cast. `openTab` picks a factory by `typeId` alone, so any plugin can hand this one a `TabInfo` of its own, and a blind cast turned that into a `ClassCastException` thrown from inside the host on a plugin's call - it is now a dead tab and a warning (#179)
- **plugins**: refusal and failure log separately. `uninstallPlugin` returns `Result.failure` on four paths and only two are refusals, so "Plugin not found" and a `pluginLoader.unloadPlugin` error were being reported as `Plugin unload refused`, sending a reader to the dependency declarations after a classloader fault. The reasons come off `PluginUnloadException.reasons` rather than the joined message, and the genuine failure branch keeps its stack trace (#178)

## Improvements

- **plugins**: a `PanelId` that resolves to nothing is logged rather than dropped in silence, and `panelIdFor` is top-level so the rule is testable without a `ComponentContext` or a `PanelComponentStore` (#179)
- **docs**: AGENTS.md records what the veto still cannot do - it cannot tell Update from Remove. The host's own update paths pass `force = true`, so the only path that meets the veto is the plugin-facing delegate, which has no way to know which button was pressed; a plugin with a *required* loaded dependent therefore still cannot be updated from the Toolbox, and closing that needs an update-shaped verb on the api rather than a change to this predicate (#178)
- **tests**: both changes were run against the pre-fix code first rather than assumed to cover it. Three of the six dependency cases fail against the previous behaviour and the other three pin what must not change; on the panel side, dropping the single-instance guard fails 2 of 5, adding replay fails the late-collector case, restoring the unchecked `as` fails 2 of 3, and reverting the registry lookup to `it.id == requested` fails 2 of the 5 resolution cases - the guessed order and the owner-matched lookup (#178, #179)

## Dependencies

- **boss-plugin-api**: 1.0.76 → 1.0.77, the release cut by boss-plugin-api#33, which adds `SplitViewOperations.openPanelAsTab` and `supportsOpenPanelAsTab`. That interface is `@HostImplemented` - `plugin-api-core` filters it into the host and serves it parent-first, so this pin is what every plugin resolves, and nothing a plugin declares can reach these members before the bump lands in a release. Verified against the release jar as a superset of 1.0.76 rather than trusted to the ordering, since `fetchApiPluginJar` has no Maven fallback (#179)

# BOSS v9.4.29

**Release Date:** 2026-08-22

Eight changes across five releases' worth of tags. A plugin that crashed with no UI mounted could end the whole session, a plugin refused for requiring a newer BOSS now offers a way out instead of silently vanishing, every Windows MSI since 2026-07-21 shipped unsigned and now does not, and the browser engine moves to JxBrowser 9.4.1.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`. The engine bump was verified against all three measures that decide the floor (`LSMinimumSystemVersion`, the framework's `LC_BUILD_VERSION` minos, and `libtoolkit.dylib`'s), and none moved.

## Highlights

- **A plugin could end the app precisely because it had no UI on screen.** One function was answering two different questions, and they come apart exactly when it matters: `attributeToPlugin` asks "which registered boundary should handle this" and is correctly filtered to plugins that can render a fallback, but the crash route used it to ask "is anyone to blame", which is broader. terminal-tab's `setPendingSidebarCommand` recursed into itself and threw `StackOverflowError` from a click; all ~1024 retained frames were terminal-tab's own, so the culprit was never in doubt - but with no boundary mounted, attribution returned null, the route fell through to the uncontainable check, and BOSS exited (#228)
- **A version-floor refusal is now recoverable rather than silent.** A plugin refused for `minBossVersion` or `minApiVersion` produced one ERROR line in the log and nothing else, which for a `systemPlugin` means a feature simply stops existing - fluck-browser *is* the browser tab, and 1.2.22 requiring BOSS 9.4.23 on a 9.4.22 host cost people their browser with no way back short of finding the previous jar on GitHub by hand. There is now a dialog that names versions and offers only remedies that actually clear the floor, including going back to the jar the update replaced (#225)
- **Every Windows MSI since 2026-07-21 was unsigned, under a green build.** `smctl sign` prints `signCommand command for file <path> FAILED` and exits 0, so nothing looked at the artifact. The missing precondition is `smctl windows certsync`, which puts the certificate in the Windows store that signtool resolves from; all three Windows signing jobs now run it before attempting a signature, and the verify gate added in #224 is what caught this in the first place (#224, #230)
- **Windows opens on the light theme.** Blueprint Light on first launch, macOS and Linux unchanged on Blueprint. The subtle half is the settings file: it is written only by `select()`, so its existence *is* the record that somebody chose a theme, and the old writer omitted `appThemeId` whenever it matched the class default (#226)

## Features

- **plugins**: `PluginVersionGate` models a floor refusal and `remediesFor` decides what to offer. An api floor offers an API update, not an application update, because the api layer is itself a hot-swappable plugin. A host update is offered **only** when it clears the floor, since an update that lands below it costs a download and a restart to arrive back at the same refusal. Reverting is always offered when possible and always last: it needs nothing published and no restart, so it is what works when everything else is unavailable. The list is never empty - when nothing can be done, the reason names both versions, because an empty dialog is worse than the log line it replaces (#225)
- **plugins**: `PluginRollbackStore` keeps the jar an install replaced, which is what makes reverting possible at all - every install path promotes over the target with `atomicMoveFrom` and deletes what it rejects, so the working version did not exist anywhere by the time anyone discovered the new one would not load. One generation deep on purpose; a history is a directory of 5 MB jars nobody prunes. Keyed by plugin id in a dot-prefixed subdirectory the plugin scan cannot mistake for an install, and restore **copies** rather than moves, so a restore interrupted before the load has not consumed the only good jar (#225)
- **plugins**: `initializeApiLayer` publishes `boss.app.version` alongside `boss.api.version` and `boss.ipc.version`. The Toolbox offered store versions this host cannot load not because it ignores `minBossVersion` - it writes that field when publishing - but because nothing ever told a plugin what version the host is, so the comparison was impossible and every published version looked installable. A system property rather than an api member deliberately: it needs no api release, so every already-installed plugin can read it the moment this host ships, and it is set before any plugin loads (#225)
- **plugin-store**: the download route returns `minBossVersion`. It returned `minIpcVersion` and not this, which left the Toolbox with the floor on browse rows and nothing at all on the path that installs. Sent as `?? ''`, because the column is nullable and a null in a field a client models as a string fails the whole decode rather than one field (#225)
- **theme**: `BossThemes.defaultIdFor(isWindows)` is the only branch, in the platform-explicit form `StartupPanelPolicy` and `FocusModeSettings` already use, so both branches run on every CI leg rather than only on `windows-latest`. Blueprint Light rather than Daylight, because it is the light half of the identity that is already the default and `BossThemesRegistryTest` records Daylight in `SIGNAL_CONTRAST_DEBT` - its amber signal sits at 2.63:1 on its own near-white floor, under the 3:1 floor for UI components (#226)

## Bug Fixes

- **crash**: `blameFor` answers the broad question - the same strategies in the same order, minus the registration filter, over every *loaded* plugin rather than every mounted one. `attributeToPlugin` keeps its narrow meaning and its old answers, and the two now share the strategy helpers instead of holding two copies of the classloader scan (#228)
- **crash**: `hasFatalCause` splits what `isUncontainable` had conflated. OOM and `StackOverflowError` are both uncontainable by repaint, for different reasons: after an OOM every recovery path allocates on a dead heap, so escalating is all that is left, while after a stack overflow the stack has unwound and the process is healthy. The one thing you must not do is re-enter whatever recursed, which is exactly what quarantining the plugin does - escalating was spending a session to avoid a redraw that was never going to be attempted. The new `QuarantinePlugin` route sits below the fatal check and above the uncontainable one, which is the whole point of it (#228)
- **plugins**: `LoadedPluginInfo.sourceUrl` carries where a plugin was actually fetched from. The host has recorded that per install on the `installed.json` row and never handed it to plugins, so a plugin needing to know where to fetch an update from had one candidate and it was the wrong one: a store plugin still declares its development repo as its homepage, and for our plugins that repo is usually private. The Toolbox duly read `url` as a download source and aimed an unauthenticated GitHub API call at it, which answers 404 for a private repo. Blank keeps meaning "ask the store", which is also what a first install sees, since the row is written after `loadPlugin` returns. Fluck Agent is the case that surfaced this (#231)
- **theme**: absence of `appThemeId` in an *existing* settings file still resolves to `DEFAULT_ID`, and only the absence of the file resolves to the platform default. A Windows user who deliberately picked Blueprint has a file that says nothing at all, and resolving that absence from the platform default would flip them to light on their next launch with no way to make the choice stick. Writes now use `encodeDefaults = true`, which ends the ambiguity for every file written from here on; a file that will not parse falls back to the platform default, since whatever it recorded is unreadable (#226)
- **windows**: `smctl windows certsync --keypair-alias=<alias>` runs in all three Windows signing jobs, after the credentials are saved and before the sign attempt. The alias goes in through `env` rather than the command line so `cmd` cannot mis-parse a value containing `&`, `^` or `|`. Sampling release runs back to 2026-07-21 shows the same FAILED line in every one of them, so this never worked rather than regressed (#230)
- **windows**: the ARM64 MSI is signed. `build-windows-arm64` packaged and uploaded with no signing steps at all, so every Windows-on-ARM user got an unsigned installer. DigiCert's client tools are x64 binaries and signtool comes from the x86 Windows Kits directory, so both run under emulation on `windows-11-arm` and that path is unproven - every signing step there is `continue-on-error` and the MSI lookup no longer exits 1, so if the tooling cannot run the release still carries its ARM64 asset (#224)

## Improvements

- **ci**: a "Verify MSI Signature" step in all three Windows jobs asserts the signature is **Valid**, not merely not `NotSigned`. `HashMismatch`, `NotTrusted` and `UnknownError` all used to fall through and pass green, which reads identically to success on the ARM path nobody has run yet. x64 and Lite fail on `NotSigned`/`HashMismatch` when credentials were present and warn on any other non-Valid status: a runner trust-store or parser quirk should be loud, not release blocking. The ARM64 verdict also goes into the run summary, written as UTF-8 without BOM because Windows PowerShell's `>>` writes UTF-16 (#224)
- **ci**: `allow_unsigned_windows` downgrades the verify gate from a hard failure to a warning, on Release Build (`workflow_dispatch` and `workflow_call`) and on BOSS Lite Release. It does not skip signing - certsync and the sign attempt still run, so the run still carries the diagnostics. It fails closed: a push-triggered release has no `inputs` context, so the expression evaluates to false and the gate stays a gate. The release body admits it, driven by what the verify steps *measured* rather than by the input, so an unconfigured-secrets build is labelled too (#230)
- **ci**: `smctl healthcheck`, `windows ksp list` and `keypair ls` run alongside the sign attempt, because smctl gives no reason for a signing failure. If certsync is not the whole story, the next run says whether the credential, the KSP registration or the keypair alias is wrong instead of costing another release to find out (#230)
- **ci**: the jxbrowser watcher opens the version-pin PR itself. It already polled TeamDev four-hourly and dispatched the branding build, but nothing moved the `jxbrowser` pin, so the shipped app kept the old engine until a human noticed - 9.4.1 published on 2026-08-14 and was pinned by hand a week later. A PR rather than a push to main, because the pin is the one thing CI cannot check for itself: a mismatched pin is an `UnsatisfiedLinkError` on libtoolkit at the first native load, not a build failure, so a green build says nothing about it (#229)
- **ci**: five silent failure modes in the pin bump are each covered by a test run against the mutation it describes - the rewrite is anchored to `^jxbrowser = "` because `jxbrowser-gradle-plugin` is the very next line, the edit is verified to have landed on exactly one line rather than trusted, the version compare is numeric field by field so 9.4.10 does not read as older than 9.4.9, the pin only ever moves forward, and an open PR is neither duplicated across runs nor reopened after a human closed it (#229)
- **docs**: `CODE_SIGNING_SETUP.md` records the certsync requirement, that the sign step's exit code means nothing, and which diagnostic answers which question. Its Windows half also documented four `DIGICERT_*` secrets that do not exist and are read nowhere; the real names are the five `CODE_SIGNING_*` ones, and there is now a table of what is and is not signed - the bundled Chromium binaries and the inner `BOSS.exe` are not (#224, #230)
- **docs**: `DESIGN_SYSTEM.md` records the two consequences of the Windows theme default rather than leaving them to be discovered - terminal-tab's `ApplyHostThemeToTerminal()` pushes host tokens into BossTerm on every compose, so a Windows first run is light throughout rather than a light host around a dark grid, and BossConsoleRust reads the same file with no equivalent of `defaultIdFor` yet (#226)

## Dependencies

- **jxbrowser**: 9.4.0 → 9.4.1. Chromium goes 151.0.7922.72 → 151.0.7922.138, a patch bump inside the same 151 branch, so nothing about the lockstep story changes shape. Verified before bumping: the 9.4.1 jar's `version.info` asks for 151.0.7922.138 and the 9.4.1 engine bundle ships exactly that framework version directory, all six platform archives exist on both sources with matching sha256, and the macOS floor holds at 13.0. Anyone carrying an explicit 9.4.0 engine pin is already handled - `BrowserEngineSettingsManager` clears any pin that is not the bundled version on load (#227)
- **boss-plugin-api**: 1.0.83 → 1.0.84, for `LoadedPluginInfo.sourceUrl`. A superset, additive with a `""` default (#231)

## Known Limitations

- **`getPluginAPI` handles are not wrapped in an attribution proxy.** That would tag cross-plugin calls exactly, but these interfaces carry `@Composable` members and routing those through `java.lang.reflect.Proxy` risks the terminal UI for a benefit the blame path already delivers. `isUncontainable` is also unchanged, so the render boundary's own carve-out still reads the same (#228)
- **The rollback store is one generation deep.** The jar an install replaced is kept; the one before that is not. A snapshot that cannot read its source leaves any earlier copy alone rather than discarding it, so restoring can land on something older than ideal but working, which beats no way back at all (#225)
- **The Windows signing chain exists in three copies and the drift is real.** A `.github/actions/sign-windows-msi` composite is the obvious next step, deliberately not folded into a release-blocking fix where it would muddy which change made signing work (#230)
- **An unsigned-installer notice lands in the GitHub release body only**, not in `docs/release-notes` or the Supabase copy the in-app update dialog reads. The signature of an installer matters to someone downloading it and not to someone already running the app (#230)
- **`ensureInitialized()` does not persist the theme it resolved.** Pinning a platform default on first launch would mean the next change to what a platform opens with reaches nobody who had ever run the app (#226)
- **The version-gate dialog does not clear itself after "Update BOSS".** The plugin stays unloadable until the new app runs, so the gate is left standing on purpose. "Update the plugin API" goes through `installPlugin`, whose api-id branch is a hot swap ending in a reload-all, which is what gives the refused plugin its second chance with no restart (#225)

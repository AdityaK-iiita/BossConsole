# BOSS v9.4.17

**Release Date:** 2026-08-18

A browser release, and both fixes are for things that worked only sometimes. Copy and paste in a browser tab now drive Chromium's own editor instead of injected JavaScript, a re-shown tab gets keyboard focus back, and Cmd+F has one code path, a bar anchored to its own pane, and the good manners to let Sheets, Docs and Notion serve their own find.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **Copy, cut, paste and select-all are real Chromium editor commands now, not `document.execCommand` in injected JS.** The old path was wrong three ways at once: `execCommand('copy')` needs transient user activation, so a right-click grants it for roughly five seconds and picking the menu item *after* reading the menu silently did nothing, with no visible difference from a success; it only ever reached `mainFrame()`, so a caret inside an iframe copied nothing; and the boolean `execCommand` returns was discarded, making a refusal indistinguishable from a copy. Paste was worse - it read the AWT clipboard and spliced text into `document.activeElement`, dropping `\r` and skipping the `beforeinput`/`paste` events framework-managed inputs listen for (#204)
- **A tab you switch back to holds keyboard focus again, so Cmd+V goes somewhere.** Nothing ever called `Browser.focus()`, and `HARDWARE_ACCELERATED` is now the default on every platform, which makes the Compose view a `SharedSurfaceWidget` over a native child view with no Java-side focus wiring - unlike the `OFF_SCREEN` widget, it depends on the native view being first responder. Switching tabs hid one view and showed another with nothing promoting the one that reappeared, so the returned-to tab went dead to the keyboard until the page was clicked. Whether it did depended on what the window fell back to, which is exactly what made it read as "sometimes". Only a tab shown *again* is focused - a new tab must leave the caret in the URL bar (#204)
- **Cmd+F had two implementations and one of them was a dead wire.** `FluckEngine`'s `PressKeyCallback` opened a Swing find bar; separately, every keymap preset bound Cmd+F to `browser.find`, dispatched into `MenuActionsHandler.browserFindEvents` - a `SharedFlow` with no collector - and because `dispatchAction` returned true the key was consumed and nothing happened. Which path ran came down to who held AWT focus. That flow is now collected in `BrowserHandleImpl.Content()`, the composition that knows it is the visible surface of the active panel, so one decision point serves both routes (#206)
- **A page that has its own find-in-page keeps it.** Chrome treats Ctrl/Cmd+F as a non-reserved accelerator - the page sees it first and `preventDefault()` wins, which is the whole mechanism behind Sheets' find. Suppressing the key meant the page never saw it. `BrowserFindKeyProbe` now injects one capture-phase listener per frame that defers with `setTimeout(..., 0)` before reading `defaultPrevented`; the deferral is what survives `stopPropagation()`, which Sheets and Docs both call and a bubble-phase listener never sees. No verdict inside 150ms opens BOSS's own bar, which covers the PDF viewer, error pages and any frame injection could not reach (#206)

## Bug Fixes

- **browser**: clipboard operations route through `Frame.execute(EditorCommand)` - no activation requirement, the real system clipboard, and the focused frame rather than the main one. The host already did this correctly for popup windows in `PopupWindowContextMenu`, so this converges the two. Refs #92 (#204)
- **browser**: the queued focus is cancelled when the composition leaves. `isValid` answers "not disposed, engine generation still matches", not "still on screen", so on a fast A→B→A the runnable focused B - whose native view is alive precisely because HARDWARE mode retains the surface. A click on the URL bar or another pane in the same interval lost the same race (#204)
- **browser**: focus is only taken when the host window is focused. Re-entering composition is not by itself a tab switch, so without this a workspace restore, a pane split or a tab move ended in `focus()` - including in a window nobody was looking at, and with two browser tabs side by side both handles called it on one rebuild with the last runnable winning (#204)
- **browser**: a red `0/0` no longer flashes on every keystroke. `FindResult.isSearching()` was ignored, so Chromium's in-progress updates were rendered before the real count landed (#206)
- **browser**: the match counter shows the current query's count. `TextFinderImpl.find` allocates a request id per call and keeps a consumer for each, and the debounce cannot cancel a search in flight, so the label showed whichever session finished last. Epoch-guarded now (#206)
- **browser**: Escape keeps the match you went looking for - it called `stopFindingAndClearSelection`, throwing the selection away, while `stopFindingAndKeepSelection` existed and was unused (#206)
- **browser**: each pane of a split gets its own find bar. It was placed against the whole window, so both panes stacked their bars in one corner and a right sidebar could sit on top of one (#206)
- **browser**: a live theme switch reaches an open find bar, where colours had been snapshotted at construction (#206)
- **browser**: the keymap path has a fallback. `onFindKeyFromShortcut` dispatched a synthetic key and returned, and only `onFindKeyFromPage` armed the verdict deadline, so everything after the dispatch depended on JxBrowser re-entering `PressKeyCallback` for a programmatically dispatched key - if it does not, Cmd+F on the AWT-focus path did what it did before #206: nothing. The deadline is armed *before* the dispatch, so re-entry, a page claiming the chord and total silence all end in something happening (#206)
- **browser**: which browser claims the chord is deterministic. `LocalIsPanelActive` defaults to true, so a browser outside a main-window panel read as active alongside the real one and the winner was whichever coroutine resumed first. A host-internal `LocalInMainWindowPanel` makes the preference explicit, and a non-preferred surface yields 40ms and claims only if nothing better did - so a sidebar-only browser is still served (#206)
- **panel**: the focus-mode quick actions no longer vanish while the find bar is up. An unowned window taking focus deactivates the main window, and `FocusModeQuickActions` renders its LIGHTWEIGHT path when unfocused, which under `HARDWARE_ACCELERATED` draws *behind* the Chromium surface - so the cluster disappeared in the one configuration it exists for (#206)
- **browser**: find-again works off macOS. It gated on `isMetaPressed` alone, so Ctrl+G matched nothing on Windows and Linux, and nothing else could serve it because the bar owns keyboard focus while it is up. One platform-aware rule now, shared with the key callback, plus F3 (#206)
- **overlays**: the 8dp margin survives `OFF_SCREEN`, where the lightweight branch ignores `regionInWindow` for the same reason it ignores `inset`. Folded per path via `overlayCornerIsHeavyweight` (#206)
- **browser**: the find controller's `dispose` is final. Every accessor used `computeIfAbsent` or `put`, so a late key or verdict re-created state - and a live `Timer` - for a dead browser (#206)

## Improvements

- **browser**: the Swing `JDialog` find bar is replaced by a Compose bar routed through the existing `OverlayCorner` seam and anchored to the pane rect `Content()` already tracks for the pinch gate. Cmd+G / Shift+Cmd+G advance and are claimed only while the bar is up with a query. It mounts in `BrowserHandleImpl.Content()`, the single chokepoint for every browser surface, so every `BrowserHandle` host gets it (#206)
- **overlays**: a focusable overlay is an owned `ComposeDialog` with `Window.Type.UTILITY` rather than a top-level window, which is also what removes the taskbar button and Alt-Tab card it had gained on Windows. AWT shortcut routing keeps working, since `findWindowId` walks `owner`; non-focusable callers keep the window they had. `HeavyweightCorner` gains `focusable` and `regionInWindow`, the latter because `inset` can only pull in from the end and bottom edges and a top-anchored pane in a split needs to say where it starts (#206)
- **browser**: the clipboard failure log derives its label from `command.name()` instead of a hand-passed string that let `editorCommand(EditorCommand.paste(), "Copy")` compile and mislabel every line, gains `handleId`, and uses `catch (Exception)` so an `Error` propagates - the stance `PopupWindowContextMenu` takes in the same package (#204)
- **browser**: the frame choice is reconciled with `PopupWindowContextMenu`, which documents the opposite conclusion. Both are right for what they hold: that callback has the frame Chromium resolved for the actual click and this method does not, so the KDoc states the cost rather than implying `focusedFrame()` is unambiguously better (#204)
- **tests**: `BrowserFindTest` (28 cases), `BrowserClipboardCommandsTest` and `OverlayCornerForwardingTest`, which pins that `OverlayCorner` forwards `focusable` and `regionInWindow` - both have defaults, so dropping either compiles and leaves everything else green. The probe script runs against a fake DOM in `scripts/test/test-find-key-probe.js` as a CI step beside the collector harness, because the Sheets case cannot be distinguished by reading the script and the two mutations that produce the wrong implementation both fail there (#206)
- **browser**: `shouldFocusOnShow(mode, alreadyShown, hostWindowFocused)` is extracted so the focus decision is testable at all - it lived inside the composable, where the load-bearing clause was unreachable from a test (#204)

## Known Limitations

- **Preferring the frame the context-menu callback already resolved is a follow-up, not done here.** A non-editable selection with an iframe focused acts on the iframe's empty selection where `mainFrame()` would have worked. It is not reachable through the browser plugin's own menu - its non-editable branch copies through AWT and never calls this, and the editable branch is gated on main-frame-only `isEditable` - but it is reachable by any other plugin holding a `BrowserHandle` (#204)
- **There is deliberately no `unfocus()` on the way out of a browser tab**, because a tab moving between windows builds one composition and tears down the other in an order the effect does not control (#204)
- **The page-claims-the-chord verdict is a 150ms timeout, not a guarantee.** A frame that answers slower than that gets BOSS's bar over its own find, and as the probe's KDoc now states, a non-focused frame can answer for the focused one (#206)

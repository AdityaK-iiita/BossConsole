# BOSS v9.4.30

**Release Date:** 2026-08-22

Six changes, all about cost. The status bar's memory readout now measures what BOSS actually holds across every process it owns instead of an eighth of it against a ceiling set by the user's RAM, the heap is bounded at 2 GB, the browser engine pre-warm finally runs on the launch that pays most for skipping it, and the release and PR critical paths each lose minutes of cold Gradle.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`. No dependency moved in this release.

## Highlights

- **The always-visible memory reading was structurally unable to warn about anything.** It was JVM heap used over heap max, and both halves were wrong for the purpose. The numerator counted about an eighth of what BOSS holds - measured on a loaded session, 299 MB of live heap inside a 2,537 MB host process with a further 907 MB in the Chromium tree - and every memory incident this app has had (orphaned plugin host JVMs, recycled engines whose Chromium was never killed, PartitionAlloc aborting on native allocation failure) lives in the part that was not counted. The denominator was not a BOSS number at all: with no `-Xmx` the ceiling is 25% of installed RAM, so it read 29.97 GB on a 128 GB machine, and the 75% warning band would have needed 22 GB of live objects to trip. The bar now reads `2.4GB · 67/128GB 4%` - what BOSS holds, the machine's used and total, then process CPU - coloured by machine memory pressure on the same critical threshold `MemoryPressureWatchdog` uses, so the bar turns red exactly when the watchdog starts its sustain clock rather than the modal being the first sign (#237)
- **The heap is bounded at 2 GB, with `-Xms256m` alongside it.** Not a footprint fix - G1 commits lazily, and that loaded session sat at 432 MB committed - but a blast-radius one: an unbounded ceiling lets a leak reach tens of gigabytes of real memory before the JVM will consider an `OutOfMemoryError`, and well before that Chromium's PartitionAlloc, sharing this process's malloc, aborts with no catchable exception and no heap dump. Eleven independent readings of this app's live heap peak at 478 MB, so 2 GB is over 4x the observed maximum and is the ceiling every machine at or below the Ultra Lite threshold already runs with. The `-Xms` is not optional beside it: the default initial heap is 1/64 of physical RAM, which on a 128 GB machine is exactly 2 GB, and an `-Xms` equal to `-Xmx` tells G1 the heap is fixed, so the cap alone would have committed the whole 2 GB for good and added ~1.6 GB of resident memory to every large machine (#237)
- **The browser engine pre-warm was skipped on precisely the launch that pays most for skipping it.** The gate asked whether the browser profile directory exists, but that directory is created *by* the first engine boot, so it really answered "has this machine ever used the browser" - and on a first install the answer is no for reasons that have nothing to do with what the user is about to do. The clearest case was the two post-download call sites, both already carrying a comment saying they warmed the engine now that it was installed, and both silently doing nothing: somebody who just sat through a several-hundred-megabyte download of the browser engine is the strongest possible signal that a browser tab is coming. `prewarmInBackground` now takes `force` for callers that already know one is - those two downloads, and `applyWorkspace` when the layout it is about to apply contains a browser tab (#236)
- **Every pull request queued behind a cold Gradle that existed to print a file.** `version-check` is the fan-out root of `build.yml` and its whole body was `./gradlew showVersion` with no Gradle cache: 153s, 157s and 211s across three consecutive runs, out of jobs totalling 160s, 163s and 221s, before any other job could start. It bought nothing - the job's two outputs are grepped straight out of `version.properties` and nothing downstream reads the task's output. The release path lost about three minutes to the same pattern (#234, #232)

## Features

- **status-bar**: the machine's used and total memory sit beside BOSS's footprint, because a single absolute figure left the reader without the context to judge it - 2.4GB is unremarkable on one machine and most of another, and nothing on screen said which. Used is derived as total minus available rather than sampled, so the pair always adds up to the total printed next to it, and both halves are scaled by the total rather than each separately: formatted independently a lightly loaded machine reads `900MB/128GB`, where the two numbers look comparable and are not. Each half degrades on its own - an unreadable footprint leaves the machine pair, an unreadable machine leaves the footprint, losing both falls back to the old heap ratio - which is not decorative, since a footprint reading fails on any platform without a reader and `SystemMemory` returns 0 for "unknown" by design (#237)
- **performance**: clicking the memory indicator on an install without the Performance plugin offered nothing at all - no panel, no dialog, no log line, a control indistinguishable from a broken one. It now offers to install the plugin through the existing install-time dependency prompt rather than a second dialog, so the offer arrives with a working Install button instead of directions. Both entry points are guarded, not just the toggle, and the check asks the installer whether the plugin is present rather than reading plugin states directly, so the guard and the Install button share one definition of "installed" - AGENTS.md records this prompt breaking once already when two halves of it disagreed. Declared optional, which is both true and what makes the copy honest in a dialog about downloading and running code (#237)

## Bug Fixes

- **browser**: `prewarmDecision` returns `RUN` / `ALREADY_RUNNING` / `OPTED_OUT` / `NO_USABLE_ENGINE` / `NEVER_USED_BROWSER` and the log prints the reason it was given, replacing one shared exit that logged "no browser profile on this machine yet" for an opt-out that had nothing to do with the profile and logged nothing at all for the most surprising outcome - a caller that knew a tab was coming being overruled. `force` is deliberately not the default and does not overrule `BOSS_BROWSER_PREWARM=false`: it creates the profile directory as a side effect, so defaulting it on would flip the unforced gate permanently for someone who never opens a browser, which is the cost that gate exists to avoid (#236)
- **browser**: the forced pre-warm is gated on a usable engine. Without that check the boot walks into `getChromiumDir()` throwing, and `applyWorkspace` is reached from around ten call sites, so an engine-less machine with a saved browser-tab workspace would have repeated a futile boot indefinitely - and since the boot slot re-armed only on failure, one of those could have been holding the slot at the moment a completed download wanted it, quietly reintroducing the bug this change is about (#236)
- **browser**: the pre-warm gate no longer does filesystem work on the UI thread. `warmEngine()` runs on the caller's dispatcher and every `applyWorkspace` call site is a Compose scope, while the gate stats the engine directories and reads two `version.txt` files before spawning anything - milliseconds, but on Main on every window creation and every workspace switch, ten lines below a comment in the same function citing THREADING.md for moving a single `resolve()` off it. Now wrapped in `withContext(Dispatchers.IO)`, still ahead of `awaitTabTypes`, which is the ordering a test pins (#236)
- **browser**: the boot slot is released in a `finally` and re-armed if the thread fails to start. Held for the process lifetime, an engine recycle - which drops the engine, and is exactly when a head start is worth something again - would have refused every later caller for good, and a `Thread.start` that throws on OOM or a thread limit stranded the flag claimed with no pre-warm ever again, including the just-finished-download one (#236)
- **ci**: the scheduled JxBrowser watcher stopped reporting a no-op as a failure. `[[ -n "${PIN_PR_URL:-}" ]] && echo ...` was the last statement in its group, and under `bash -e` a false test makes the AND-list return 1, which `-e` cannot tell apart from a command that failed. `pin_pr_url` is empty precisely when there was no PR to open, so this fired on every quiet run: a daily red cron sitting exactly where a real engine-release failure would have shown up. Written as a full `if` rather than `|| true`, because a reader has to know about this failure mode to spot it (#233)

## Improvements

- **perf**: `ProcessFootprint` attributes processes by command line, never by `ProcessHandle.descendants()`. The descendant tree from the host JVM measured 7,858 MB, of which 4,414 MB was the user's own work started in terminal tabs, while two Chromium helpers had been reparented to pid 1 and sat outside the tree entirely. Both directions are covered by tests. Heap health is kept and merged rather than replaced, since heap exhaustion did not stop being a way to die (#237)
- **perf**: the footprint sampler costs 0.327% of one core when visible and nothing at all when it is not. Three rounds of measurement got it there. Ownership comes from an exact pid-set delta rather than reclassifying the whole process table - on a machine running 1,219 processes, reading every command line costs ~70 ms and reading a five-pid delta under 1 ms, so a settled machine classifies nothing, with a 5 minute full rescan to cover the one case a delta cannot see, a process that execs in place. Sampling is gated on the indicator being in the composition, driven by the composable's own lifecycle rather than by restating the three settings that decide visibility, because the reading has exactly one consumer and a session with the bottom bar hidden is not rare - focus mode hides it per edge and Windows ships with it. `FootprintDisplay` counts mounts rather than holding a flag, since a session can have several windows whose bars mount and dispose independently, and clamps at zero so an unpaired dispose cannot latch sampling off for the ones still open. Measured over 16 ticks: 196 ms/min visible, against 269 ms/min after the first pass and ~900 ms/min for the original design, with the periodic 130 ms spike gone (#237)
- **ci**: `.github/actions/sign-windows-msi` is the single owner of the DigiCert signing chain, replacing three near-identical copies that had already drifted - `release-lite.yml`'s credential reset passed one `SM_*` variable where the other two passed four, and the arm64 copy had lost a diagnostic the x64 copy kept. Every fix during the August 2026 signing incident had to be written three times, including the `certsync` step that finally made signing work. Net 384 lines deleted for 304 added, 241 of which are the action itself. Credentials move from command lines into `env`, since `smctl credentials save` interpolated the API key and password straight into a `cmd` line where a value containing `&`, `^`, `|` or a space would be mis-parsed and fail looking exactly like a KeyLocker outage (#235)
- **ci**: the signing action is smoke-tested on its own pull requests, which is the coverage whose absence let a missing `certsync` survive from 2026-07-21 to 9.4.24. The only place a signature was ever read off an artifact was a real release, and `prepare-version` declares `environment: release`, so dispatching the release workflow from a branch is rejected outright. The test compiles its own trivial PE with `csc` and asserts it is `NotSigned` first - signing something already signed would make the assertion vacuous - then checks both that the status reached the caller as an action output and that the signer subject is ours. Path-filtered rather than run on every PR, because each run consumes one signature from the KeyLocker allocation (#235)
- **ci**: the ARM64 job loses its per-step `continue-on-error`. That hedging existed because DigiCert's x64 tooling under emulation on `windows-11-arm` was unproven; two runs have since signed arm64 to Valid. The job-level `continue-on-error` stays, since the ARM runner can still be unavailable. Stated plainly: if arm64 signing breaks now, the release loses the arm64 asset instead of shipping it unsigned, which is the right way round (#235)
- **ci**: `version-check` prints `version.properties` instead of running `showVersion`, and drops the JDK setup with it since nothing left in the job touches Java. That is strictly more information than the formatted box gave, with the same job id, the same two outputs and the same grep expressions. `compatibility-test`'s `showVersion` call is deliberately left alone - there the task is the thing under test rather than a progress message, and that job has a Gradle cache (#234)
- **ci**: three changes on the measured release critical path (`prepare-version` 2m55s, `build-macos-arm64` 10m17s, `create-release` 1m39s). `prepare-version` was the only job running `./gradlew` with no `setup-java` and no `setup-gradle`, so every release fetched the Gradle distribution and resolved dependencies from cold for a single 166s step that all five platform builds wait behind; both setups now carry the same condition as the step they exist for, so a tag-push release - where the increment step does not run - pays neither the install nor a cache save at the head of the job everything queues on. The unconditional second Gradle invocation to clear the prerelease suffix is now guarded by reading the file, which is exact rather than approximately exact: all four of `ClearPrereleaseSuffixTask`'s writes sit after its early return. And the `showVersion` call in all five platform jobs is gone, since `Verify Built Version` reads the generated `VersionConstants` and is what would actually catch issue #111 recurring (#232)

## Known Limitations

- **The footprint reading is a `ps` spawn on macOS, and that is the floor.** The cheap answer is `proc_pid_rusage` via JNI, and Panama's FFM would need Java 22 where this ships on 17. Linux already pays nearly nothing, reading `/proc` directly (#237)
- **A forced pre-warm creates the profile directory as a side effect.** So a restored layout with a *background* browser tab the user never selects satisfies the unforced gate from then on. That is the intended trade - a layout with a browser tab is a browser user - but the argument for not defaulting `force` on rests on the same side effect (#236)
- **The 2 GB heap ceiling raises the limit on very small machines as well as lowering it on large ones.** A 4 GB box gets 1 GB today and comes up to 2 GB. That second direction is the one to revisit if a very small machine ever reports heap trouble (#237)
- **`-Xmx` is a fixed string in the packaged `java-options`.** No static flag pair expresses `min(percentage, ceiling)` and jpackage has no hook to compute one per machine. `-XX:MaxRAM` was tried and is wrong: it replaces the physical-memory figure rather than capping it, so `-XX:MaxRAM=16g -XX:MaxRAMPercentage=25` hands an 8 GB machine half its RAM (#237)
- **The Performance plugin is not reloaded after it installs, and the dependent is not either.** This is the existing behaviour of the missing-dependency prompt, survivable because consumers resolve the API lazily per call (#237)
- **`create-release` still assembles the upstream IPC JARs on the tail**, 28s plus 7s of Gradle setup, for work that depends on no platform build. Moving it to a parallel job would recover that at the cost of an artifact round trip. Notarization is 263s and is Apple's queue, with nothing local to win (#232)

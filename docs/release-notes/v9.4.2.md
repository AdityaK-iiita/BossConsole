# BOSS v9.4.2

**Release Date:** 2026-08-06

A plugin that throws no longer takes BOSS with it: the crash is attributed to the plugin, the plugin is disabled, and every window, tab and live terminal session survives. Alongside it, the rest of the app's dialogs and overlays finally render above the hardware-accelerated browser surface rather than behind the page they belong to, and the configuration follow-ups from v9.4.1's Browser Engine screen close a set of blank-value, lost-update and file-permission holes.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **A plugin crash is recoverable instead of terminal.** Every exit from the crash dialog used to end the process - "Don't Send", Escape and even a *successful* report submission all reached `System.exit(1)`, while the title-bar close box merely disposed the frame and recovered nothing, so which control the user reached for changed the outcome. A crash attributable to a plugin now disables that plugin and keeps the app running; only a fatal host crash still terminates. Nine review rounds went into the paths where that promise could break (#139).
- **Every dialog and overlay routes above the browser.** v9.4.1 flipped JxBrowser to `HARDWARE_ACCELERATED` everywhere, and under hardware the browser view is not a node in the Compose scene at all - Chromium attaches its own native child window that composites above everything Compose paints. That was solved for context menus, tooltips and one modal; the "Open Link" dialog, all 25 Material alert dialogs, the Ctrl+Tab switcher and both drag ghosts were left rendering behind the page. The routing primitive moves down into `plugin-ui-core`, so plugins draw through the same registry rather than a second one that can disagree (#140).
- **Attribution is now unforgeable, and pinned at the call site.** Attribution decides which plugin gets disabled and written out of `installed.json`, and it was asking the classloader what its own id was - a plugin defining classes through a nested loader of its own could have named a rival. The host installs a resolver only it can answer, first-install-wins, before any plugin loads. Review then found a shorter route than the one being closed: the resolver setter itself was reachable from plugin code, which would have rerouted every attribution in the process at once (#142).
- **Blank configuration values fall through where the value is actually decided.** Fixing the UI half alone had turned a confusing-but-truthful state into a silent lie: with `BOSS_RENDERING_MODE=` exported, the dropdown read Off-screen, the command-line preview listed the off-screen switches and the startup log claimed the flag was applied - while the engine still ran hardware. The rule moved into `ConfigLoader.resolve`, applied at all four tiers (#137).

## Features

- **plugins**: recover from a plugin crash instead of terminating BOSS. `PluginExecutionBoundary` records the plugin id before the host calls into plugin code and tags any escaping throwable, so attribution survives the stack unwinding - the normal case for a registered callback such as a context-menu action, where no plugin frame remains by the time the uncaught handler looks. `classifyCrash` returns `RecoverablePlugin` or `FatalHost`, fatal for no plugin id, `OutOfMemoryError` / `StackOverflowError` (disabling a plugin gives no heap back), no recovery seam wired, or - added in review - a plugin no live manager can actually act on, since the dialog was otherwise promising "BOSS keeps running, x will be disabled" and then terminating on the next click. `PluginCrashRecovery` quarantines the plugin synchronously so its surfaces stop rendering, then unloads in the background: close its tabs across windows, disable it in every live manager, persist the disable, tell the user. The dialog names the plugin, reads "Continue Without Plugin", omits "Clean Data & Restart", and gives the button, Escape and the close box one shared `dismiss()`. Nine review rounds, and the interesting ones were all cases where this feature was *worse* than what it replaced: an `Error` escaping the two `catch (e: Exception)` blocks around the dialog left the slot held for good, silencing every later crash including a fatal one; suppression running before classification let a host `OutOfMemoryError` be written to disk while the process carried on under heap exhaustion; a submit that threw between its two happy paths left `isSubmitting` set forever on a frame that is now `DO_NOTHING_ON_CLOSE`, so the dialog had no exit but killing the process; and recovery quarantine was conflated with the ordinary contained-render-fault marker, so any plugin whose panel had ever shown a fallback had all its later crashes written silently to disk. The fatal-path record now writes inline rather than queueing onto a daemon thread nothing drains at shutdown - it is the entire justification for that branch, and it was missing for the one crash class where it matters most (#139)
- **overlays**: heavyweight popups gain anchored placement, and plugins share the renderer. `OverlayConfig.heavyweightPopup` becomes a forwarding accessor onto `BossOverlayHost.popupRenderer`, so a plugin's context menus and dropdowns take the same window implementation as the host's. `BossPopupAnchoring.AnchorBounds` places content below the caller's window-space bounds, corrected by the parent's content-pane inset - the overlay window is placed at the *frame* origin while Compose measures anchors against the *content pane*, so without that correction an anchored popup sits a title-bar too high and overlaps the control it belongs to. Cursor anchoring is untouched and remains the default (#140)

## Bug Fixes

- **overlays**: route every dialog and overlay above the `HARDWARE` browser surface. `BossDialog` is a drop-in for `androidx.compose.ui.window.Dialog` owning the scrim and centering on both paths, so all 30 call sites are a rename; `BossAlertDialog` rebuilds Material 2's card from design-system tokens with the parameter list kept name for name, because Material offers no injection point, and that covers `GenericDialogHost` and therefore every plugin-requested dialog with no plugin release. Only a window that actually hosts a browser surface routes heavyweight - without that gate a Settings dialog opens over the MAIN window, since the overlay measures `LocalAwtWindow`, and then floats above it. Then the defects a new window path brings with it: a modal must not act on the click that opened it (cmd-clicking a link opened the dialog and the release immediately chose whichever option sat under the pointer, so input is refused until the pointer is known idle, on the Initial pass, with a held button vetoing arming whichever signal asks); the anchored popup flashed at the screen origin at full width for a couple of hundred milliseconds, because the renderer ran before `onGloballyPositioned` and an unmeasured anchor is a distinct state from one measured at the origin; the anchor probe was not layout-neutral despite a comment claiming it was, `fillMaxWidth()` having starved later siblings in a `Row` and changed anchoring even for off-screen installs; and the input guard could latch off permanently when a press was released over another application, leaving the dialog mouse-dead with only Escape out. A shadowed parameter is worth naming on its own: `anchorWidthDp` collided with an existing `contentWidthDp` local, the local won, and the content was constrained to the width it already had - perfectly circular, silently swallowing three real upstream fixes, and detekt reported it the run it was introduced as "Condition is always 'true'" and was dismissed as noise. The api mirror is now synced as a whole file by `scripts/sync-plugin-api-overlay-mirror.py`, exiting non-zero if a token substitution stops matching; the previous marker-based splice had left every `ScrimmedModalContent` fix out of the copy `ApiClassLoader` actually serves on an older host (#140)
- **plugins**: attribute plugin callbacks at the call, and pin that the wiring exists. The context-menu seam was wrapped at mapping time, handing back a fresh closure per item per recomposition - the items compared unequal every time, so Compose could never skip the menu subtree. Attribution moves to where the host invokes the callback (`PluginExecutionBoundary.invokeAttributed`), which costs one cached class lookup and no allocation and covers every item reaching that call site rather than only those built through a wrapping factory. Nothing proved the wiring was called: delete the call site and the whole suite still passed while every plugin callback silently went unattributed, and the same was true one layer up of `installPluginIdResolver` in `main.kt`, whose deletion would have reverted production to the spoofable duck-typed fallback. `ContextMenuAttributionTest` drives the real `contextMenu` modifier with a genuinely plugin-defined lambda - real jar, real `PluginClassLoader` - and both cases were confirmed to fail when the call is removed. Also: a throwing plugin action left the context menu open, since `invokeAttributed` rethrows past `onDismissRequest`, which used not to matter when the throw took the app with it; `finally { onDismissRequest() }` could swallow an in-flight plugin throwable and replace it with a host one, losing the tag and blaming BOSS for the crash; and plugin ids are capped and stripped of control characters at every display site including the dialog body, where a long id from a manifest pushes "Re-enable it from Toolbox" out of view (#142)
- **config**: a blank environment variable is not a value. `ConfigLoader.resolve` applies the rule to all four sources, so a properties line reading `KEY=` is treated the same way; `defaultValue` is deliberately exempt, since a caller passing `""` has said so. The same rule reaches `BossLogger.configureFromEnvironment`, where `export BOSS_LOG_LEVEL=` resolved through `LogLevel.fromString("")` to a level nobody chose and shadowed both the system property and the dev-mode default, and `GitHubConfig`'s source attribution, which had the mirror problem of reporting the environment for a token that came from `local.properties`. Level resolution is split into a pure `resolveLevel(envLevel, propLevel, devMode)` because a JVM cannot set its own environment variables, which is the same reason `resolve` takes its sources as arguments (#137, closes #134)
- **settings**: settings edits compose instead of overwriting each other. `updateSettings` took a finished value while its callers computed `current.copy(field = new)` from a snapshot collected earlier, so two edits landing in one frame discarded the first - ordinary rather than exotic with per-keystroke number inputs. It now takes a transform applied through `updateAndGet`, with the write path re-reading under the mutex; the 15 call sites bind the parameter as `current` rather than `it`, since several callbacks already bind `it` to the new control value. The settings file is created with `rw-------` via `createFile` rather than chmod-ed after `writeText`, closing the window where a file that can turn off the Chromium sandbox sits at the default umask, with a restrict-after-write retained as the fallback the create-with-attributes approach had quietly removed. Identical queued writes are coalesced, since typing "8192" wrote the same bytes four times (#137)
- **settings**: "Reset engine flags" was a silent no-op after a corrupt load. Seeding the write cache from `bootSettings` recorded "defaults are persisted" about a file holding nothing of the sort, because `loadSync` answers a parse failure with a DEFAULT object while the corrupt file stays on disk - so Reset matched the cache, skipped the write, and left the corrupt file in place while the UI reported success. Introduced by the previous round's own fix, which made the code match a KDoc that was the wrong half to keep. Assigning `settingsFile` also clears the cache now, since a different file means nothing is known to be persisted in it (#137)
- **startup**: configure logging before the first line that logs. It sat below `applyToSystemProperties`, `setLinuxWMClass` and `setupNativeLibraryPaths`, so the Chromium flag audit trail, the corrupt-settings warning and the Skiko backend warning all ignored `BOSS_LOG_LEVEL` - and the flag audit is the line most worth being able to turn up. Verified safe rather than assumed: `configureFromEnvironment` only reads env and system properties, `initialize()` only registers a shutdown hook, and file logging is opt-in with an explicit path, so `setupNativeLibraryPaths` reassigning `java.io.tmpdir` below cannot affect it (#137)
- **overlays**: `BossPopup` defaults `focusable = false`, matching `Popup`. It is documented as a rename-only migration from `androidx.compose.ui.window.Popup`, and `PopupProperties()` defaults to false while this defaulted to true - so a caller who renamed and changed nothing else got a popup that steals focus, which under a text field means typing stops working. Every existing caller passes the parameter explicitly, so the flip changes nothing today and would have been expensive to make after the version froze (#140)

## Improvements

- **crash**: one cause-chain walk, one uncontainable check. The bounded, cycle-guarded cause walk existed in four copies with four copies of the depth bound, three carrying comments claiming they matched the others - and they had stopped matching, which is how the uncontainable carve-out got fixed in `classifyCrash` and left flat in `decideWindowExceptionRoute`, so an identical `InvocationTargetException(cause = OutOfMemoryError)` escalated in one and was contained in the other. One `Throwable.causeChain()` now backs `isIgnorable`, attribution, the uncontainable check and the render route, with a single implementation in `plugin-sandbox` re-exported into the crash package. `PluginCrashInterceptor.attributeToPlugin` consults the boundary's tag first, since the two attributions disagreeing about the same throwable routed a render fault to Contain or Escalate instead of the plugin's own boundary (#139, #142)
- **docs**: record the behaviour change v9.4.1 shipped without announcing. `docs/FEATURES.md` now states that `--no-sandbox` and `--remote-debugging-port` and their siblings are refused from `BOSS_CHROMIUM_EXTRA_SWITCHES`, because a confirmation that can be sidestepped by typing into a free-form box is not a confirmation, along with the env-still-wins precedence and why capability keys bypass `ConfigLoader` (#137)
- **tests**: three restart tests were asserting a fact about the developer's home directory. `bootSettings` is a val read from the default path at object construction, before any test can redirect `settingsFile`, so `assertTrue(boot.isDefault)` failed on any machine that had ever saved a Chromium setting - including, pointedly, one carrying a `~/.boss/chromium-flags.json` written by the bug an earlier commit in the same PR fixed. `restartWouldChangeAnything` takes `boot` as a defaulted parameter now, so tests pass a synthetic one and production is unchanged. The Graphite test also resolved against the live mode where production uses the next-launch mode, which agree only while boot is default - exactly the condition under which the test would stop noticing (#137)

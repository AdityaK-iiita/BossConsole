# BOSS v9.4.21

**Release Date:** 2026-08-19

Two changes, both about a component that could not fit what it was given. The host's credential fill is deleted rather than repaired - it had to guess which field to type into and on accounts.google.com it guessed a hidden decoy - and `BossAlertDialog` now takes the smaller of the width it wants and the width it has, instead of clipping in a panel narrower than 400dp.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **The host no longer fills credentials into web forms.** `FormFieldInjector` is gone, all 953 lines. Reported as "right-click a saved credential and the email box stays empty", and measured live on accounts.google.com the fill did something worse than nothing: the password went into a `display: none` `hiddenPassword` input while the visible identifier box was never touched (#215)
- **One root cause behind all three failures - the signature is `(username, password, fillBoth)`, so the host had to guess the field.** `input[type="password"]` took the first such element in the DOM whether or not it was rendered, which on that page is Google's hidden decoy; `[autocomplete="username"]` is an exact attribute match while the real field declares `autocomplete="username webauthn"`, a space-separated token list per the HTML spec; and the last-resort strategy was "first text input in a form containing a password", on a page with no `<form>` element at all (#215)
- **`BrowserHandle.fillCredentials` survives as a deprecated no-op returning false.** Removing the declaration would make every caller compiled against an older api throw `NoSuchMethodError` at the call site - and fluck-browser 1.2.18 and earlier call it bare inside a `launch`, where an Error reaches the coroutine uncaught and the host tears the whole plugin down, closing every open browser tab (#215)
- **An alert's width is what it wants, not what it must have.** `Modifier.width(AlertWidth)` made 400dp the minimum as well as the maximum, so on the scrimmed in-window path - measured against the app window rather than a dialog window of its own - a narrower window or panel slot got a card it could not fit and clipped it at the edge (#214)

## Breaking Changes

- **browser**: `BrowserHandle.fillCredentials(username, password, fillBoth)` is deprecated and does nothing, returning false. It is scheduled for removal in a later release. The eligibility rules belong next to the code that chose the field - a right-click menu was raised on a specific element and an autofill suggestion is anchored to a specific box, so every caller already knows what the host's guess was reconstructing. See fluck-browser's `CredentialFill`; consumers gate on `minBossVersion` (#215)

## Bug Fixes

- **ui**: `BossAlertDialog` measures with `BoxWithConstraints` and takes the smaller of `AlertWidth` and the space available. Reported against the Atlas plugin, whose panel slot is routinely narrower than that: its approval dialog is a consent surface, and inside a card that could not shrink the action Row was measured first child to last, so at 240dp the last button - "Allow once", the primary - came out 0dp wide, leaving "Always in this chat" as the only visible way to proceed. Measured, not inferred (#214)
- **browser**: a saved credential picked from the right-click menu no longer writes the password into a hidden input on pages like accounts.google.com. The host path is deleted outright rather than fixed in place, so the fill happens where the field is actually known (#215)

## Improvements

- **ui**: `BoxWithConstraints` rather than `widthIn(max = AlertWidth)`. With only a maximum a `Surface` wraps its content, which would have made every short alert in the app narrower than 400dp; taking the minimum of wanted and available leaves the wide case byte-identical and changes only the case that was broken (#214)
- **browser**: `discretePasswordFill` now mirrors to the `boss.fluck.discretePasswordFill` system property, exactly as `showShareButton` already mirrors to its own and for the same reason - the plugin loads in a separate classloader and cannot read the host's settings object. It only ever ran as part of the deleted fill, so its Settings toggle would otherwise have become a switch that does nothing. Both defaults are published from an `init` block, because a Kotlin property initializer does not run through a custom setter and a first launch with no settings file would leave the property unset - and the privacy default is true (#215)
- **quality**: eleven now-meaningless detekt baseline entries go with `FormFieldInjector`, so that area is enforced again rather than permanently excused. `fillField`, `installFormSubmissionMonitor` and the discrete-mode pair had no callers outside the object, and `logFieldDebugInfo` was already flagged `UnusedPrivateMember`. `FormFieldDetector` stays - `injectFormDetectionScript` is still used (#215)

## Known Limitations

- **A plugin pinned to an old host gets a silent no-op.** `minBossVersion` gates plugin updates, so a user on an older host can be stuck on a fluck-browser build whose fill now returns false with no message. That is still strictly better than what it did before, which was writing a password into a hidden input (#215)
- **The api jar's copy of `BrowserHandle` is not the one that runs.** The host compiles its own in and serves it parent-first, so the boss-plugin-api copy is shadowed - which is why this behaviour change lands in the host rather than in an api release, and why reading the api source will not tell you what `fillCredentials` does (#215)
- **Dialog height is deliberately left alone.** Constraining it without giving the body a scroll would move where a tall dialog clips rather than fix it, and each call site bounds its own content today (#214)

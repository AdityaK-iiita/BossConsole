# BOSS v9.5.0

**Release Date:** 2026-08-26

Four changes. A window could freeze outright on any page load - the page-helper injection blocked JxBrowser's own RPC thread on a queue only that thread could drain - AI provider settings leave the host entirely for the plugin that owns the credentials, the macOS title bar comes back on by default with a migration rather than a default flip, and a tab's close cross stops hiding until the pointer finds it. The browser engine moves to JxBrowser 9.5.0.

> **macOS 13.0 (Ventura) or later is required.** The floor is set by the bundled JxBrowser engine's declared `LSMinimumSystemVersion`, which was 13.0 for every 9.4.x engine; the engine moves to 9.5.0 in this release and that declaration was not re-checked against the new bundle.

## Highlights

- **The window no longer deadlocks on a page load.** `NavigationFinished` is delivered on JxBrowser's RPC thread, and the handler made two blocking round trips straight from it - `renderProcess().pid()` and `injectPageHelpers()`, whose `executeJavaScript` re-enters `RpcThreadCallExecutor` and parks on a queue only the thread it is blocking could drain. Every later blocking call on that browser then queues behind it: the EDT parks inside its own `executeJavaScript`, the AppKit main thread parks behind the EDT, and the window and the menu bar both freeze (#268)
- **`Settings > AI Providers` is gone, and so is the singleton behind it.** The credentials live in the Secret Manager plugin's vault, and since 1.2.19 that plugin has an AI section of its own - so the page that manages those keys now sits beside the keys rather than two clicks and a different window away. Settings search still answers for `api key`, `anthropic`, `claude`, `vault` and `secret manager`, through a curated panel signpost that opens the plugin's panel and raises the main window (#258)
- **The title bar is back on by default on macOS.** It had been switched off there with the traffic lights moved onto whichever column is leftmost, which works only while a column is wide enough for a 78x28dp box - a collapsed tab bar is one 40dp rail, and the fallback for anything narrower was to draw the row anyway. "Off" was never a state a macOS window could reliably be in, and the row appeared and vanished as a window was resized past the bar's collapse width (#269)
- **A tab's close cross is always visible.** It used to be revealed on hover, which cost twice: whether a tab could be closed from the strip at all was undiscoverable, and the chip changed *width* when the cross appeared, so the strip reflowed under the pointer reaching for it (#269)

## Features

- **tabs**: the close cross on a tab chip is rendered unconditionally rather than gated on hover. The cost is accepted and real - every chip is wider now, so fewer fit before the strip scrolls, and a pane with many tabs is where closing one from the strip matters most. Four composition cases pin it, all of which fail against the hover gate (#269)
- **window**: the macOS title bar needs a migration, not a default flip. The class default stays `false` so Windows and Linux keep the row off, and `encodeDefaults` is false, so a value equal to the class default is never written to their files - meaning an existing macOS install cannot be told apart from a fresh one by the file alone. A fresh install takes the platform branch in `getDefaultSettings`; an existing one takes the new 1 -> 2 step, which turns the row on for macOS only. That step inherits the blindness the 0 -> 1 step already documents: a settings file records what a value is, never who set it, so somebody who deliberately switched the row off on macOS moves too (#269)

## Bug Fixes

- **browser**: page-helper injection deadlocked the JxBrowser RPC thread. Both blocking round trips move onto a dedicated single daemon thread, following the pattern `contextMenuExecutor` and `frameProbeExecutor` already establish in the same file, and the in-flight follow-up is superseded per commit the way `frameStallJob` is. The renderer pid is cleared synchronously on commit and written back off-thread only if that commit has not been superseded, which keeps the `RendererPid` rule intact - a stale renderer is never reported for a new document, and "unknown" stays the only failure mode (#268)
- **settings**: removing the AI Providers section took its search entry with it, so `api key`, `anthropic` and `claude` matched nothing and Settings answered "No matching settings" for a feature that exists one window away. Nothing would have replaced it: plugin pages are merged into the index at query time, but the AI section is a *panel*, not a settings page, and `pluginPageEntry` drops words shorter than four characters anyway (#258)
- **settings**: the new signpost fired `openPanel` then `focusWindow` unconditionally, so the four cases the removed section used to name - plugin never installed, switched off, rejected as binary-incompatible, hidden for lack of `secret.read` - all ended with the Settings window dropped behind a raised main window showing nothing, and the row was searchable regardless of RBAC. One read answers all of it: a plugin that is absent, off, incompatible or not permitted registers no panel, so signposts are filtered on panel registration at query time, read outside the `remember` so a late registration turns the row on rather than leaving search stale until Settings is reopened. `revealPanel` re-resolves as a fence, returns without raising when the panel has gone, and emits the registered id rather than the requested one (#258)
- **settings**: the unresolved-deep-link debug line fired on every plain Settings open, since `open()` passes null and null resolves to `Unresolved` too. It is gated on a section actually having been asked for (#258)

## Improvements

- **settings**: what went with the AI Providers section - the `LLM_PROVIDERS` section and its sidebar entry, its embedded-panel registration, its search-index entry, `LLMProvidersSettings.kt`, and `LlmProviderAPIAccess` in full plus its startup wiring. That singleton's own KDoc said it existed because "the settings UI needs the singleton - host composables have no plugin handle", and with that UI gone nothing read it. `DefaultPlugin.llmProvider` never used it and still does not: it resolves against its own instance's registry, because `DefaultPlugin` is per window while the cached reference was overwritten by each window's `initialize()`. `PluginContext.llmProvider`, which is the part other plugins consume, is unaffected (#258)
- **settings**: a stale `boss://settings?section=LLM_PROVIDERS` deep link resolves to `SettingsDeepLink.Unresolved`, so the window opens on its default section rather than failing - checked rather than assumed, and pinned in both directions, since a future section or plugin page taking that name would silently resurrect the old target (#258)
- **settings**: `SettingsSearchEntry` gains a third target alongside section and plugin page id. `revealPanel` lives in its own file because `SettingsWindow.kt` was already at detekt's `TooManyFunctions` threshold (#258)
- **docs**: the comments in `SelfHealingSettings` and `SelfHealingSettingsManager` that pointed at the old section, the RBAC guide, and `AGENTS.md` (which still opened "Three sections", naming a caller this change deletes) all point at the plugin's panel now. Earlier release notes are left as the historical record they are (#258)
- **tests**: signpost guards for its six keywords - asserted by *searching*, since a keyword that is present but unrankable is the failure worth catching - plus one for its shape and one at the rail, so the breadcrumb that carries the whole message cannot go missing. The window-appearance migration cases fail against a step that does nothing, and every new guard was verified by reverting the fix under it. 2,879 tests, 0 failures (#258, #269)

## Dependencies

- **JxBrowser 9.4.1 -> 9.5.0**. The engine bundle for 9.5.0 is published on both sources, so the pin can follow; opened automatically by the JxBrowser auto-release watcher. `gradle/libs.versions.toml` is the single source of truth, generating `VersionConstants.JXBROWSER_VERSION`, which every engine call site reads (#270)

## Known Limitations

- **A macOS user who deliberately turned the title bar off gets it back.** The migration cannot tell them from someone who never touched the setting, and turning it back off in Settings works as before (#269)
- **secret-manager has no version floor, deliberately.** The AI section exists in that plugin only from 1.2.19, and nothing in the host gates on it: secret-manager is not in the `system_plugins` manifest, so no `min_version` applies, and plugin updates surface in the Toolbox rather than installing themselves. A user on 1.2.18 who takes this build gets the Secret Manager panel with no AI section in it. Nothing is deleted and nothing is lost - the credentials stay in the vault and `PluginContext.llmProvider` keeps serving every plugin that asks - and the only lever the host has for a floor is refusing to load the plugin, which would take the vault down with it (#258)
- **Someone who never installed Secret Manager now finds nothing in Settings search rather than an install offer.** The signpost is filtered on the panel being registered, which is the same rule the rest of the window follows for plugin pages (#258)
- **AI self-healing is unaffected and still resolves its own key.** `SelfHealingSettingsManager` runs before any window or plugin exists, so it cannot reach the plugin's store: it reads `AI_REPAIR_API_KEY`, then the provider's own environment variable, then the legacy `~/.boss/llm_settings.json`. A key rotated in the plugin's AI section does not reach it (#258)

# BOSS v9.3.0

**Release Date:** 2026-08-04

Minor-version release carrying the JxBrowser 9.4.0 / Chromium 151 engine, which raises the macOS floor to 13.0 and brings the updater refusal guard that makes raising it safe. Alongside it: system plugins finally get signature sidecars ahead of the enforcement flip, the crash dialog's buttons stay reachable and its failure message is sanitized properly, and the IPC `renameFile` that reported every failure as success is fixed.

> **macOS 12 is no longer supported.** JxBrowser 9.4.0 dropped it, and the 9.4.0 engine bundle declares `LSMinimumSystemVersion 13.0`. The updater now reads that requirement from the incoming DMG *before* it quits the app, so a macOS 12 install is refused with an explanation and keeps working rather than being deleted and replaced with a bundle Launch Services will not open.

## Highlights

- **Selecting the 9.4.0 browser engine bricked the browser, and the version check could not see it.** JxBrowser resolves its native toolkit under a directory named after the Chromium build its *Java* library was compiled against, so a jar pinned at 9.3.0 asked for `Versions/150.0.7871.47` while the installed 9.4.0 engine ships only `Versions/151.0.7922.72` - `System.load` failed on a path that was never going to exist. `isChromiumInstalled()` compares `version.txt` against the *effective* version (the Settings pin), not against what the linked library needs, so the engine looked correctly installed right up to the native load. The bundled library moves to 9.4.0, which makes the pin unnecessary, and any pin that is not the bundled version is now cleared rather than honoured - a setting that JxBrowser's design guarantees cannot work is not a preference worth preserving.
- **Raising the macOS floor is unsafe unless the delivery path is gated on it.** `generateMacOSUpdateScript` quits BOSS, `rm -rf`s the installed app, copies the new one and relaunches, with no OS check anywhere under `updater/` and no minimum-OS field in the release manifest. For a macOS 12 user - supported deliberately since v9.2.61 - this release would have deleted a working install and left no in-app way back. Both the Kotlin path and the shell script now read `LSMinimumSystemVersion` from the incoming bundle, so they track whatever DMG is being installed and need no maintenance the next time the floor moves.
- **Every system plugin sat on disk unsigned.** A store signature travels to load time as a `<jar>.sig` sidecar, and every install path writes one - except `PluginStoreSetup.downloadSystemPluginFromGitHub`, which installs api, Toolbox, the microkernel runtime, terminal-tab, editor-tab and fluck-browser on first run. Invisible only because enforcement defaults to off; when #102 flips it, every one of those stops loading, Toolbox included - which is how a user would otherwise recover. Sidecars are now written on install *and backfilled for the installed base*, which the first cut missed entirely.
- **Expanding "Technical Details" pushed the crash dialog's buttons off-screen with no way to scroll them back** - so the one moment the user most needs to report or dismiss a crash was the moment they could not. Fixed header, scrollable body, pinned footer.

## Bug Fixes

- **browser, updater**: bundle JxBrowser 9.4.0 so the 9.4.0 engine actually loads, and refuse an update this Mac cannot launch. The library pin moves 9.3.0 → 9.4.0 (compiled against Chromium 151.0.7922.72, exactly what the `chromium-v9.4.0` bundle carries, published on both release sources for all six platform archives) and becomes the default, so the Settings pin is no longer needed to run it; `effectiveVersion` normalises away any unusable pin at load and writes the file back, so the Settings UI stops displaying it too. The macOS floor rises to 13.0 with it, tracked as a documented consequence of the engine bundle rather than a constant, and the two places that quote it to users move with it. Six review rounds hardened the update path around that floor, each finding the previous round's fix incomplete: the OS check moved ahead of the quit so the user gets a real dialog with the app still running (the shell guard stays as defence-in-depth, pinned by a test asserting it precedes the `rm -rf` - a bare `indexOf("rm -rf")` matches the guard's own comment, so the test matches the shell-escaped command); `installUpdate` returns an `InstallOutcome` across the expect/actual boundary so the tailored reason reaches the user instead of being flattened to a literal "Installation failed"; both sides fail *open* on an unreadable or non-numeric plist and on an unknown current OS, after PlistBuddy's exit-1 error text was found passing the `-n` test and being ranked against a version number by `sort -V`; the 5s PlistBuddy timeout was dead code, since `readText()` blocks to EOF and ran before `waitFor(timeout)`; and the decision is now a pure `osFloorMessage(required, current)` in its own file, tested in both directions on all three CI legs - swapping its arguments previously left all seven tests green while blocking every macOS 13 user and sending every macOS 12 user down the destructive path. No API changes were needed; 9.4.0 is additive over 9.3.0. Follow-ups filed rather than carried: the dropdown can still pin a mismatched engine (#118) and a refused update is re-offered and re-downloaded every cycle without a manifest-level `min_os` (#119) (#99)
- **plugins**: sign the system-plugin install path, and stop stale sidecars outliving their JARs. System plugins come from GitHub releases rather than the store, so the signature is fetched separately and matched to the bytes actually downloaded - the sha256 comparison is load-bearing, not defensive, because `POST /github` re-hosts JARs through Supabase Storage and pairing the store's signature with GitHub's bytes would produce a *present-but-invalid* sidecar, which hard-fails at load regardless of the enforcement flag. Every failure path therefore clears the sidecar: unsigned is the pre-existing state and still tolerated, wrong is not. Review found the first cut never reached the installed base - `ensureSystemPluginsInstalled` returns early once a JAR exists and the update check only fires for a strictly newer release, so an up-to-date user stayed unsigned forever - and that the store lookup was keyed on the GitHub tag rather than the manifest version the loader re-derives the anchor from. Round 2 found the backfill re-creating the state it exists to prevent: it raced the update check on the same scope for the same JAR (old signature written beside new bytes), and it ran before `PluginStoreConfig.accessToken` was ever set, so it 403'd deterministically for exactly the plugins with non-empty `requiredPermissions` while booking a phantom download row on every retry. It now queues and drains once per process off the `sessionStatus` collector, serially, skipping any plugin whose update check is in flight; `persistStoreSignatureSidecar` re-hashes before writing so the bind only happens if the bytes still match, closing the race for both callers; sidecar writes are temp-file + `ATOMIC_MOVE`, since this is the first code writing them concurrently with plugin loading reading them. Also closed: the crash window between the move and the sidecar write, `catch (Exception)` swallowing `CancellationException`, a `writeText` outside the try that could fail a whole install on a full disk, and four more sites where a `.sig` could outlive its JAR (both old-version cleanups, `PluginJarReconciler`'s duplicate cleanup, and `PluginLoaderDelegateImpl`'s microkernel-runtime rejection - the dangerous one, since uninstall→reinstall of the same version reuses the filename). "No signature" was logging at debug, which is the one signal telling you whether the fleet is ready for the flip; raised to warn. Four enforcement-flip comments pointed at BossConsole#872, an issue that does not exist in this repository after the open-source cutover - refiled as #102 with its two blockers recorded (#101)
- **crash**: make the crash dialog body scroll so its buttons stay reachable. The whole body was one unscrollable `Column` in a deliberately small window, and expanding "Technical Details" added ~250dp, pushing "Report Issue", "Don't Send" and "Clean Data & Restart" below the bottom edge. Now a fixed header, a body capped with `weight(1f, fill = false)` - `fill = false` keeps the cap from becoming a floor, so a collapsed report renders exactly as before - and a pinned footer that the submit-result card moves into, since an off-window "failed to submit" is worse than none. The stack trace keeps its 200dp cap on its own scroll state so a deep trace does not turn the body into an endless scroll; scrollbars appear only where a region actually clips, excluding `ScrollState.maxValue`'s `Int.MAX_VALUE` sentinel that would otherwise report overflow on the first frame of content that fits, with the body's thumb overlaying rather than reserving a gutter so a width→height feedback path cannot latch overflow on; thumbs are styled from theme colours, since Compose's default black-at-12% is invisible on these panels (#106 tracks lifting that into `BossTheme`). `CONTENT_PREFERRED_*` on the `ComposePanel` makes `pack()` derive the frame from the content instead of the content minus a title bar. Seven layout tests at a content box tighter than any that ships, each controlled against the defect it claims to catch. #104 and #105 filed rather than folded in (#100)
- **crash**: sanitize the submit-failure message with the right sanitizer. #100 made that card selectable and ran it through `LogSanitizer.maskUriParams`, which redacts a fixed set of named params inside a `?`/`#` segment - and the ktor message the code comment cited as the reason to sanitize has neither, so the host and path shipped verbatim in the string #100 itself identified as most likely to be pasted into a public issue. Measured on that exact input, `maskUriParams` leaves `[url=https://api.risaboss.com/functions/v1/crash-report, ...]` while `sanitizeExceptionMessage` gives `[url=https:[PATH] request_timeout=15000 ms]` - the latter is what `CrashHandler` already applies to the exception message and stack trace, so this card was the only one held to a weaker standard. Also in this change: the scroll-boundary rule becomes a zero-height overlay inside the body rather than a footer sibling consuming ~17dp while gated on the measurement that decides whether to show it (monotone, so never oscillating, but able to latch overflow on for content near the boundary - which undercut #100's claim that a collapsed dialog renders unchanged); the stack-trace cap becomes a shared constant documented as load-bearing, since the pane's `verticalScroll` nests inside the body's and removing the `heightIn` throws on an infinite max-height constraint; and the sanitize call is memoized, since `userNotes` is read in the same restartable scope and every keystroke re-ran the regex passes. Six new tests, each controlled against the defect it claims to catch, two of them rewritten after their controls passed. #109 tracks bare-host exceptions the shared sanitizer still lets through (`UnknownHostException.getMessage()` is just the hostname); #110 tracks sanitizing at construction so this stops being call-site discipline (#107)
- **ipc**: `renameFile` could not overwrite on Windows, and reported every failure as success. Two compounding defects in `FileSystemServiceImpl`: the `overwrite = true` path used `File.renameTo`, whose behaviour when the destination exists is platform-dependent in the direction that hides it during development (POSIX `rename(2)` replaces, Win32 `MoveFile` fails with `ERROR_ALREADY_EXISTS`), so the one request this API explicitly offers was the one it could not serve there - the same split that cost the browser its favicons in #95. And the boolean was discarded with `Empty` returned unconditionally, so a missing source, a permissions error or the Windows case above all told the caller the rename had happened, on every platform. Now `Files.move` with `REPLACE_EXISTING` when asked for, `ATOMIC_MOVE` tried first and dropped for a cross-volume move - a real possibility for an arbitrary path pair arriving over IPC, unlike the in-process caches in #95. Failures raise gRPC statuses rather than propagating as a bare `UNKNOWN`, since `Empty` has no `errorMessage` field to fall back on: `ALREADY_EXISTS`, `NOT_FOUND`, `PERMISSION_DENIED`, `INTERNAL`, each naming the path. `PluginInstallService`'s delete-then-`renameTo` - which works on Windows but leaves a window where neither file exists, so a crash there loses an installed plugin JAR - moves to `atomicMoveFrom`. `FileSystemServiceRenameTest` is the module's first test, verified to catch the bug: restoring the old body fails 2 of 5, and only one of those two is Windows-only. A review round also corrected a TOCTOU comment that claimed a guarantee POSIX does not give - the JDK's non-atomic `Files.move` does its own `stat` in Java then calls bare `rename(2)`, so the window narrows rather than closing, and in a change whose whole subject is that rename semantics diverge by platform, that comment should not have been the one place asserting they do not. `createFile` and `deleteFile` in the same file discard their booleans the same way and are deliberately left, being a behaviour change to an IPC surface beyond what #96 covers. Fixes #96 (#103)

# BOSS v9.2.63

**Release Date:** 2026-07-30

Single-change release: the host stops owning AI provider configuration. **Settings → LLM Providers** becomes **Settings → AI Providers**, rendered by the secret-manager plugin that now holds the credentials, the environment-variable resolution and a live model catalogue - and `PluginContext.llmProvider`, which the host had never implemented, finally returns something.

## Highlights

- **The host's LLM stack is gone** (~1,400 lines). `LLMModelFetcher` advertised itself as a dynamic fetcher but returned hardcoded lists from every provider function - its own comments said so - with no-op cache reads and writes, and lists that had drifted years out of date. `LLMSettings` carried a 40-entry `LLMModel` enum whose secondary constructor took a provider and discarded it, so it could never be filtered by provider. Both, plus `DesktopLLMSettingsManager` and the startup effect that loaded it, are deleted.
- **Provider config moves to a plugin that can actually do it**: keys are stored as encrypted secrets rather than plaintext on disk, and model lists come from the providers themselves. `LlmProviderAPIAccess` mirrors `EditorAPIAccess` as the single relay backing both the settings section and `PluginContext.llmProvider` - plugins offering AI features previously got `null` there.
- **Self-healing keeps working across the migration**: `SelfHealingSettingsManager` resolves a key before the window opens and long before any plugin registers, so it can't read the new store. It reads the legacy key file directly and now also tries `llm_settings.json.migrated` - the name the plugin's one-shot import renames the original to - so an operator who accepts that import doesn't silently lose self-healing on an upgraded install.

## Features

- **plugins**: implement `PluginContext.llmProvider` - a new `DefaultPlugin` override relays the `LlmProviderSettingsAPI` registered by the owning plugin, so a plugin with AI features can reach provider configuration instead of reading `null`. It's a `get()` rather than `by lazy` because registration is asynchronous and a lazy would cache `null` forever, and it's forwarded through `TrackingPluginContext` and `SandboxedPluginContext` so sandboxed and out-of-process plugins see it too (#77)

## Improvements

- **settings**: render **Settings → AI Providers** from the secret-manager plugin, following the `BossEditorSettings` delegate pattern. The section is registered as an *embedded* panel - the plugin's panel scrolls itself, and nesting that inside the host's scroll container measures with infinite height and crashes. It uses the new `supportsSettingsPanel` flag so a plugin that registers without overriding the panel shows the explanatory notice rather than an empty section, and `LlmProviderSettingsPanel` delegates to `rememberProvider` so a late-registering plugin's panel appears when its asynchronous startup registration lands instead of never. `LLM_PROVIDERS` keeps its enum name so existing deep links still resolve; only the display name changes (#77)
- **self-healing**: correct the three UI strings that told operators to set a key in LLM Providers - that guidance became untrue the moment the settings screen could no longer feed it, so the readiness card, the model field description and the blocker list now name `AI_REPAIR_API_KEY` or the provider's own environment variable. The `SelfHealingProvider` KDoc is rewritten too: it linked to the deleted enum, and its last clause had become backwards (self-healing *does* now need its own key). The provider names still can't be renamed, but the reason is now that `llm_settings.json` is a legacy on-disk format keyed by them - a constraint nothing checks for us with the enum gone (#77)

## Bug Fixes

- **plugins**: resolve `llmProvider` against **this** window's registry rather than the singleton - `DefaultPlugin` is per window and `apiRegistry` is per instance, while `LlmProviderAPIAccess.cachedDefaultPlugin` is a singleton overwritten by each window's `initialize()`. Routing the member through it meant window 1's plugins resolved against window 2's registry, getting another window's API object or `null` if that window hadn't registered yet - the exact failure this relay exists to fix. The settings UI still goes through the singleton because host composables have no plugin handle (#77)
- **self-healing**: read `llm_settings.json.migrated` as well as the original, extracted as a testable `legacyKeyFrom` with nine new cases. This was the quietest logic in the change: reading only the original name would have stopped self-healing the moment a user accepted the plugin's import - on upgraded installs only, with nothing in the log. A file that exists but has no entry for *this* provider falls through to the next candidate rather than short-circuiting, an unreadable file is skipped rather than aborting the search, and a corrupt file now warns at most once per lookup instead of once per candidate (`hasApiKey` re-runs on every settings change) (#77)

## Dependencies

- **boss-plugin-api**: 1.0.69 → 1.0.71 for `LlmProviderSettingsAPI` and `supportsSettingsPanel`. Skipping 1.0.70 is deliberate: the api release workflow performs its own version bump, so the bump to 1.0.70 in that repo's PR was consumed and the released tag is v1.0.71 - there is no v1.0.70 release. `fetchApiPluginJar` resolves from store/GitHub releases with no Maven fallback, so a 1.0.70 pin was unresolvable regardless (#77)

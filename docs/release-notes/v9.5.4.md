# BOSS v9.5.4

**Release Date:** 2026-08-29

Two changes, both about the application's own update. The banner at the top of the window now offers the same powers as the download center it could not reach - a Cancel while it downloads, a Cancel beside Install Now once it is staged, and a click that opens the dialog the bottom bar's progress item opens - and underneath, installing and discarding a staged update can no longer both proceed, which is what pressing Install and then Cancel used to do.

## Highlights

- **The more prominent surface was the weaker one.** The update banner showed progress and nothing else: no way to stop the download, and no way into `DownloadCenterDialog`, where the identical row already carried Cancel. Both banner states now open that dialog on click and carry their own Cancel (#279)
- **Install then Cancel gave the user neither.** Both operations checked the state and then acted with a real coroutine dispatch in between, so two buttons 8dp apart could both pass their guards: the discard deleted the artifact while the install was opening it, and the user lost the download *and* got an installation failure. `claimStagedUpdate` compare-and-sets out of the exact `ReadyToInstall` value, so the loser touches nothing (#280)
- **Two quick presses of Install Now meant two elevated installers.** The banner's button is a plain button, unlike the dialog's, which clears its action when it fires. The claim closes that for free: the second press is a no-op (#280)
- **The dialog was destroyed by the transition it exists to show.** Found in review of #279: held inside a `when` branch, an open download center vanished the moment a finished download moved `Downloading` to `ReadyToInstall` - at the exact instant its row gained an Install button (#279)

## Features

- **updater**: the downloading banner is clickable and opens `DownloadCenterDialog`, with a Cancel after the progress bar. The app update is one row in the same dialog rather than a surface of its own, matching the bottom bar's progress item. Cancel is a `TextButton`, like the other banners, and consumes its own press, so hitting it does not also open the dialog behind it (#279)
- **updater**: the ready-to-install banner gets the same two affordances - it opens the dialog on click, and Cancel sits beside Install Now, where before there was only Install Now while the dialog behind the bottom bar offered both for that same row (#279)
- **updater**: `UpdateHandle` gains `cancelDownload()` and `discardDownloadInBackground()`. They reach `UpdateManager` directly rather than through `DownloadCenter.cancel(APP_UPDATE_ID)`, even though the row carries the same action: that row exists only while `UpdateDownloadCenterMirror` is collecting, and a banner button whose behaviour depends on a collector being live is one that silently does nothing when it is not. Both surfaces end at the same idempotent manager method, so pressing Cancel in the banner and in the dialog is one cancel however they interleave (#279)

## Bug Fixes

- **updater**: a staged update has exactly one owner now. `installUpdate` set `Installing` only once it had been dispatched and `discardDownload` deleted the file *before* moving the state, so each was a check-then-act across a dispatch - and every caller reaches them through `launchInBackground`. Both callers go through `claimStagedUpdate`, which also fixes the direction a narrower patch misses: a discard that has already won refuses the install, not only the other way round. An ignored install request is logged with the state it found (#280)
- **updater**: the banner's download center survives the state changes it reports. `showDialog` was remembered inside each `when` branch, so `Downloading` to `ReadyToInstall` tore the subtree out and took the open dialog with it, and pressing Install did it again (to `Installing`, which draws no banner). It is hoisted above the `when` and rendered outside it, including for the states that draw no banner, since those still have a row (#279)
- **updater**: the two Cancels route differently and are pinned that way. `Downloading` reaches `cancelDownload`, `ReadyToInstall` reaches `discardDownload`. The two abandon different things and only one is free - cancelling stops bytes arriving, discarding deletes an artifact already on disk, which is why `discardDownload` suspends - and crossing them would be silent, since `cancelDownload` refuses anything that is not `Downloading`, so a ready-state Cancel wired to it would render enabled and do nothing (#279)
- **updater**: `UpdateHandleGuardTest` had three holes, one of them exactly where a new method lands. It scanned for `override fun`, so it never matched `override suspend fun checkForUpdates`; it bounded the last override's body at end of file, so that slice swallowed the `private fun guard(` declaration and any method appended at the bottom of the class inherited a free pass; and it let `release()` pass by that same accident while being genuinely exempt, so it could not tell "must not be guarded" from "forgot". Rewritten off reflection over `UpdateHandle`, asserting each member appears as `guard("<name>")` - which also catches a copy-pasted label - with `release` exempted by name and the `compareAndSet` reason written down (#279)

## Improvements

- **updater**: `cancelDownload` is deliberately not wrapped in `launchInBackground`. It only cancels the download job and does not suspend, so a dispatch would put the cancel behind a hop for no reason, and the point of the button is that the bar stops immediately (#279)
- **updater**: `claimStagedUpdate` takes its destination as a lambda rather than a value. The discard side computes its next state from `_updateInfo` - `Idle` unless there is genuinely a newer version, since after discarding a downgrade `UpdateAvailable` would put the older version in the banner - and evaluating that eagerly for a claim that then loses would read state the loser has no business acting on (#280)
- **updater**: `TooManyFunctions` on `WindowUpdateHandle` is suppressed in source next to the reason instead of in the baseline, as three other classes in the same area already do. One delegate per handle capability is the shape of that class rather than debt, and a baseline row reads as legacy. This release leaves `detekt-baseline.xml` untouched (#279)
- **tests**: `StagedUpdateClaimTest` covers the claim rather than driving `UpdateManager`, which builds its own `UpdateService` - a test through the real methods would need a seam that does not exist, or would reach a real installer. Five cases, including 200 rounds of eight concurrent claimants, all confirmed to fail against the pre-fix check-then-act shape (#280)
- **tests**: `UpdateBannerActionsTest` renders the banner in both states and asserts against the rendered tree, because what regresses in a banner is a button that stops being reachable - dropped from the layout, or placed where it does not draw - and neither shows up in a signature or a source grep. It uses `assertIsDisplayed` rather than a bare existence check, since being in the semantics tree is not the same as being on screen, and also asserts the progress label survives the new trailing button (the bar carries `weight(1f)`, so a wider action shrinks the bar rather than the text) (#279)
- **tests**: two Compose cases cover what a source scan cannot - the dialog survives `Downloading` to `ReadyToInstall`, and Cancel does not open it while the row does. Both confirmed to fail against the pre-fix shape (#279)
- **tests**: the update tests use the shared `testsupport.repoRoot()` rather than a third private copy of it (#279)

## Known Limitations

- **Only the banner's Cancel is new; nothing changed about what a cancel does.** `UpdateManager.cancelDownload` still refuses anything that is not `Downloading`, and a partially written artifact is cleaned up by the paths that already did so (#279)
- **The race was fixed in the state machine, not in the layout.** Install and Cancel are still 8dp apart on the banner and side by side in the download center's dialog; what changed is that only one of them can win (#280)
- **No test drives `installUpdate` and `discardDownload` themselves.** `UpdateManager` constructs its own `UpdateService`, so the invariant is pinned on `claimStagedUpdate` instead (#280)

# BOSS v9.4.31

**Release Date:** 2026-08-23

Five changes. macOS and Linux open on a new NVIDIA theme, the status strip breaks out the memory the active browser tab's renderer is holding, a plugin refused for a bad signature now offers to reinstall itself instead of silently ceasing to exist, the retired My Secrets panel is swept in favour of Secret Manager, and every bar's height stops being a literal in the file that draws it.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`. No dependency moved in this release.

## Highlights

- **macOS and Linux open on NVIDIA, green on pure black.** Every value is a literal out of nvidia.com's own stylesheet or composited from it, with the source named on each line: the surface ladder is the site's grey ramp over a genuinely pure black floor, the text ladder is its `.theme-dark` copy colors, and the status colors come from its category-tag ramp. `signalText` aliases `signal` because `#76b900` is the rare accent needing no twin - 8.7:1 on black as a glyph and 8.7:1 against the black type it carries as a fill, which is how the site uses it in both directions. `ok` is teal rather than green, since with a green signal a same-hue success chip is indistinguishable from a primary action. There is no light half and that is forced, not an omission: `#76b900` is 2.4:1 on white, and darkening it enough to clear the 3:1 floor stops it being the brand green, so Windows keeps Blueprint Light. Only users with no settings file at all are re-skinned, which is exactly "has never opened the theme picker" (#238)
- **The status strip breaks the browser out of the lump.** It showed one figure for all of BOSS, and on a real session that figure is dominated by one thing: measured live, Chromium renderers ranged from 99 MB to 1,637 MB, so a single heavy page can be most of the footprint with nothing on screen saying so. Now `1.9GB (195MB tab) · 66/128GB 0%`, nested rather than listed beside it, because the renderer is already summed into the footprint and side by side a reader could add the two and get a number that means nothing. Almost all of it already existed and had never been connected: `ActiveBrowserRegistry.activeIn` already answers which browser is on screen in a window, and `ProcessFootprint` already measured every Chromium process each sample and threw the per-pid detail away, so carrying it costs no extra `ps` call and no second cadence (#244)
- **A plugin refused for a bad signature no longer just disappears.** The refusal is correct and fail-closed, but it only reached an ERROR line in the log, so from the user's side the plugin stopped existing - and when the plugin is the Toolbox, the thing that vanishes *is* the way to reinstall it. It happened for real: a jar in `~/.boss/plugins` was replaced by hand while its `.jar.sig` still signed the previous bytes, the next launch logged `total=41, successful=38, failed=3`, and recovery needed a shell, since the Toolbox and its `plugins_list` / `plugin_enable` tools were the casualty. Hot reload is no way out either - it unloads before it loads, and there was nothing loaded to unload. Reinstalling from the store is the only remedy offered: no version is wrong so updating cannot help, and reverting would swap one unverifiable artifact for another (#243)
- **My Secrets is retired into Secret Manager, and the first-run default was pointing at the wrong half.** Both plugins read the same vault and both listed the caller's own secrets; Secret Manager now has two sections that partition it. `usersecretlist` was ESSENTIAL and a wizard default while `secretmanager` was PRODUCTIVITY and not, so a default install got the read-only half and never the half that can add a key - and since AI provider settings live in secret-manager, that install could not configure AI at all. Unlisting a store row does nothing for a machine that already has the plugin, which is every machine when the plugin was a first-run default, so `RetiredPlugins.sweep()` uninstalls it at startup, before anything can register a panel or an MCP tool that the replacement is already providing (#241)

## Features

- **theme**: NVIDIA is the sixth selectable host theme, and nothing outside `BossThemes.kt` was needed to make it work - the picker renders `BossThemes.all`, `AppThemeSettingsManager` persists any id, and the token accessors are getters onto `BossThemeController`, so the host and every in-process plugin re-skin live. terminal-tab's `ApplyHostThemeToTerminal` derives the terminal from the host tokens, so the shell follows with no plugin change: NVIDIA's ink is pure black and so is BossTerm's XTerm-derived `default` builtin, but the bridge's builtin match is restricted to `boss-` prefixed ids, so with no BOSS builtin at that floor it synthesizes from host tokens and the shell comes up green on black (#238)
- **status-bar**: the renderer figure is resolved per window in the bar rather than sampled into `MemoryMetrics`. It is drawn live and differs per window, so putting it in the snapshot would persist a meaningless number into all 10,000 retained history entries and every export, and would show one window's tab in the other window's strip. The per-pid map rides on `Reading` rather than beside it, so the sums and the detail cannot come from different samples - a torn read would surface as a tab figure larger than the total it sits inside. Verified against ground truth: the strip read 195MB for a pid the app resolved itself, `ps` agreed on that pid, and the pid was independently confirmed to be a `--type=renderer` process under the engine directory. With no browser on screen the parenthetical is correctly absent (#244)
- **plugins**: `PluginLoadGate.SignatureRejected` records the refusal so the existing remedy dialog explains it, and `PluginLoadRemedy.ReinstallFromStore` fetches what the store actually signed. Two things make the install different from the api-update path it borrows: the unload is lenient, because a refused plugin never loaded and `StoreVersionInstaller` treats a failed unload as fatal, which is the exact dead end this breaks; and the refused jar plus its stale `.sig` are deleted afterwards, or two jars would declare one plugin id and the startup scan could pick either (#243)
- **chrome**: `ChromeDimens` holds the seven bar metrics, `ChromeDensity` selects a set, and the bars read them through `BossChrome.dimens`. `WindowAppearanceSettings` already lets a user switch any bar off, which is the right answer to "I never want this bar" and no answer at all to the more common one on a 13" laptop, "all of them, but tighter". COMFORTABLE is today's values to the dp and is what `LocalChromeDimens` defaults to, so every bar renders exactly as it did; COMPACT and SPACIOUS are defined and unreachable until a setting selects them. The COMPACT numbers are floored by their content rather than guessed - `MIN_TAB_BAR` is 36 because a 34dp bar leaves the new-tab "+" a single dp on each side - and the title bar gets no compact value at all, because on macOS that row is what the traffic lights are drawn over and 26dp is already its floor (#240)
- **chrome**: `ChromeMetrics.mainPanelBudget` makes "the browser feels cramped" falsifiable. It derives the budget from the same two settings objects the scaffold gates its bars on, `WindowAppearanceSettings` and `FocusModeSettings`, so the measurement cannot drift from what is drawn without one of them changing, and it reports the steady state - a bar focus mode is clearing counts as absent, because the question is how much room the page gets while you are reading it. `ChromeBudgetReadout` renders nothing and logs the budget under `BOSS_CHROME_BUDGET=1` or `-Dboss.chrome.budget=1`, for the manual pass on a small screen no test can do; it sits in the scaffold rather than the bottom bar on purpose, since the configuration most worth measuring is the one with the bottom bar switched off (#240)

## Bug Fixes

- **browser**: the renderer pid refreshes on every main-frame commit rather than alongside JS injection, closing two ways it could go stale. Injection is skipped for `about:blank`, so a tab navigating from a heavy site to the dashboard kept pointing at the previous document's renderer and the strip went on charging that memory to a blank tab; and the capture was the last statement in a shared `try` after three injections, so any of them throwing left the previous value in place. Both are the "wrong number that looks right" the design is built around. Only the `Int` is ever kept, never the `Frame` or the `RenderProcess`: neither `renderProcess()` nor `pid()` carries a `checkNotClosed`, so a stale frame does not throw, it answers with the previous renderer's pid. The pid is cleared on `RenderProcessTerminated`, browser close and dispose, which also closes the pid-reuse hole, since Chromium recycles pids and a retained one would later charge another helper's memory to this tab (#244)
- **browser**: the pid is pushed, not pulled. Of the chain `mainFrame() -> renderProcess() -> pid()` only the first is IPC, so capturing at commit costs no round trip and leaves the reader a load safe to make from a Compose pass. Pulling instead would have put a blocking call on `PerformanceMonitor`'s sampling loop, where `syncCall` bounds what a dead browser throws but never how long a live-but-wedged one takes - one bad page could have frozen memory, CPU, GC and resource sampling for every window, indefinitely and silently (#244)
- **plugins**: the signature reinstall could delete the plugin's only jar. Passing `runningJarPath = null` also disabled the collision avoidance in `StoreVersionInstaller.targetFor`, which is guarded on that path being non-null, so the download target was `<pluginId>_<version>.jar` unconditionally - a name this same path writes. For a plugin installed from the store and then replaced by hand, the target resolved to *that file*, and since `activate` discards the target when the load fails, a failed repair deleted the plugin's only jar: `installed.json` then pointed at nothing, the next launch failed with not-found rather than a signature error, `loadGateFor` returned null, and no dialog was ever shown again. The silent disappearance this change removes, made permanent, under a failure message reading "Reinstall the plugin from the Toolbox" when it *is* the Toolbox (#243)
- **plugins**: remedies run through `KeyedDetachedJobs`, detached from the window and coalesced per plugin id. The dialog is driven from a window scope, so closing it mid-download aborted the install, and `.part` cleanup runs through `getOrElse`, which a `CancellationException` skips. The gate registry is a `StateFlow` and the host is per-window, so two windows each had a live button on the same gate. The store lookup is bounded at 6s rather than the client's 30, because the dialog does not render until it returns and an unreachable store would otherwise replace a silent failure with half a minute of nothing (#243)
- **plugins**: the retirement sweep no longer drops the `installed.json` row while a jar survives. `PluginArtifactCleanup.remove` only logs the delete result, which is right for the interactive uninstall and wrong here, because `DefaultPlugin.loadExternalPlugins` scans the same directory later in the *same launch* and installs every jar the manager does not know about - so a failed delete did not leak a file, it reinstalled the plugin in the session the user was just told it left, and every launch after that swept and announced again. `purgeJarsFor` now runs first and matches on the manifest id rather than the recorded path, since `jarPath` can be stale while a differently named jar for the same plugin is still there and artifact prefixes are prefixes of each other; it re-lists rather than trusting delete results, because a Windows lock makes `delete()` return false silently and an already-absent file returns false too (#241)
- **plugins**: the retired plugin is no longer *offered*. Unlisting the store row is a manual database action outside CI, so until it happens a user could install it, have the sweep remove it at the next launch, and install it again indefinitely. `RetiredPluginIds` is filtered wherever `NOT_USER_INSTALLABLE` is, with a test pinning it against `RetiredPlugins.ALL` so the two cannot drift (#241)
- **chrome**: the budget is charged for two pieces of drawn chrome it was omitting, which matters more than their size because these numbers are the baseline later work is measured against. Each icon strip draws a 1dp divider down its inner edge inside the same `AnimatedVisibility` that gates the strip, so the hairline comes and goes with it - the vertical side counted every one and the horizontal side counted none. And the main panel reserves a 4dp ring on both axes unconditionally, since `BossMainPanel` draws a 2dp border and insets its content by the same 2dp so a foreign native surface has nowhere to cover it from. So the shipped macOS figure is 146dp vertical / 86dp horizontal, not 142/80, and the floor this architecture can reach is 47dp rather than 43. The ring also becomes the single value its KDoc always claimed it was, moving to `ChromeDimens.panelBorderThickness` (#240)
- **chrome**: `mainPanelBudget` loses its `dimens` default. Once density is selectable, a defaulted Comfortable means "silently assume the user picked comfortable", and a caller who forgets the argument gets a plausible wrong answer with nothing to catch it. The readout flag reads a system property as well as the env var, with a blank env var falling through to the property rather than shadowing it - a bug `BrowserAnalytics.telemetryEnabledFrom` records this repo hitting for real - and it carries its `windowId`, since two windows produced two indistinguishable lines (#240)

## Improvements

- **theme**: `BossThemes.DEFAULT_ID` deliberately stays `blueprint` and is now no platform's first run, because it still answers two questions neither platform constant does: what a settings file saying `{}` means, and what `byId` falls back to for an unknown id. `{}` on disk is someone who chose Blueprint under the old `encodeDefaults = false` writer, so re-pointing `DEFAULT_ID` at nvidia to make it consistent would silently re-skin every one of them on all three platforms at once - a test fails if anyone tries. `ensureInitialized()` runs unconditionally in `main.kt` about a hundred lines before `application {}`, so the first frame is already correct and there is no flash of Blueprint on the platform that no longer ends there (#238)
- **plugins**: `PluginVersionGate` becomes `PluginLoadGate`, with `required` and `current` moving off the shared interface onto a `VersionFloor` sub-interface. The abstraction is about refusals, not versions - leaving those two up top would force any future variant to invent a pair of version strings for a dialog to print, which a signature mismatch has nothing to fill in. `remediesFor` splits into `signatureRemedies` and `versionFloorRemedies` behind a `RemedyOptions` parameter object, since the two kinds of refusal share nothing (#243)
- **plugins**: `RetiredPlugins.sweep()` fails closed at every step, deliberately the opposite of `satisfiesVersionFloor`'s own default. A wrong "yes" deletes the panel the user reads their shared credentials in, so a replacement that is absent, disabled, missing its jar, reporting a version that is unparseable or older than the release which absorbed the retired plugin, or that would be re-copied as a bundled or system plugin anyway, all mean "not yet" and wait for a launch that can prove otherwise. The version is parsed explicitly rather than through `satisfiesVersionFloor`, which returns true for anything `SemanticVersion` cannot parse - `dev`, `v1.2.17`, a trailing `-` - and that is exactly the locally built jar whose owner would lose both panels. The removal is announced once per sweep rather than once per retirement, because `showMessage` cancels the previous message and the sweep is one-shot, so a missed notice means a panel vanished with no explanation ever; `noticeFor` groups by replacement, since two retirements pointing at different replacements is the only case the function exists for (#241)
- **chrome**: `ChromeDimens` lives in composeApp rather than in `plugin-ui-core` beside `BossTheme.space`. Plugins never draw the title bar, the tab bar or the strips, and that module carries binary-compatibility constraints for dynamically loaded plugins that host layout tokens have no business touching. `ChromeMetricsTest` pins 146dp / 86.9% for the shipped macOS defaults, so growing the chrome now means changing an assertion and saying so, and Comfortable's individual values are pinned against the literals they replaced (#240)

## Known Limitations

- **The renderer figure is the renderer behind the tab, not the tab alone.** A renderer can serve several tabs - LITE caps at 4, ULTRA_LITE at 2, and same-site navigations reuse - and the bias runs both ways. On macOS and Windows a renderer's RSS includes the whole shared Chromium framework, so the figure overstates the page (Linux Pss divides shared pages honestly); against that, a page is not one process, since cross-origin iframes are their own renderers under site isolation and the GPU and network services hold page-attributable memory, so a heavy site with third-party embeds can materially under-state (#244)
- **COMPACT and SPACIOUS are defined and unreachable.** Nothing provides `LocalChromeDimens` yet, so this release changes no bar's size; the setting that selects a density arrives with the visible budget readout that belongs beside it. `BossPanelTopBar`, the update banner and split view are excluded from the budget on purpose - the panel header belongs to SidePanel and a main-panel browser tab never pays it, the banner is transient, and a single panel is the best case, so a real split is never better than reported (#240)
- **BossConsoleRust has no `nvidia` variant.** It mirrors these palettes and reads the same `~/.boss/app-theme-settings.json`, so `ThemeId::from_id` returns `None` there and that host falls back to Blueprint. The `{}` contract between the two is intact, since its `ThemeId::DEFAULT` still matches `DEFAULT_ID`; what diverges is first run and any explicitly stored `nvidia` (#238)
- **Removing the retired secrets plugin has no "already done" flag.** The sweep keys on the plugin being installed, and dropping the `installed.json` row is what makes the next launch a no-op. `sweep()` is `internal` and startup-only, because `PluginArtifactCleanup.remove` deletes a jar without unloading anything, which is safe only before any plugin has loaded (#241)

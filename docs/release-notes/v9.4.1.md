# BOSS v9.4.1

**Release Date:** 2026-08-05

The embedded browser moves to hardware rendering on macOS and Linux, joining Windows, and every Chromium engine tunable that had accumulated as an environment variable is now reachable from **Settings → Browser Engine**. Also: a new default theme that matches bossconsole.ai, out-of-process plugin children that no longer survive a Cmd+Q (434 orphaned JVMs holding 27 GB were found on one machine), and download links in these notes that actually resolve.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **macOS and Linux default to `HARDWARE_ACCELERATED` rendering.** macOS moves for idle power and memory rather than throughput: it already scored 47.9 on Speedometer 3.1, ahead of Chrome, so a Speedometer sweep there comes out flat and is the wrong instrument. The reading that matters came from a content-matched A/B over clean 94-sample idle windows - idle CPU 0.59 → 0.06 cores (~10x), RSS 3095 → 1974 MB (-1.1 GB, -36%), peak CPU -14%, peak RSS -25%. Both readings are true at once: off-screen is fast on macOS and expensive to sit idle in, and the fleet's complaints are about battery and RAM. Linux follows and remains the least-measured of the three. `BOSS_RENDERING_MODE=OFF_SCREEN` is still the escape hatch everywhere.
- **Nine engine tunables were environment-variable-only and unreachable from the app; four more switches were hardcoded on with no way off.** Settings now feed the *existing* `ConfigLoader` precedence chain by being published as system properties at startup, so one call in `main.kt` is the whole bridge: an environment variable still wins for a one-session override, settings now beat `local.properties`, and no read site had to learn that settings exist. Capability-granting keys deliberately bypass `ConfigLoader` - a DevTools port is full control of the browser profile with no prompt, so `local.properties` must not be able to enable it for every future run of a checkout.
- **A new default theme, Blueprint, matching the page BOSS is downloaded from.** The app shipped three themes and none looked like bossconsole.ai, so a user who downloaded from that page landed in an amber UI. Blueprint (electric blue on ink) and blueprint-light lift every value from the site's own stylesheet, with each line naming its source, and the site's hero mocks the app itself so the chrome ladder is the site's rather than an interpretation of it. Existing installs keep whatever they had.
- **Every host exit stranded the whole out-of-process plugin cohort, a clean Cmd+Q included.** The shutdown hook kills children by iterating `processRegistry.getAllProcesses()`, but plugin children were never in that map: `ProcessSpawner.spawn()` did not register, and the plugin spawner kept its handles in a private map of its own, so the hook iterated an empty list and killed nothing. A child's gRPC registration reached only the registry's separate manifest map - manifest-visible, process-invisible. 434 orphaned plugin JVMs holding 27 GB and 45k threads were found on one developer machine after 19 days of uptime, spanning four api releases.

## Features

- **theme**: add Blueprint and blueprint-light, and make Blueprint the default. Nothing beyond `BossThemes.kt` was needed to make it work - the picker renders `BossThemes.all`, `AppThemeSettingsManager` persists any id, and `BossColors` / `BossThemeColors` / `SettingsTheme` / `FileIcons` / `PanelScrollbarConfig` are all getters onto `BossThemeController`, so the host and every in-process plugin re-skin live. `byId()`'s fallback moves to Blueprint alongside `DEFAULT_ID`, since those two drifting apart would give a user with an unknown persisted id a different theme than a fresh install. No new tokens, so `ThemeToken` / `themeTokenColors` / `ui_protocol.proto` were untouched. `BossThemesRegistryTest` holds every palette to WCAG floors, and records a pre-existing defect rather than hiding it: Daylight's amber signal is 2.63:1 on its near-white floor, pinned in `SIGNAL_CONTRAST_DEBT` so a new theme cannot quietly join it (#129)
- **settings**: every Chromium engine flag in **Settings → Browser Engine** - rendering mode, extra switches, the sandbox opt-out, Skia Graphite, the renderer cap, prewarm, the top inset, the Skiko backend, the DevTools port. Every field is nullable and null means "no opinion", not false: a user who never opens this screen must get byte-identical engine options to before it existed, and a `Boolean` defaulting to false would instead have turned off flags that ship on (`--no-pings`, VA-API decode), so `SwitchToggles.from()` does that resolution once. The UI names the overriding variable per row and disables the control, because a dropdown that silently does nothing reads as broken. The effective command line is shown twice - active this session, recorded at engine creation rather than recomputed (a recomputation would start reporting a command line no running process ever had, under the heading "active"), and after the next restart, built by calling the engine's own `performanceSwitchesFor` so the preview cannot drift from the boot. Nothing applies live, so the screen offers a restart, gated on the settings differing from the ones the process booted with; the sandbox opt-out and the DevTools port are behind confirmations that state the exposure, while turning either back off is unconfirmed (#128)

## Bug Fixes

- **kernel**: reap out-of-process plugin children on host exit. Registration moved *into* `ProcessSpawner.spawn()` rather than left to one caller remembering it - all three spawn sites wanted it, and the original defect had exactly the shape of a forgotten call; mutation proved the first cut untestable, since deleting the lone `register()` left the whole suite green. `PLUGIN` is exempt from the global monitor (`PluginProcessMonitor` already owns plugin health, restart budget and in-process fallback, and supervising them twice would read a deliberately disabled plugin's clean exit as a crash and respawn it behind the operator), non-alive plugin entries are pruned so a crashed plugin stops being handed out by `getAllProcesses()`, and supervision stops before the hook reaps so the hook's own kills cannot be answered with a fresh generation. Three review rounds followed, one of which meant the PR did not fix the leak at all: `DefaultPlugin` built a *second* spawner reflectively via `getConstructor(String, File)`, a constructor this PR's third parameter had removed, so the lookup threw into a broad catch and out-of-process plugins stopped spawning entirely - ending the leak by turning the feature off. It now reuses `KernelBootstrap.processSpawner`, the only registry-wired instance, and `KernelReflectionContractTest` pins every reflective lookup because the compiler checks none of it. Exit cost no longer scales with the cohort: both reap loops did destroy / `waitFor(2s)` / `destroyForcibly` per process, so N plugins could add 2N seconds to a Cmd+Q and a hook cut off part-way stranded the tail; kills are issued first and waited against one shared deadline, IPC channel shutdown (up to 5s per child, serial, ahead of the budget meant to bound it) moved out of the kill path, and the remaining budget is divided so one hung child cannot starve the children behind it. Plus a prune that could evict a live replacement, `terminate()` unregistering before killing, and a respawn that could outlive the reap's snapshot (#131)
- **panels**: reserve and paint the active-panel border ring, so the browser cannot cover it. Reported from a live macOS hardware build: the selected panel's border was cut off everywhere the browser rendering area touched it. `Modifier.border` decorates existing bounds rather than adding to them, which is fine for a Compose-rendered child and not fine for a foreign native surface - under `HARDWARE_ACCELERATED` the browser is Chromium's own native window composited *above* the Compose scene, so Compose can neither draw over it nor clip it. The border now reserves its own ring, named once because the inset and the stroke must agree exactly, and the ring exists whether or not the panel is active (one that appeared on activation would reflow the page on every click). Reserving space without painting it then left the parent showing through as a white outline in every theme, since the split-view `Box` paints no background - filled with `BossTheme.colors.panel`, the same token the tab bar directly above it uses. Known and not fixed: the tab drag-and-drop drop-target highlight has the same root cause and needs a heavyweight overlay window (#128)
- **overlays**: stop the heavyweight overlay path from washing the whole screen, and re-assert transparency on realization. The New Tab dialog intermittently rendered a flat mid-grey over the entire window instead of the app dimmed behind it. Two defects on that path: both `HeavyweightPopup` and `HeavyweightModal` fell back to `rememberWindowState(placement = Maximized)` when they could not measure their parent, which sizes the overlay to the *screen* and takes a transparent undecorated window through the platform's own zoom path, where macOS can bring it up opaque - and neither logged anything, so an intermittent report had no signal at all. Shared resolution moved to `OverlayWindowBounds.kt` with an explicit screen rect, a warning naming which condition failed, and bounds keyed on the parent window (previously unkeyed, so an overlay staying in composition across opens could place itself over the wrong window). The instrumentation then disproved that as the cause - the fallback never fired - and the colour identified the real layer: a uniform mid-grey is 40% black over an opaque *light* background, so the scrim was compositing over the overlay window's own background rather than over the app, meaning `transparent = true` had not taken. On macOS that has to be applied before the window is ordered on screen, and these windows are created once and never resized, so losing the race leaves them opaque for life. Both overlays now check after realization and set it if needed - check-then-set with a warning, not an unconditional assignment, so a wrong diagnosis stays silent and that silence is the signal (#128)
- **theme**: split `signal` into fill and text. The Blueprint PR asserted "never a hairline of signal alone" in three places while ~90 call sites drew signal *as* text: `Text("Update Now", color = signal, 13.sp)` in the updater went 8.6:1 → 3.7:1 for every user who never picked a theme. The root cause is a missing slot rather than the palette - a saturated accent cannot be both dark enough to carry white content as a fill and light enough to read as a glyph on ink, which amber could do and is why one token sufficed until Blueprint. `BossColorScheme` gains `signalText`, held to 4.5:1, distinct only in the two themes that need it (blueprint #88A9FF at 8.1:1, from the site's own link-blue family; daylight #95580A at 5.3:1). 63 sites swept by walking back to the enclosing call rather than by pattern, since `contentColor` on a filled button means `onSignal` and `Divider(color=)` is not text; progress indicators, surface fills and dividers stay on `signal` as graphical objects. Contrast floors now assert against `panel` and `raised` as well as `ink` - the dark themes' panel and raised are *lighter* than ink, so an ink-only check flattered every ratio, and this immediately caught a second pre-existing Daylight defect (warn at 2.88:1), fixed by darkening rather than by growing the exemption list (#129)
- **release notes**: repair the published download tables. They were fabricated: v9.4.0 listed two macOS DMGs when one Universal DMG ships, `BOSS-9.4.0-windows-x64.msi` when the asset is `BOSS-9.4.0.msi`, and a Debian-style `boss_9.4.0-1_amd64.deb` when it is `BOSS-9.4.0-amd64.deb`. Every one of those five links 404s, and Windows ARM64 plus all four Linux RPM and JAR builds were missing entirely - not one release either: 9.2.65, 9.2.64, 9.2.63 and 9.2.61 each listed 5 links against 8 or 9 real installers, and only 9.2.62 was correct. The same table reaches users twice more, because `sync-release` pushes these notes into `app_releases.release_notes` and the in-app update dialog rendered the identical 404s. All five are regenerated from each release's real asset list and every link verified to resolve, with 9.2.63 correctly getting 8 rows rather than 9 (#130)
- **bench**: find the benchmark window by executable path, not by process name. `raise_and_maximize()` matched "first process whose name is BOSS", and the operator's own BOSS is almost always running under that same name - caught by doing it, when a probe script repositioned the operator's window to 1400x870 while the benchmark build sat unraised behind it. The second half is worse for being invisible: an unraised window means Chromium throttles `requestAnimationFrame`, which Speedometer paces on, so every arm would have scored throttled garbage while the sweep looked like it worked. Targeting the launched pid does not work either, since the macOS bundle's binary re-execs, so windows are resolved by enumerating accessibility processes named BOSS and keeping the one whose executable runs from this worktree; no match warns and touches nothing (#128)

## Improvements

- **browser**: default Skia Graphite on under hardware rendering. Graphite is Chromium's Metal-native raster backend and is default-on in stable Chrome on Apple Silicon, so it is the better backend where it works; the reason it was opt-in here was specific rather than cautious - verified live on JxBrowser 9.3.0 / Chromium 150 / Apple Silicon, Graphite blanked the content area, with pages, navigation, titles and favicons all fine and frames never reaching the Compose surface. That failure is in the OSR frame-export path, which `HARDWARE_ACCELERATED` does not use, which is what makes this reachable at all. So the default follows the *rendering mode* rather than flipping globally, and the second half is the half that protects someone: off-screen is the documented escape hatch from hardware, so defaulting Graphite on there would hand exactly those users a blank browser and make the escape hatch worse than the thing they escaped. The Settings toggle stores the explicit boolean instead of collapsing "off" to null, since with a mode-dependent default "off" is a real choice that has to survive a switch back. Not measured - a correctness change on the strength of Chrome's own default, with no throughput or power claim attached (#128)
- **browser**: mode-aware pinch-to-zoom, which hardware rendering would otherwise have broken silently. The gate read `pointerOverBrowserView`, set from Compose `PointerEventType.Enter`/`Exit` - and under hardware the browser is not a component in the Compose scene at all, so macOS delivers mouse movement to that foreign window, Compose never reports Enter, and the flag stays false for the life of the tab with every pinch rejected behind a debug line. Hardware now decides by geometry, converting the AWT pointer into the *content pane* rather than the window (via the window would be wrong by the title-bar height, enough to zoom while pointing above the view and refuse near its bottom edge), and an undeterminable position refuses the pinch. Review then caught the comparison mixing units - `boundsInWindow()` is device pixels and the AWT pointer is logical units, which coincide only at density 1.0, so the gate was correct on an unscaled external monitor and wrong by 2x on a Retina panel, zooming a browser the pointer was not over. Extracted as a pure `pointerInsideBounds(boundsPx, pointerLogical, density)`, table-tested at 1.0/1.25/1.5/2.0, with density read from composition since it changes when a window moves between displays (#128)
- **bench**: port the paired rendering A/B and the perf recorder to macOS and Linux, so the platforms that just changed default can check it on their own hardware. Two harnesses, because macOS and Windows are different questions: Windows lost throughput to off-screen and macOS does not, so a flat Speedometer result on macOS is the *expected* result rather than evidence against the change, and `UNIX.md` says so where someone about to run it will read it. `SpeedometerCdp.java` is reused from `win/` as-is, since one implementation reading the score from Speedometer's own DOM is what makes the numbers comparable; the interleaving discipline carries over intact, including the median of per-pair ratios rather than a ratio of medians, with the win count printed alongside. Platform parts were verified by running them: the bundle's *inner* binary is launched rather than `open -a`, because `open` hands the launch to launchd, which does not inherit the shell environment, so every `BOSS_*` variable would be dropped and each arm would measure the platform default while claiming otherwise. Two findings documented - do not run the recorder from a BossTerm tab inside the BOSS being measured (that shell is a descendant, which turned a machine idling at ~0.4 cores into a 9.64-core sample), and Python's `statistics.median` averages the two middle values where the PowerShell version takes the upper (#128)
- **release**: generate the download table instead of hand-writing it. The auto-generated release body listed nine bare filenames in a "Package" column with no links at all, while the curated notes were told in prose to include "a download table with platform links" - two bodies for the same release, written twice by different authors, agreeing only by luck. `scripts/release-download-table.sh` emits that section once for both producers, each row carrying the versioned asset plus a link that always resolves to the newest one. Rows are filtered by what was actually published, because `create-release` needs only macos-arm64, linux-amd64 and windows to succeed, and linking bare filenames merely gave a reader nothing to click while linking them turns a failed ARM64 build into four live 404s; drops are reported on stderr, since "the ARM64 build failed" must not read as "this release has no ARM64", and a filter that matches nothing lists everything and says why. On a pre-release the "Always latest" links resolved to the newest *stable* - a downgrade presented next to the pre-release's own assets as though it were newer - so `--prerelease` threads through, read from `github.event.release.prerelease` rather than inferred from a dash in the tag string (a `release_type=beta` dispatch on 9.4.0 yields a dashless tag that *is* a prerelease, and `sync-release.yml` already compensates for that case).

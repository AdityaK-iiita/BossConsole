# BOSS v9.4.0

**Release Date:** 2026-08-04

Repair release for the JxBrowser 9.4.0 engine that v9.3.0 shipped. Four rounds of browser fixes make the startup guard, the engine resolver and the packaged app agree on one version rule - the 9.3.0 bump alone would have left every existing install throwing `UnsatisfiedLinkError` before the download that repairs it was ever reached - and the engine download UI now says which version it is fetching and offers the restart a staged install needs.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.3.0. The bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`, and the updater reads that from the incoming DMG before it quits the app.

## Highlights

- **The 9.4.0 engine bump broke the browser for every existing install, and the guard that would have caught it ran too late.** `main.kt` booted the engine twice - `prewarmInBackground()` at line 431 and `PasskeyPlatformInit.initialize()` at 474 - before `isChromiumInstalled()` at 536. JxBrowser resolves its native toolkit under `Versions/<VersionInfo.chromiumVersion()>`, a value baked into the jar, so bumping the jar made every on-disk engine stale and both early boots threw before the guard, and the download that repairs it, was reached. While jar and engine were both 9.3.0 the early boots succeeded and the ordering never showed. The guard now leads.
- **The guard and the resolver were checking different directories.** `isChromiumInstalled()` inspects only `~/.boss/boss-chromium` while `getChromiumDir()` prefers a bundled engine from the app image - so a passing guard proved nothing about the engine that actually boots, and a mismatched *bundled* engine could not be repaired at all, because the download writes to the cache the resolver was ignoring. The version check moved into the *choice* rather than being a veto after it: a candidate wins only if it is well-formed and carries the required Chromium build.
- **Off macOS, the bundled engine was never version-checked.** `version.txt` was written only by `ChromiumAutoDownloader`, and the bundled engine was checked via the macOS-only framework probe - so on Windows and Linux a mis-built release would ship a stale bundled engine that wins first priority, is never questioned, and cannot be repaired. All five bundling sites in `release.yml` and all three in `release-lite.yml` now stamp `version.txt`, and a CI shell guard asserts they keep doing so.
- **The engine download blocks the whole app for several hundred MB without saying what it is fetching**, and a staged install sat in `boss-chromium.pending` doing nothing until the next launch, announced only as a muted note. The status line now names the version in all three phases, and a successful stage of the default engine offers a confirmed "Restart BOSS" button.

## Bug Fixes

- **browser**: check the engine before anything boots it, and fail legibly when it mismatches. The guard moves above both early boots - `promotePendingInstall` has to lead anyway, since it renames the engine directory, which is unsafe once a running engine holds files inside it - pre-warm is skipped when a download is needed, and `CrossDeviceBrowserManager` stops booting a multi-second Chromium engine in its constructor on the pre-UI path (all three consumers read it as a null check and return OS-derived answers either way, so it is lazy and `suspend` now, reached only when a passkey flow actually opens the embedded browser). Ordering is a convention a future edit can break silently, so `FluckEngine` also preflights and throws a message naming both versions rather than letting JxBrowser surface a path with no cause. Three review rounds followed: the legible message reached only the log, because `initializationError` is assigned in exactly one place and the preflight throws before it, so the user saw "window not ready" - arguably less useful than the `UnsatisfiedLinkError` it replaced; the pre-warm never fired in the session that just downloaded an engine, restoring the cold start it exists to remove; `isChromiumInstalled`'s execute-bit check had never fired, resolving `<dir>/<name>/Contents/MacOS/BOSS` when the branding workflow writes the bundle name without its `.app` suffix; `@Volatile` on the two engine references the constructor move stopped safely publishing; and the engine path moved out of a message that `classifyError` substring-matches for "host"/"connect"/"license", which would have reported a stale engine as a network or licensing failure (#120)
- **browser**: make the startup guard and the engine resolver agree. `resolveEngineDir()` now applies the same priority order and version check the boot will, and `hasUsableEngine()` drives both the download prompt and the pre-warm; `isChromiumInstalled()` is left alone, since "does the cache hold the right engine?" is still the right input for deciding what to *download*. Review found the first cut removed the cross-platform version check entirely - `frameworkVersionsDir` returns null off macOS by design, so the predicate collapsed to "executable exists" and a user carrying a 9.3.0 cache into a 9.4.0 build would pass the guard, pre-warm against the stale engine and get the `UnsatisfiedLinkError` back with no prompt, on two of three platforms. Round 2 found two more: `redownloadWouldRepeat` keyed on `version.txt` alone, so a *corrupt* cache - partial extraction, or a macOS binary that lost its execute bit - was told to restart for a download that provably would never fire again, states that repaired themselves before this PR; and the pre-warm fired in the branch where no usable engine exists, a guaranteed-futile boot. The three-way decision is extracted as `engineStartupAction(hasUsableEngine, cacheHealthy)`, `cacheHealthy` is read once and threaded through so resolver and decision cannot disagree, and the diagnosis reports a present-but-stale engine specifically instead of "BOSS-branded Chromium not found". Fixes #121 (#122)
- **browser, release**: stamp the bundled engine so one version rule covers both candidates. All five bundling sites in `release.yml` (macOS, Linux x64/arm64, Windows x64 via POSIX shell, Windows arm64 via PowerShell) and all three in `release-lite.yml` write `version.txt` with the `JXBROWSER_VERSION` they fetched - the same stamp the downloader writes - and `installedVersion()` generalises to `installedVersionAt(dir)` so one reader serves both. The bundled check stays deliberately more lenient than the cache's: app images built before this change carry no stamp, and refusing those would make every such user re-download for nothing, so "can't tell" fails open and what it catches is a stamp that is present and wrong. The PowerShell site uses `File.WriteAllText` rather than `Set-Content`, which prepends a UTF-8 BOM that a plain string compare fails on - U+FEFF is not `Character.isWhitespace`, so `trim()` does not remove it. Later rounds caught the stamp failing open silently on an unset `JXBROWSER_VERSION` (an empty `version.txt` maps to null and the resolver lets it through, reverting to unguarded behaviour on a fully green release build), the PowerShell extraction degrading URL, availability flag and stamp together with no `else`, and the diagnosis going blind to exactly the engine this change rejects - `engineLocations()` is now separate and unfiltered, because selection drops rejected engines but a diagnosis has to describe them. `scripts/test/test-bundled-chromium-stamp.sh` pins the invariant in the Shell Script Tests job, since release workflows only run on publish; its first version was worthless and the mutation check proved it, matching the string `version.txt` that also appears in the comment above each stamp. Closes #123 (#124)
- **browser**: name the engine version while downloading, and offer the restart a staged install needs. The download dialog blocks the entire app for a several-hundred-MB fetch triggered by an engine/jar mismatch, so "which version, and why now" is the first question it raises; the status line answers it in all three phases. A staged engine does nothing until `promotePendingInstall` swaps it in at startup, so the muted "restart to apply" note read like a silent failure - a successful stage now offers a "Restart BOSS" action. Self-review corrected a warning written without checking (restart runs the JVM shutdown hook and `LastSessionCoordinator.saveOnProcessExit`, so tabs are restored, not lost - the warning would have deterred people from the one action that makes their download take effect). Review then found the button offering to discard the engine it had just staged: `updateSettings` runs `withoutUnusablePin()`, so staging a non-default engine persists no pin and the next launch re-downloads the default, putting a quit plus a several-hundred-MB re-download one click away. It is gated on `appliesOnRestart` now, routed through the repo's `ConfirmationDialog` with `isDestructive`, modelled as a sealed `StagedInstallOutcome` rather than two booleans that had to agree, and seeded from `getPendingChromiumDir()` so closing Settings no longer loses the pending state (#125)

## Improvements

- **docs, deps**: record the ktor 3.5.x outcome and its coupling to supabase. The comment above `ktor` described a 3.4.3 pin and asked whoever moved it to write down what broke; #113 moved it to 3.5.1 and nothing broke on any of the three OSes, so the note read as though the bump were still untried. It now records what is durable instead: the plugin-isolation claim *and* the loophole it omitted (`io.ktor` is absent from `defaultSharedPackages`, but a plugin can opt in via manifest `sharedPackages` - checked across `boss_plugins`, only `boss-plugin-api` declares any, for its own package), and the coupling that is easy to miss - supabase-kt depends on ktor directly (3.6.0 → 3.4.3, 3.7.0 → 3.5.1), so bumping supabase alone leaves the host's direct ktor deps behind while `ktor-server-core`/`cio` resolve forward transitively, mixing ktor artifacts on one classpath. Comment-only (#126)

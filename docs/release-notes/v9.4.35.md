# BOSS v9.4.35

**Release Date:** 2026-08-26

Three changes, and the largest of them is that a download is finally something you can see and stop. Every transfer the host started - a panel's update badge, "Install Store Version", a missing dependency, the application's own update - now reports into one `DownloadCenter` that the bottom bar renders and a dialog opens, with a Cancel that deletes what it wrote rather than a button that only looks like one. The Toolbox joins Settings in the host's action row, drawing the plugin's own icon rather than a second one invented here, and on macOS the traffic-light clearance moves onto the column that is actually under the buttons. One dependency moved: `boss-plugin-api` 1.0.85.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **One download center, in the bottom bar, with a dialog behind it.** The only visible download progress in the app belonged to the Toolbox plugin: a status-bar widget fed by its own tracker. Everything the *host* downloaded was invisible, uncancellable and unclickable, including the app update, which had a banner and nothing else. `DownloadCenter` is now the one place a transfer is reported; clicking the bottom-bar item opens the rows with their own controls - Cancel while it is still bytes, Install for a downloaded app update, and Minimize, which leaves everything running. The plugin-facing half is `DownloadCenterProvider` (api 1.0.85), so the Toolbox reports into the same center rather than drawing a second widget (#257)
- **Cancel had to be made real rather than cosmetic.** A cancelled download deletes what it wrote, because `PluginUpdateBridge` streams onto a version-named jar in the plugin directory and a partial file there is one the next directory scan tries to load. `PluginRepository.downloadPlugin` takes an `onProgress` callback, since `getDownloadProgress` is a flow that only exists once a download has started and a caller wanting a bar had to race it into existence. And the jar swap itself is **not** cancellable: withdrawing the button was necessary and not sufficient, so both swap paths and the dependency installer's promotion run under `NonCancellable` (#257)
- **The Toolbox sits beside Settings in the host's action row.** One list feeds four places - the top bar, the right rail, the vertical bar's foot and the floating cluster - so the button appears in all of them, directly after Settings. That position is the point: both are "go and configure the app", where Search and the tools launcher open something. It renders the plugin's own `SidebarItem`, looked up by panel id and clicked through `handleSidebarItemClick`, so an icon changed in a plugin release follows it here with no host change (#265)
- **macOS: the traffic-light clearance goes on the column that is actually under it.** The left columns run strip, then an open plugin panel, then the vertical tab bar - so with a panel open the *panel* is what the 78dp light box covers and the bar behind it is out of reach. The old rule insetted the columns as a group, which put the panel's header under the buttons while the bar kept a 28dp gap it did not need. The inset is asked per column by offset now, and an open panel counts toward the width, which is the honest way to make the full-width title row rarer (#264)

## Features

- **downloads**: the bottom-bar status item shows the active transfer and opens the center. It composes nothing at all when there is no transfer - a widget with an empty label and a zero-progress bar would satisfy "no text saying Downloading" and still shove every status-bar item beside it sideways each time a download finished (#257)
- **downloads**: three contract points api 1.0.85 gained are honoured. `owner` on every row (the prefix that opened it, null for the host's own), so a plugin can tell its row for `com.foo` from the host's row for `com.foo`, which the id alone cannot once the prefix is stripped for its owner. `detail(id, text)`, so a row's text can follow its steps. And a non-finite fraction is indeterminate rather than clamped: `coerceIn` propagates NaN, and NaN is what `bytes / length` gives when the length is absent or zero, so it reached the bar (#257)
- **plugins**: the Toolbox button is addressed by **panel** id, not plugin id - the plugin kept the id `plugin-manager` when it was renamed to Toolbox, and a plugin id would find nothing and report no error. Opening goes through the same entry point the sidebar icons and the tools launcher use, so a custom `onClick` the plugin registered is honoured here too. It is a slot rather than a callback, exactly like the tools launcher: the scaffold owns the item and the click, and the four hosts render what they are handed (#265)

## Bug Fixes

- **updater**: `DesktopUpdateService` caught `CancellationException` in its general clause, which turned the user's own Cancel into "Download failed" and left a half-written installer staged (#257)
- **plugins**: pressing Cancel on a plugin update left the truncated jar in the plugin directory for the next launch to load. `PluginUpdateManager.downloadUpdate` caught `Exception` - which includes `CancellationException` - and returned `Result.failure`; `updatePlugin` then returned rather than throwing, and `RemotePluginRepository`'s `runCatching` swallowed it one layer lower still, so the guard this change added for its own headline hazard could never run, and the Toolbox was told "update failed: StandaloneCoroutine was cancelled". Both layers rethrow now, and the cleanup also runs on the plain FAILURE branch, which covers a dropped connection: the same truncated scannable jar with no cancellation in sight (#257)
- **plugins**: `PluginUpdateBridge` discarded the downloaded jar on **any** cancellation, including one arriving after the load had succeeded, so the next launch met an `installed.json` row pointing at nothing. The discard is gated on whether the swap had started (#257)
- **downloads**: `begin()` could hand ownership of one row to two callers. `update` is a compare-and-set retry loop and `created` was set rather than assigned, so a caller that built the row and lost the CAS still believed it owned one, and both `finally` blocks then deleted each other's rows (#257)
- **downloads**: the dialog reopened by itself. The status item's early return disposes the dialog's subtree in the same recomposition that empties the list, so its self-close effect never dispatched and `showDialog` stayed true - the next download popped the dialog with nobody clicking (#257)
- **downloads**: Cancel vanished when pressed. The button was rendered on the action's presence and the press clears it; it is rendered on the phase now, which is what its own KDoc claimed (#257)
- **updater**: the app-update row's Cancel went dead on a second download. `begin` leaves an existing row alone, so ReadyToInstall then another version then Downloading kept the ready-state actions: a Cancel calling `discardDownload()` that early-returns, rendering enabled and doing nothing. Each state asserts its own actions now (#257)
- **updater**: Install could be double-clicked into two elevated installs, because the action was withdrawn only when the state reached Installing - a background hop and a recomposition away, while the row still read "Ready to install". Both actions are read-and-cleared in one update. Same argument this change makes for `NonCancellable`: the disabled button is UI state (#257)
- **updater**: a specific-version download was labelled with whatever the last **check** found, because only the check path published `_updateInfo` - so downgrading to 9.4.20 showed a row reading "BOSS v9.4.34". It is published before the download starts now, and restoring "available" is gated on the version actually being newer, or discarding a downgrade would put an older version in the banner as an update (#257)
- **downloads**: two host operations on one plugin id share a row, since the host keys plugin work by `pluginId`, and the joiner's Cancel used to be dropped silently - so the row's Cancel abandoned whichever operation got there first. The row withdraws Cancel instead of offering one that stops the wrong thing (#257)
- **downloads**: a plugin's view of transfers could freeze permanently. The provider was first constructed per plugin **load**, each installing an eager collector on a scope nothing cancels, so every hot reload left one behind; caching per plugin id then captured the scope it was first asked with, and `DefaultPlugin` is per **window** with a `dispose()` that cancels `pluginScope` - so closing the window a plugin happened to resolve through froze that plugin's view for the rest of the process. The views live on a scope the center owns. Making it `Unconfined` was not cosmetic: `.value` was briefly stale after a write, which is exactly the question `.value` gets asked ("is this one busy?") and the reason these views are eager rather than `WhileSubscribed` (#257)
- **updater**: the app download deleted its partial on cancellation but not on failure, the same asymmetry closed on the plugin side (#257)
- **updater**: `discardPartialDownload` could not report the failure it exists for - `delete()` returns false rather than throwing on a Windows lock, so `runCatching` never fired. Absence is the postcondition now (#257)
- **plugins**: update prompts stopped going stale. `PluginUpdateRegistry.reconcile` drops a badge once the plugin is no longer on the version the check found it at, so updating from the Toolbox or from its toast clears the badge and the "Update Available" alert the host would otherwise still offer (#257)
- **macos**: an open left plugin panel had the lights on its header while the tab bar behind it kept a gap it did not need. `columnInset(offsetFromLeft)` clears only a column that starts inside the box and `leftColumnOffsets` works out where each one begins - two pure functions and one table of cases (#264)

## Security

- **downloads**: transfer ids were one unnamespaced space shared by the host and every plugin, so a plugin could fabricate an app-update row, or withdraw the user's Cancel from a host transfer by phasing it to INSTALLING. Ids from a plugin are prefixed with its plugin id in `TrackingPluginContext`, the only layer that knows who is calling, and stripped on the way back so a plugin still matches its own work by the id it passed (#257)
- **downloads**: `DiscardDownloadContainmentTest` covers the one security-relevant guard that was untested - a path outside staging, a traversal, a symlink pointing out, the directory itself, and an absent path (#257)

## Improvements

- **downloads**: the update mirror allocated a fresh cancel lambda per progress tick, so `begin`'s "another operation joined" check - reference identity - fired on every tick, withdrew Cancel, had `setActions` put it straight back, and rebuilt the list three times per tick. A guard that fires constantly for the one caller it does not mean is no guard, which is why the case it exists for went untested for a round. Actions are allocated once (#257)
- **downloads**: the delegate's "presence test" forced its own lazy provider, since reading the property is what forces it - one unread instance with its own collector per window. The center is process-wide, so there is nothing to test for and nothing to read (#257)
- **plugins**: the Toolbox button uses the puzzle piece, the mark this app already uses for a plugin, rather than a toolbox glyph. A second tool-shaped icon beside the launcher's app grid would read as two doors to the same room, and a glyph chosen in the host goes stale the moment the plugin changes its own (#265)
- **layout**: `FOCUS_QUICK_ACTION_COUNT` goes to four with the right rail's height reserve and the floating cluster's clip bound, which is a hard ceiling rather than an estimate - content past it is cut off. Three existing tests caught that arithmetic before the build did, and two of them were repeating the number 3 rather than reading the constant they exist to protect, so they agreed with themselves while disagreeing with what the rail renders (#265)
- **tests**: four fakes implement `PluginRepository` in `plugin-repository` and `plugin-updater`, and their test source sets are not compiled by `:composeApp:desktopTest` - so the `onProgress` signature change compiled everywhere it was being looked at and nowhere else. `PluginUpdateCancellationTest`, `DownloadCenterProviderImplTest`, `UpdateDownloadCenterMirrorTest` and `DownloadCenterStatusItemTest` pin the new behaviour, each checked by putting the defect back. The cancel-after-`onInstalling` test needed a real suspension point in the fake to mean anything: the first version passed with `NonCancellable` removed, which made it worthless (#257)
- **tests**: a layout test's first stand-in for the Toolbox button was an empty lambda, which drew nothing, so the section measured one row short of the reserve and failed for a reason that had nothing to do with the arithmetic it exists to check. It renders a real button now (#265)

## Dependencies

- `boss-plugin-api` 1.0.84 to 1.0.85, a superset: `DownloadCenterProvider` and `PluginContext.downloadCenterProvider` are new declarations with a null default, so nothing a host module or an installed plugin resolves has been withdrawn (#257)

## Known Limitations

- **The macOS title row still appears and disappears during a resize drag.** Removing that fallback was tried on this branch and reverted: when no left column is wide enough to hold the 78dp box the buttons land on the **pane**, and nothing there can be moved out from under them - a strip's chips can be indented, but the active pane's focus outline is drawn behind the buttons either way, so the pane loses the top-left corner of its own boundary. 26dp to protect one corner is expensive, and it is still the only answer that keeps the buttons off the pane (#264)
- **A Toolbox that is not registered at all leaves the rail over-reserving by one row.** No button is drawn, which is the harmless direction; gating the count on the plugin's presence would make it dynamic, and the rail's reserve is a compile-time constant (#265)
- **A row shared by two host operations on one plugin id offers no Cancel.** Withdrawing it is right - the alternative stopped whichever operation got there first - but the user cannot cancel either one until they finish (#257)

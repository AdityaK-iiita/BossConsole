# BOSS v9.2.65

**Release Date:** 2026-08-02

Windows-weighted release. The browser defaults to hardware-accelerated rendering there - measured at +33%, within 4% of Edge on the same Chromium generation - favicons update again after the first save, and two crashes that took the whole app down are now contained: a plugin layout bug and a right-click in an OAuth popup. Also lands a least-privilege plugin-publishing role and makes the per-tool MCP kill-switch fail closed.

## Highlights

- **`RenderingMode.OFF_SCREEN`, not Chromium switches, was the Windows performance gap.** The fluck browser scored 18.1 on Speedometer 3.1 against Edge's 24.7 on Chromium 150; six switch sets were measured and none helped (four made it worse). Windows now defaults to `HARDWARE_ACCELERATED` at 23.8 - 96% of Edge - with macOS and Linux deliberately left on `OFF_SCREEN`.
- **A bookmarks-plugin layout bug ended the app, and nothing in the host caught it.** Crash attribution works by finding a plugin frame on the stack, which cannot work for the layout phases: the plugin's composables have already returned, having emitted only `LayoutNode`s, so the stack holds no plugin frame at all. Attribution returned null, the host treated it as its own fault, and Compose's default handler disposed the window. Out-of-process isolation would not have helped - `BridgedPanelComponent` still composes and lays out in the kernel process.
- **Right-clicking an OAuth or payment popup could crash the EDT.** `SuggestionsPopup` - JxBrowser's own spell-check menu - resolves its position from `getLocationOnScreen()` inside an `invokeLater`, and a popup that closes *itself* when the flow completes is exactly the window where a click lands on a disposed component.
- **The MCP kill-switch is the only access control an admin operator actually has, and both of its persistence paths failed open.** `permitted()` short-circuits on `isAdmin`, so for the common single-user desktop case the user-disabled set is all that remains - and a corrupt `mcp-disabled-tools.json` silently re-enabled every tool, while a failed write applied the change in memory anyway and lost it at the next launch.

## Features

- **rbac**: add a least-privilege `boss_plugin_admin` role and enforce `plugins.create` on every Plugin Store publish route. Publishing previously required `boss_admin`, which also carries `role.read`/`create`/`assign`, `secret.read` and the whole `plugins.admin.*` moderation family; the new role can create plugins and publish versions of the ones it owns, and nothing else. The publish endpoints themselves checked only "are you authenticated", so any signed-in user could claim an unused pluginId and mint a publish-scoped API key - enforcement is therefore a tightening, and the migration backfills the role to everyone already in `plugins.author_id` or holding a live `plugin_api_keys` row. `plugins.admin.publish` is deliberately not reused: its RLS policy has no author scoping, so it authorizes updates to *any* plugin and stays moderation-only. A new narrow `user_has_permission(uuid, text)` SECURITY DEFINER probe (granted to `service_role` only) lets the edge function ask the database about an API key's owner - a key carries no JWT to read claims from - which is what makes a role revocation stop a key immediately rather than at expiry, and it fails closed on a DB error unlike the `validateDeclaredPermissions` beside it, which fails open on purpose. `getAuthenticatedUser` now returns a discriminated outcome, so a valid key with the wrong scope is `403` rather than the `401` it used to collapse into; creating an API key requires `api_key.create`, while listing and revoking deliberately do not (revocation is a safety valve, and gating it behind a permission the user just lost would strand their keys). Client-side, `PluginStoreApiKeyProviderImpl` tested a literal `plugin_admin` role no migration ever created - a dead branch that collapsed the check to admin-only - and now keys off `api_key.create`. 13 new edge-function tests, 22 new pgTAP assertions, 4 new host gate tests, plus two source-level wiring guards, because deleting `requiredPermission` from one of the five handlers leaves every behavioural test green and still type-checks (verified by mutation) (#93)

## Bug Fixes

- **browser**: favicons stopped updating on Windows because `File.renameTo` will not overwrite. `FaviconCache.saveFavicon` encodes the PNG to a sibling temp file to check it against the 100 KB limit, then promotes it with `renameTo` - POSIX `rename(2)` replaces the target, so macOS and Linux were fine, while Win32 `MoveFile` fails with `ERROR_ALREADY_EXISTS`. A URL's favicon could be written exactly once ever, and since `~/.boss/cache/favicon-cache` outlives the process, "once" had usually already happened in an earlier run. The failure was worse than "no update": `saveFavicon` returned null, which reached `updateFaviconCacheKey(null)` and **reset the tab to the default globe**, discarding a perfectly good cached icon. A new `File.atomicMoveFrom` (beside `atomicWriteText`, which now shares it - its delete-then-retry Windows fallback left a window with no file at all) uses `Files.move` with `REPLACE_EXISTING`, preferring `ATOMIC_MOVE` and dropping it where the filesystem cannot honour it; `saveFavicon` no longer reports "no icon" when it merely cannot improve on the cache, returning the existing key instead - stale beats blank - and cleans up the temp file on every failure path. `AtomicFileWriteTest` and `FaviconCacheTest` pin both halves (the tests were validated by swapping `Files.move` back to `renameTo`, which fails 3 of 5 with the exact message the app logs - and can only fail on Windows, which is why PR CI's `build-test (windows-latest)` leg is where they earn their place). Follow-up #96 tracks the same `renameTo` bug in `FileSystemService.renameFile`, which offers an explicit `overwrite` flag and discards the boolean, so it reports success on every platform (#95)
- **browser**: stop popup windows crashing the EDT on right-click, fixing BossConsole-Releases#17. Two browsers still used JxBrowser's built-in menu, both hosted in a Swing `JFrame` - the `window.open`-with-bounds popups and the duplicate of that flow in `BrowserFunctions`. Installing any `ShowContextMenuCallback` suppresses the built-in menu, which is what removes the crash; rather than leave popup windows with no menu at all, `installPopupWindowChrome` substitutes a small Cut/Copy/Paste/Select All menu and pairs it structurally with the page-click dismiss handler that a heavyweight surface needs (Chromium consumes the press before AWT sees it). Enablement derives purely from the click target rather than four `isCommandEnabled` round-trips into the Chromium process, the target frame comes from `params.frame()` rather than `focusedFrame()` (OAuth and payment pages are routinely iframed), and the clipboard probe runs only when it could change the answer and off Chromium's wait path - a Windows clipboard open is a retry-with-sleep loop. The `try` block now contains only `params` reads, so a partial read degrades to a minimal menu instead of to no menu at all; `tell.close()` is wrapped here and at both sites in `BrowserHandleImpl.setupContextMenuHandler`, since a throw from a `finally` on a JxBrowser thread is the same uncaught-crash class this change exists to remove; and each install is guarded independently so a failed menu install cannot take down the OAuth window it was meant to protect. Tab browsers were checked and are unaffected. #91 and #92 track the browsers that still get no context-menu setup and converging the tab menu onto `EditorCommand` (#89)
- **plugins**: contain and recover from plugin render-phase crashes. `PluginRenderBoundary` wraps plugin content in a `Layout` guarding measure, placement and draw, attributing by position rather than by stack inspection - but testing showed it does not catch the reported crash, which arrives via `MeasureAndLayoutDelegate.remeasureIfNeeded` with Compose re-measuring the plugin's node straight from its dirty list and the boundary not on the stack. `PluginRenderRecovery` is what fixes it, attributing by which panels are mounted: rebuild on the first failure; suspect one plugin if that does not take; release a suspect proven innocent and try the next; stop when all are ruled out. Quarantine goes through `recordRenderFault`, which shows the fallback **without closing tabs** - quarantining everything at once closed the user's terminal and browser tabs. Unattributed exceptions are no longer fatal: `decideWindowExceptionRoute` (extracted from `main.kt` so it can be tested) escalates uncontainable errors ahead of the circuit breaker, so an `OutOfMemoryError` never triggers a repaint of every window under heap exhaustion, and `CrashHandler.recordContained` keeps the crash report without the terminal dialog so host-side render bugs stay visible. `PluginErrorFallback` was written against Material 3 in a Material 2 app - every colour fell through to M3 defaults - and now uses `BossThemeColors`. Verified live against the pre-fix plugin with four plugins mounted: one rebuild, culprit quarantined on the first guess, zero innocent suspects, zero tabs closed, app alive (#88)
- **plugins**: post-merge follow-ups on render recovery, three of them real defects in shipped code. `recordContained` wrote to `_pendingCrashReport`, which has no consumers - so the telemetry it existed to preserve was still lost, and worse, that single-valued slot belongs to the interactive dialog, so a contained fault arriving while the user typed notes would replace the report and Submit would send the wrong crash. Contained reports now go to `~/.boss/crash-reports` (owner-only, off the EDT on a daemon thread, at most one per signature per session with recurrences on a log curve) and the dialog's slot is left alone. The containment budget raced the narrowing loop and lost: faults from a repainting subtree arrive ~16ms apart, so with three panels mounted the fourth fault escalated and disposed the window - the app dying before the culprit was found, after quarantining two innocents. Mount tracking was not reference-counted, and since `PluginErrorBoundary` is per surface, closing one of a plugin's two boundaries removed it from the mounted set while it was still rendering, after which the real culprit could never be suspected and the incident ended `Unexplained` - leaving exactly the permanently broken window the class exists to prevent. It is now a `LinkedHashMap` of counts, which also fixes recency. And the panel path still used `recordCrash`, which closes the plugin's registered tab keyed by plugin id alone - so a render fault in a side panel would close that plugin's unrelated main tab. Two further review rounds corrected the budget fix itself: clearing the whole burst on progress made `Escalate` unreachable with two or more panels mounted, so a genuinely corrupt scene could spin forever (it now removes only the fault just recorded); and `RenderRecoverySeamTest` was re-implementing the record → recover → progress pairing instead of calling it, so the wiring it is named for was unasserted - the pairing moved into `noteRecoveryOutcome`, which both the handler and the test now drive, verified non-vacuous in both directions (#90)
- **mcp**: make the per-tool kill-switch fail closed on both I/O paths. On the read side, a file that existed but did not parse returned `emptySet()` behind a single WARN - identical to "file absent" - so a corrupt or truncated `mcp-disabled-tools.json` silently re-enabled every tool. Unparseable is now a different answer from absent: it salvages every legible tool name from the damaged text (truncation, the realistic corruption, leaves nearly all readable) and keeps withholding them so the rebuild cannot drop the operator's list, copies the damaged bytes to `<name>.corrupt` before anything can overwrite them, withholds every registered tool while still *reporting* them through `disabledToolNames` - the shipped Toolbox tab derives `permissionDenied = !on && !userDisabled`, so withholding by emptying both flows would grey every switch out, blame missing permissions, and leave the fail-closed state with no in-app way out - and logs at ERROR with a sticky fault. Turning any tool back on rebuilds the file from the withheld set, clearing the degraded state without widening exposure beyond the tool that was clicked. On the write side, `setToolEnabled` mutated the in-memory set and then swallowed a failed write with a WARN, applying the change anyway, so a tool switched off came back on at the next launch with no signal. It is now write-through under one invariant - nothing the persisted record withholds may stop being withheld on the strength of a change nobody recorded - giving three reported outcomes: `APPLIED_SESSION_ONLY`, `REFUSED`, and `NO_CHANGE` (which the earlier two-state logic reported as a session-only disable, i.e. told the operator a fully exposed tool was off). Faults are published on `McpToolRegistryImpl.killSwitchFault` and rendered by the status bar for as long as the state is degraded, since a transient toast cannot carry a fail-closed state and one raised at startup would be gone before anyone looked; `onFault` runs after the mutation lock is released and never from the constructor. New `McpKillSwitchPersistenceTest` (13 tests) plus the existing 28 in `McpToolRegistryCoreTest`. What cannot be fixed: when the path itself is unwritable no code can make the decision durable - what changed is that the operator is told now instead of at the next launch (#97, closes #85)

## Improvements

- **perf(windows)**: default the browser to `HARDWARE_ACCELERATED` on Windows - 23.8 on Speedometer 3.1 against `OFF_SCREEN`'s 17.9 and Edge's 24.7, same-session medians on a quiet machine, with the 17.9 control reproducing the operator's independently reported 18.1 and so calibrating the harness. Six Chromium switch sets were measured and none helped (`--disable-gpu-compositing` 11.0, `--disable-gpu` 11.0, `--use-angle=gl` 11.5, `--disable-gpu-vsync --disable-frame-rate-limit` 9.56, `--force-device-scale-factor=1` 4.85 - half speed - against an 11.5/10.2 control), and three other plausible causes were refuted by direct measurement rather than by trying flags blind: the renderer is not priority- or EcoQoS-throttled, not on a software rasterizer, and its idle `rAF` and `setTimeout(0)` match Edge exactly. What remained is that the renderer burns 0.26 of a core during a run while the machine sits at 0.65 - blocked waiting on frames, not computing - which is why the deficit was uniform across all 206 metrics while raw arithmetic was only 1.17x off. macOS and Linux keep `OFF_SCREEN` deliberately: macOS measures 47.9 there because it can share the off-screen surface with the GPU and would lose the two-finger swipe-back gesture under HARDWARE, and Linux is unmeasured and does not inherit a Windows finding. HARDWARE's UI consequences are handled by fixes ported from BossConsoleLite: `OverlayConfig` + `HeavyweightPopup`/`HeavyweightModal`/`SwingTooltip` route context menus, modals and hover tooltips into native windows because a lightweight Compose `Popup` renders *behind* the browser surface (`NewTabDialog` moves onto `OverlayModal` at the source); `Ctrl`/`Cmd+R` reloads the focused browser directly rather than through the focused window, which is unset when the native surface holds focus; and the browser surface is retained across composition exit, since tearing down a heavyweight GPU surface on every tab switch paints blank on the way back - gated on HARDWARE so OFF_SCREEN keeps today's exact lifecycle. Everything overlay-related is gated on `OverlayConfig.useHeavyweightPopups`, false under OFF_SCREEN, so macOS and Linux execute the path they do today. Adds `--no-pings` and `--disable-domain-reliability`, plus opt-in `BOSS_RENDERER_PROCESS_LIMIT` and `BOSS_SKIKO_RENDER_API`; Lite's engine switch block was deliberately *not* taken wholesale, since it still carries `--no-sandbox` unconditionally and `--disable-dev-shm-usage` on desktop Linux where shared memory *is* the OSR frame transport. Escape hatch with no rebuild: `BOSS_RENDERING_MODE=OFF_SCREEN`. Also adds a JDK-only Windows Speedometer harness that drives the fluck tab over CDP via the opt-in `BOSS_BROWSER_REMOTE_DEBUGGING_PORT`, so the embedded browser is measurable like any other rather than read off a screenshot (#87)
- **ci**: auto-release new JxBrowser engines. A scheduled watcher (four-hourly, against TeamDev's roughly monthly cadence) resolves the latest JxBrowser version from Maven metadata, checks the branded-Chromium releases repo for a complete asset set against `.github/chromium-required-assets.txt`, and dispatches the branding build when one is missing - with `workflow_dispatch` inputs for forcing a version and for a dry run that validates without dispatching. The resolver is shared verbatim between the watcher and the branding workflow's preflight, a resolver failure files (and de-duplicates) a "watcher is broken" issue rather than passing silently, and `scripts/test/test-jxbrowser-autorelease.sh` covers it in CI (#94)
- **benchmarks**: add a Speedometer 3.1 cross-browser comparison and the dependency-free harness that produced it - fluck 47.9, Comet 46.2, Chrome 35.5, ChatGPT Atlas 34.6, Safari 29.9, Firefox 22.5 (median of 3 interleaved runs on one macOS machine). Three runners cover what each browser exposes: CDP for Chrome/Comet, WebDriver via geckodriver for Firefox, and CPU-idle detection plus screen capture for Safari and Atlas, which expose no automation endpoint; the fluck browser is driven through the host's MCP tools since it is a tab inside BOSS, and its tab must stay active because a hidden tab throttles the `requestAnimationFrame` Speedometer measures with. The main finding is that engine version does not explain the spread - Comet and Atlas ship the same Chromium build family yet differ by 34%, with Chrome 151 between them, and the gap is concentrated in DOM-mutation suites and absent in canvas and navigation (a field-trials explanation was tested and refuted). Review caught that the headline fluck-vs-Comet claim was the one measurement *not* produced by the interleaved protocol; re-run as a paired experiment (+4.0%, +1.8%, +6.4%) the margin is the same size as each browser's own spread and 3/3 is p=0.125 under a sign test, so the report now states the two are tied within measurement precision and keeps only the claim the data supports - both sit ~30% above Chrome and Atlas. Conditions are documented rather than cleaned up: 800–1300% ambient CPU, Safari on a real profile against fresh Chromium profiles, 40% run-to-run spread on Firefox, and four harness bugs that each produced plausible wrong numbers (#83)
- **docs**: correct and scope the infrastructure-plugin entries in the README. The Kubernetes entry mentioned Helm releases while the MCP examples row named no `helm_*` tool despite the plugin exposing more of them than `k8s_*` ones; more substantially, "destructive actions require confirmation" sat in a row whose subject is MCP tools, but that dialog lives in `DockerPanelViewModel` - the sidebar path a *human* clicks, which an agent calling `docker_rm` never sees. The README now states per-tool what is permission-gated versus merely mutating, names `k8s_exec` and `k8s_apply` explicitly as arbitrary in-cluster execution that routes around both Secret-redaction mechanisms, splits the ungated set by real reach versus local-only, and leads with the distinction that matters on a single-user desktop: `permitted()` short-circuits on `isAdmin`, so for an admin operator the permission-gated list stops nothing and the kill-switch is the only control that always applies. Also narrows two over-broad claims - published ports bind to `127.0.0.1` only on the `docker run` path, while ports in your own compose file bind as written, and "never writes to your kubeconfig" does not extend to `helm_repo_add`, which writes the shared `~/.config/helm/repositories.yaml` - pins what was audited and when, drops per-plugin tool counts that describe an independently released repo with no CI here to catch drift, and files the plugin-side gaps as tracked issues. Two parsing traps are recorded because the first nearly shipped a false claim in the other direction: splitting on `McpToolDefinition(` misses every tool built by the `withRbac` factory, which is exactly the gated set (#84)
- **mcp**: `admin does not bypass the disabled set` now pins the invariant the docs lean on. The existing coverage missed the combination - the two admin tests never touched the disabled set and the disabled-set test ran logged-out and non-admin - and the test was validated rather than trusted: folding `applyExposed`'s two conjuncts into an early `if (isAdmin) true` makes it the *only* failure in the class (#84)
- **ci**: run the plugin-store edge function's type check and tests. The Edge Functions workflow had a single job pinned to `working-directory: supabase/functions/passkey`, so its `find . -name '*.ts'` type check and its `deno test` never left that directory and the plugin-store function had no CI at all, despite the workflow already triggering on `supabase/functions/**` - which mattered most for the two wiring guards that exist precisely because a dropped route gate leaves every behavioural test green. Added as a sibling job rather than by widening the passkey one, which is deliberately scoped to the WebAuthn surface (#93)

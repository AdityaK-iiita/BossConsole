# BOSS v9.4.10

**Release Date:** 2026-08-15

A Windows and dialogs release. Updating on Windows now brings BOSS back afterwards, every window wears the BOSS icon instead of the JDK coffee cup, dialog cards are the width they were designed to be, and one legacy-shaped dependency row can no longer fail a whole plugin install.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **Installing an update on Windows relaunches BOSS.** It used to work and then simply end: BOSS quit, msiexec ran, and nothing came back. The macOS helper script has always finished with `open "<app>"` and the Linux one with `nohup /opt/boss/bin/BOSS &`; the Windows one finished with `del "%~f0"`, and there was nothing to relaunch with either, since `getCurrentApplicationPath` only resolved a macOS `.app` bundle. Note the helper is generated by the *old* running app, so the relaunch first appears on the update after the one that ships this (#174)
- **Every window but the main one showed the Java icon on Windows.** The Settings window wore the JDK's coffee cup in its title bar, taskbar button and Alt-Tab card, and so did every other window BOSS opens. jpackage puts `boss_icon.ico` on the launcher `.exe`, but that icon never reaches a live AWT window, and exactly one of the fifteen window sites in the repo passed an icon. macOS reads the `.app` bundle and Linux the `.desktop` file, which is why neither platform ever showed it (#176)
- **The Confirm Logout dialog rendered as a band across the whole window.** `BossDialog`'s contract is an intrinsically-sized card, and the two paths punish a filling card differently: the lightweight path caps content at the platform default width, so a `fillMaxWidth()` card looks plausible there, while the heavyweight path used by the main window measures it inside a full-window scrim and ignores that cap (#175)
- **Installing Flow failed on every shipped build** with "Tool not found in repository" for a row that is present and valid. `plugin_versions.dependencies` is free-form JSONB holding two shapes for one concept, and a required non-nullable `versionRange` - a field nobody reads - hard-failed the decode of the entire plugin detail response (#175)

## Bug Fixes

- **windows**: `windowsLauncherPathFor` resolves the launcher from `jpackage.app-path` first, then a walk up from the running jar for a sibling `BOSS.exe`, while BOSS is still running, because after msiexec there is no process left to ask. The walk must find an `app\` or `runtime\` marker jpackage emits: above `<install>` for a per-user install the ancestors are all user-writable, and the result goes straight to `start`. An unresolvable path is not fatal - it installs without relaunching, which is exactly what Windows did before (#174)
- **windows**: msiexec exit codes 3010 and 1641 now count as success. `/norestart` makes msiexec report 3010 rather than 0 whenever a file was in use, which is routine when replacing a running app's directory, so `if %ERRORLEVEL% NEQ 0` called a completed install a failure and handed the user an installer they did not need. The raw code survives the mapping and is echoed when it differs, since 3010 also means the relaunch can bring back a partially-updated install (#174)
- **windows**: `cmd /c start /b "<script>"` never ran the helper for an account whose name has a space. ProcessBuilder quotes any argument containing one, and `start` takes its first quoted token as a window *title* - no install, no relaunch, nothing in the log, for exactly the users most likely to have an awkward path. The empty title argument is now passed, and the command construction moved to a pure `updaterLaunchCommand` so the shape is pinned by a test (#174)
- **windows**: every `timeout /t N /nobreak` in the update script was failing outright. `launchScript` starts the helper with ProcessBuilder, so stdin is a pipe, and `timeout` refuses to run under redirected input - the waits never happened, the quit poll was a hot loop hammering tasklist, and three errors went into the one log anybody diagnosing a failed update would read. Now `ping -n N 127.0.0.1 >NUL` (#174)
- **windows**: the script is written CRLF. cmd.exe parses a batch file by seeking byte offsets that assume CRLF, so a `goto` into a label misbehaves in an LF-only file by jumping to the wrong place rather than by failing, and the failure branch now needs a `goto` (#174)
- **dialogs**: `LogoutConfirmationDialog` is a fixed 400.dp house card, the width `ConfirmationDialog` and `BossAlertDialog` already use, taking its colours from the `BossTheme` tokens rather than raw Material 2. `CrossDeviceAuthenticationDialog` is 480.dp for its two-line instruction copy, and `ProjectSelectionDialog` loses a redundant full-size centering Box - both paths already center the content, so that was a scrim inside the scrim (#175)
- **dialogs**: seven call sites declaring a width above the 580.dp platform cap now pass `usePlatformDefaultWidth = false`. They were quietly squeezed on the lightweight path only; `ShortcutTestDialog` is the one that mattered, asking for 900.dp and living in the Settings window, which always takes the clamped path (#175)
- **plugin-store**: `DependencyInfo.versionRange` defaults to `""` instead of being required. `ignoreUnknownKeys` forgives the extra `version` and `optional` keys a manifest-written row carries, but a missing required field is still a hard error thrown while decoding the whole detail response, so one legacy-shaped entry failed `getPlugin` for the entire plugin. Empty rather than nullable because the same type is the body of `PublishVersionRequest` and the server declares `versionRange` as `z.string()` (#175)
- **plugin-store**: a repository that cannot answer is no longer reported as a plugin that does not exist. `PluginRepositoryManager.getPlugin` flattened every repository's `Result` with `getOrNull()`, so the decode exception was destroyed before the wizard saw it. `success(null)` now means every repository was asked and none had it, while a repository that threw yields `failure(PluginLookupException)` - but only when nothing was found, so one broken repository still cannot hide a plugin another can serve (#175)
- **plugin-store**: the same swallow is fixed on every path that shared it. `PluginStoreVersionBridge` only appeared to draw the distinction - `RemotePluginRepository.getPlugin` returns `Result.failure` rather than throwing, so `runCatching` always succeeded, `result.isFailure` was dead code and every failure fell through to "not published", which is what the Toolbox reported for Flow 1.0.14. `StoreMissingDependencyInstaller` had it twice, and `PluginRepositoryManager.downloadPlugin` turned the new `PluginLookupException` straight back into `PluginNotFoundException` one method along from the fix. `checkForUpdates` deliberately does not propagate: it is a batch over every installed plugin, and failing all of it because one lookup broke would hide updates that are available (#175)
- **panel**: the sidebar header's trailing controls sit on the right edge again. The title carried `weight(1f, fill = false)` and a Spacer beside it carried `weight(1f)`, so the two split the free space 1:1 - and because the title does not fill its share, the half it left over was laid out *after* Minimize and the kebab. Measured in a 420dp bar, a short title pushed Minimize 170dp clear of the edge (#173)
- **panel**: the build tag clips instead of wrapping at narrow widths. Grouping it with the title reversed the measurement priority - it is now measured against what the trailing controls leave - and `PluginBuildTag` set neither `maxLines` nor `softWrap`, so a starved pill went from 13dp tall to 28dp, exactly filling the bar's hard height. The band is reachable, since `BossResizablePanel` floors a panel at 2% of its parent or 20dp (#173)
- **panel**: the overflow menu no longer offers a dead row. Both build rows were gated on the build being tagged, but the click is `onBuildTagClick`, which `SidePanel` leaves null when the panel has no resolvable window. They are now gated on the action existing, and go together, since a row named as an imperative that silently does nothing is a worse failure than no row at all (#173)

## Features

- **panel**: the overflow menu offers "Install Store Version" for a plugin running a DEBUG or HOT build, on the same action the tag itself performs. The version row above it already carried that action, but it reads as a statement of fact, so the only discoverable way back to the released build was guessing that either that line or a 10sp pill was clickable (#173)
- **windows**: `ai.rever.boss.window.WindowIcon` is the single source for window branding - one ImageIO decode of `/boss_icon.png`, exposed as `BossWindowIcon.painter` for the ten Compose `Window`/`DialogWindow` sites and as a pre-scaled 16..256 list for the five raw Swing frames (the crash dialog, the fullscreen browser frame and overlay, and the two browser popups). The Compose sites take the list too, through `ApplyBossWindowIcon`, since the 16px title-bar case is what motivated the list; on a 150%-scaled display Windows asks for 24x24 and 48x48 and both are exact entries, so no resampling happens at all (#176)
- **windows**: `DefaultWindowIcon.install()` is the net under windows BOSS does not create itself - JxBrowser's own Swing dialogs, JFileChooser, a frame opened by a plugin. It brands only frames whose `iconImages` are still empty, so an explicit icon is never overwritten, and it sits below the headless exits in `main()`: `--unregister-protocol` and the single-instance deep-link forward both exit without ever showing a window, and neither should be made to initialise the AWT toolkit first (#176)

## Improvements

- **windows**: icon downscaling halves progressively (256, 128, 64, 32, then the target) so the last step is always under 2x. A single bicubic 256 to 16 jump samples far too few source pixels (#176)
- **plugin-store**: `PluginLookupException` carries a deliberately short message and keeps the real error as its cause. That message reaches the wizard's failure list, and a kotlinx malformed-input error appends the entire offending document - `PluginInstallService` logs the cause at ERROR and reports the short message, and says "not found" only when the plugin genuinely is not there. `addSuppressed` filters by identity, since two repositories surfacing one Throwable instance made `first.addSuppressed(first)` throw and replace the diagnosis with an `IllegalArgumentException` about suppression (#175)
- **updater**: the resolved launcher path is masked in the debug log through `WindowsProtocolCleanup.maskUserPath` - a per-user install puts the Windows account name in it (#174)
- **theme**: the logout dialog's destructive button is white-on-red again. `textPrimary` is `#131820` in the Daylight scheme, so it put near-black text on a red button in that theme while every other destructive button is white (#175)
- **menus**: `ContextMenuItem` carries a leading icon through the native path. The comment claiming an NSMenu item is "a label and an enabled flag, nothing more" was stale - `isNativeRepresentable` rejects only trailing icons and non-representable submenus, so a leading icon keeps the native path and is rasterised by `collectIcons()` (#173)
- **tests**: three convention guards hold the next change to this, all modelled on the same premise - nothing in the diff looks wrong, and whether the author sees the bug depends on which platform or which window they use. `WindowIconConventionTest` requires branding within a 40-line lookahead of every window opener, per call site rather than per file, so one branded site cannot immunise a file with three; `DialogCardWidthConventionTest` requires a width before any fill; and `BossPanelTopBarLayoutTest` asserts against a laid-out screen, since the panel header's model was correct throughout that bug and only measurement could see it. The Windows update script is verified by executing the real generated bytes for all three installer outcomes (0, 3010, 1603) with only msiexec and `start` stubbed (#173, #174, #175, #176)

# BOSS v9.4.32

**Release Date:** 2026-08-24

Two changes, and one of them is the window. Tabs move to a vertical bar down the leading edge, there is now exactly one of those bars per window rather than one per split pane, and both that bar and a hidden top bar become the defaults on every platform; alongside it, the chrome metrics added in v9.4.31 stop being measurement-only and are enforced against the bars that draw them.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.1 engine declares `LSMinimumSystemVersion 13.0`. No dependency moved in this release.

## Highlights

- **Tabs run down the left, and that is the default everywhere.** Tab titles in BOSS are file names and page titles, and `SHRINK_TO_FIT` already squeezed them to a 36dp favicon once a panel held a dozen; a vertical bar trades width for a list that scrolls instead of shrinking. Settings gains a global Tab Bar Position (Top | Left) with a width setting, a collapse-to-icon-rail chevron, a hover-reveal drawer and auto-collapse below a narrow-*panel* threshold (a split can leave one panel at 300dp inside a 2000dp window, so window width is the wrong input). Windows, Linux and macOS all default to Left with the top bar hidden, and nothing here is platform-keyed - the only platform-specific appearance default left is the title bar, which really does differ. **Changing the constants alone would have done almost nothing**, because the settings manager writes the whole object on every save, so every existing file names both values explicitly and would have kept them for ever; the file gains a `settingsVersion` and a migration instead, the same shape as `WorkspaceSettingsMigrations`. The step moves a file sitting on exactly what every previous build shipped and leaves any other combination alone, so someone who hid the top bar but kept top tabs keeps both (#248)
- **A split no longer grows a second tab bar.** Each `SplitNode.Panel` owns a `BossTabsComponent` and each panel drew its own bar, so a two-way split showed two of them - in Left position, two ~200dp columns side by side eating a third of the window with nowhere to see what was open. The nesting is unchanged (Window → Split → Panel → Tabs, and a pane still owns its tab stack); what a pane no longer owns is a bar to draw them in. `SplitViewPanel` draws one bar and splices each pane's rows into a single `LazyColumn`, with per-pane group keys, one hoisted scroll-to-active that watches the pane being worked in, and only the active group wearing the amber marker. Each group opens with a header that says which pane it is twice over: a small filled-rectangle diagram of the split, and a word ("Left", "Top right", or a number when a pane touches no useful edge), both computed from the panes' *measured* rectangles so they stay right for any arrangement and follow a divider as it is dragged. One pane renders exactly as before, with no rule and no header (#248)
- **Panes you are not looking at collapse, and there are three ways back into them.** Four panes with five tabs each is twenty rows, nineteen of them about somewhere the user is not. A background pane now costs its header, a row of favicons for its tabs, and nothing else; the *active* pane is always open, because collapsing the one place someone is switching between was all cost and no saving. Opening another is sticky rather than expand-while-hovered - the obvious reading collapses the group the instant the pointer moves down onto the rows it just revealed - so hovering a header chooses which pane is open and that choice survives until another is hovered or the pointer leaves the bar. Each pane also carries a 24dp favicon strip across its own top, with a "+" and a right-click menu, and the foot of the bar holds a clickable split map: the one place in BOSS where a pane is a thing you can point at rather than the region you are already inside, so rename, close, split, and double-click-to-zoom all live there (#248)
- **Switching workspaces asks whether to keep the old one running.** It always kept it, silently, and nothing could stop one afterwards - preserved state was released only when a workspace was *deleted*. Switch between five in a session and all five stay live, each holding real tab components, which for browser tabs means live Chromium on a runtime where a native OOM is an instant crash rather than a graceful one. The switch now asks, with a "Don't ask again" that Settings → Workspaces can take back, and it is not asked when the answer cannot matter (a first switch, or one back onto the workspace already showing). Dismissing cancels the switch rather than guessing, because the two buttons throw away different things and neither is a safe default for Escape. Closing clears the old tree's tabs, since applying the next workspace over the top drops the reference and disposes nothing - which is the memory this exists to free (#248)

## Features

- **tabs**: the sidebar is sectioned, Arc-style. Pinned tabs are **always the first N of a panel**, and that invariant is the design rather than an implementation detail: a `Set<String>` of pinned ids would make the drawn order differ from the model order, which means translating every index in the system - the reorder arithmetic, the drag bounds keyed by `actualIndex`, the MRU cycle, `closeTabsToRight`, the positional shortcuts. Keeping them at the front means drawn order *is* model order, none of that translation exists to get wrong, and persistence collapses to one integer per panel instead of a flag per tab. It needs maintaining in exactly two places, because every close funnels through `removeTab` and every reorder through `moveTab`; `pinTab`/`unpinTab` deliberately do not go through `moveTab`, which infers pinned-ness from where a drag landed - right for a drag, wrong when the user has said which they want. Dragging across the separator pins or unpins, which falls out of the invariant as `toIndex < pinnedCount` rather than being a special case. Sections appear only once something is pinned (#248)
- **tabs**: a Favorites shelf sits above everything else in the bar, as an icon-only grid. Icon-only is the point rather than a shortcut - these are the few places someone goes constantly, recognised by favicon long before a title would be read, and a grid costs four rows' height instead of twenty - with titles in the tooltip. Opening one routes through the *workspace* converter rather than a second `TabConfig` → `TabInfo` mapping, because a bookmark stores exactly the `TabConfig` a workspace does and a private copy would be a second mapping to keep in step with every new tab type. **It is the bookmarks plugin's surface, not the host's**: `BookmarkAPIAccess` returns null for everything when that plugin is absent, so the section offers to install it through the same prompt the install-time dependency flow uses, marked `userInitiated` so a previously dismissed offer still answers a click. Dropping a tab on the shelf files a bookmark, the one drop in the bar that does not move the tab (#248)
- **tabs**: the collapsed rail shows favicons instead of dots. A dot said "a tab is here" and nothing else, so finding one meant hovering along the rail reading tooltips - on the one layout where the labels have already been taken away. The chips are larger there than anywhere else, because on the rail the mark *is* the tab rather than sitting beside a title; `TabFaviconChip` grew an optional context menu for the same reason, since collapsing takes away the labels and not the actions. A pinned tab says so in both shapes: a glyph on a full row (always drawn, unlike the close, because an indicator you have to hover for cannot answer "which of these are pinned" at a glance), and position before a short rule on a 20dp chip that has no room for one (#248)
- **panel**: double-clicking a pane in the split map shows it alone. Zoom *hides* panes rather than closing them - the split tree is untouched and the zoomed pane is rendered directly rather than through it, so exiting restores the arrangement with nothing having to remember it, and every pane's tabs go on existing, which is what lets the one window bar keep listing them all. It follows the active pane rather than pinning one, or clicking a tab in another pane's group would appear to do nothing. The way out is the map itself, which wears the signal border, dims and says "Exit Full Screen": it already draws what you are going back to, and unlike a floating button it needs no `OverlayCorner`, because sidebar chrome has nothing composited above it (#248)
- **workspace**: the workspace menu marks every workspace that is running, not just the one on screen. Two separate reasons the old mark was wrong: a single window runs several workspaces at once, since `preserveCurrentState` keeps the whole split tree with live `BossTabsComponent`s in it; and `currentWorkspace` is one value on a manager every window shares, so with two windows on different workspaces both buttons marked whichever loaded last. "Which workspaces are running" is therefore a set *per window*, and the window is the only thing that knows it - its own preserved keys plus the one it is showing. Three states now: filled dot for the one on screen here, outlined for one running somewhere, nothing for one that is not running. Registered per window rather than accumulated and released on close, because a stale claim is worse than no mark (#248)
- **panel**: the project and workspace pickers move into the vertical bar when the top bar is off. Both live in the top bar, so switching it off left "which project am I in" unanswerable from the window at all - and the top bar is now off by default. They sit at the bar's foot above the split map, drawn only when the top bar is absent, through a `footer: @Composable () -> Unit` slot composed in `BossAppScaffold` where the workspace manager and the window's project dialog already are; threading a workspace manager into a tab bar would have been five parameters through three layers. The project button opens the window's own project dialog rather than standing up a second copy of the top bar's recent-projects menu and its two dialogs (#248)
- **chrome**: `ChromeDimensConventionTest` pins that the bars actually read the metrics. `ChromeMetricsTest` pins the arithmetic *given* a `ChromeDimens`; it cannot see whether the chrome drawn and the chrome measured are the same thing, and the system failed open in the direction that matters - a bar written next month as `HorizontalBar(height = 36.dp)` compiles, ships and is silently absent from the budget, which is the exact failure the work opened with. `HorizontalBar` and `VerticalBar` are the only two ways a chrome bar's extent is set, which makes the surface small enough to police textually, in the style of `NoRawDialogConventionTest`. It found two offenders immediately, one of them its own KDoc quoting the call it catches (#245)

## Bug Fixes

- **plugins**: adding `pinnedCount` to `PanelConfig` silently disabled the bookmarks plugin. `plugin-workspace-types` is published and plugins compile against it, so its constructors are ABI, and a Kotlin default parameter does not preserve the previous shape: the primary constructor went from `(String, List)` to `(String, List, int)` plus a synthetic `$default`, while every plugin already built against the old jar went on calling the two-argument form. `BinaryCompatibilityValidator` rejects the *entire* plugin when one member is missing and the host then disables it, so bookmarks was installed, enabled and not running. `@JvmOverloads` emits the old constructor as a real overload; `PanelConfigBinaryCompatTest` pins it **through reflection rather than a Kotlin call**, because source would resolve through the default and prove nothing about what a plugin's linker sees. Note for anyone adding a field here later: `@JvmOverloads` does not cover `copy()`, so prefer adding nothing to these types (#248)
- **plugins**: and the second bug, which is what made the first hard to see. The Favorites shelf gated on "can I reach the bookmarks API" while its Install button gated on "is the plugin installed". Those disagree exactly when a plugin is installed but not running, which is the state the ABI break created, so the shelf offered Install, `offerIfMissing` correctly declined to prompt for something already installed, and the click did nothing, said nothing and logged nothing. Both now ask `MissingPluginOffer.isInstalled`, presence is keyed on the manager's observable `pluginStates` rather than a bare `getProvider()` (a plain registry lookup would have left the shelf sitting on its offer after the install finished), and the shelf distinguishes four states rather than three, including "installed but not running", where it says so instead of offering an install that would go nowhere (#248)
- **browser**: a tab whose page loaded before its listener attached stayed on "Loading...". `TitleChanged` is an event and `addTitleListener` only appended, so a listener arriving after Chromium had already reported the title heard nothing and the tab kept its creation placeholder for the rest of its life. The window is not narrow: a cached page fires almost immediately, and session restore attaches listeners for many tabs while those tabs are already loading, which is why this showed up as "sometimes". `lastKnownTitle` was already tracked for the context menu, so registration now replays it, skipping blank for the same reason `updateTitle` does - `about:blank` reports an empty title and replaying it would blank a tab. `addLoadingListener` had the identical shape and replays `_isLoading` too, with no blank case, since `false` is a real answer (#248)
- **tabs**: right-clicking a tab sometimes opened the tab *bar's* menu, and it took two independent faults to produce the intermittency. The tab's pointer handler was keyed on `contextMenuItems` - a fresh list of freshly built lambdas every composition - so the coroutine behind it was cancelled and restarted on hover, on a favicon arriving, on any tab-state change, and a right-click landing in that gap found no handler at all and travelled to the bar. It is keyed on `Unit` now, with its two values read through `rememberUpdatedState`. Separately, the shared `contextMenu` modifier runs on the main pass, child to parent, so a menu on a container saw every right-click inside it; it now ignores a press a child consumed, which is what the tab bar's own comment has claimed all along and was simply not true of the code it described. That second fault was deterministic, not just intermittent - right-clicking a rail favicon opened both menus, with the bar's on top (#248)
- **panel**: selecting a project no longer opens Codebase and Run Configurations on its own. It did so everywhere except Windows, and the two arrived on top of whatever the window already had arranged, so the first thing to do after choosing a project was often to close them. All three effects are gone: the pending project handed over by "Open in New Window", a project already selected when a window composes, and one selected later. Every panel is still one sidebar click, menu item, deep link or CLI command away. `StartupPanelPolicy` goes with them rather than being left switched off, since with no platform answering yes there is nothing left for it to choose between (#248)
- **settings**: Settings → Window Appearance → Show pane tab strip wrote a value nothing read back. It was read through `derivedStateOf { flow.value }`, and a `MutableStateFlow`'s `.value` is not a snapshot read, so the derivation had an empty dependency set, computed once, cached for ever, and being inside a `remember` was never rebuilt either. `collectAsState`, as every other reader of these settings already does (#248)
- **tabs**: menu-visibility reports were counted as deltas but sent as state. Every tab row emitted a `false` on its first composition, decrementing a count it had never incremented, and closing a menu reported `false` twice - so with every pane's rows in one `LazyColumn`, a menu open in the hover-revealed drawer was cancelled by any other row mounting (a scroll, or a background pane opening a tab), which retracted the drawer and took the menu with it: the exact failure the callback exists to prevent. Reports are paired now, one `true` on open and one `false` when that effect is disposed. The drawer's busy signal also only knew about menus, and the drawer unmounts its whole content when the pointer leaves, dialogs included, so a new-tab dialog raised from a pane header's "+" vanished mid-typing; "busy" now means every reason the bar must not leave the screen under the pointer (#248)
- **tabs**: Favorites tiles rendered as letters rather than favicons. The tile read `loadFaviconFromCache(faviconCacheKey)` synchronously during composition, and that key is absent on any bookmark not saved from a browser tab and misses on one saved before its favicon was cached, so the fallback was the common case rather than the edge. It goes through `loadHighQualityFavicon` now - starting from the URL and returning a 128px icon, in a `LaunchedEffect`, because it touches disk and network and composition is the wrong thread for either - with the cache read as the fallback and the letter as the fallback's fallback. The tiles are also tiles: 30dp with a 16px icon read as a row of dots, so 40dp rounded squares with a 22dp icon, four to a row, which is the other reason the high-quality fetch matters (#248)
- **panel**: splitting a pane from the map appeared to do nothing, because `checkAndCloseEmptyPanels` closes a tabless panel about 50ms later and the new pane was gone before it drew. Splitting first and filling afterwards cannot be made to work, since the pane stays empty for as long as it takes someone to answer a dialog. So "Split Right" records a pending split, opens the new-tab dialog, and passes the result to `splitPanel(tabToMove = ...)`, and the pane is never empty for even a frame. The pending split is *consumed* rather than read and cleared on dismissal, or the next ordinary New Tab would land in a second new pane; `place` moved above the dialog rather than inside a callback, because plugin tab types resolve their own target component and would otherwise have ignored the pending split for exactly the tab types a plugin contributes (#248)
- **chrome**: `dividerThickness` was measurement-only. The budget adds it five times vertically and twice horizontally and nothing drew with it - `VDivider` hardcoded `1.dp` and the horizontal dividers took Material's default - so it was the one metric where changing the value moved the reported number and not a single pixel, which is precisely the drift `ChromeMetrics` exists to prevent, sitting inside `ChromeMetrics`. No pixels move today: every density says `1.dp` (#245)
- **chrome**: `PasskeyBrowserScreen` hand-copied a 26dp title bar and a 40dp top bar, with comments saying "matches BossTitleBar" and "matches main BossTopBar structure". Copies, so they would have kept saying 26 and 40 the first time a user picked Compact while the chrome they claim to match moved. They read the metrics now, which is what those comments were always asserting (#245)
- **chrome**: `ChromeBudgetReadout` takes `dimens` as a parameter instead of resolving `BossChrome.dimens` itself. It is composed above the `Column` holding the bars, and the natural place to provide `LocalChromeDimens` is around that `Column`, below it - so the failure would have been silent, with the readout reporting Comfortable while the bars drew Compact. Its effect also keys on `windowHeight > 0.dp` as well as the size bucket, because bucket 0 covers both the degenerate mid-layout size and any real size under 50dp, and a window whose first real size landed there would never re-key and never log (#245)
- **panel**: `registerPanelDropZones` took its leading inset from the bar's *width*, and a window bar is registered against every panel while covering none of them - so every panel would have lost 200px of its left edge, and with it left-split-by-drag, to a bar nowhere near it. The inset is the measured overlap now, which is one rule for both cases. `PanelDropZones.fromBounds` likewise resolves every zone inside the panel *minus* the bar's strip, so the bar and the split zones partition the panel rather than overlap. Edge-scroll fired at a group's own ends, which is exactly where a drag aims when moving a tab to the next pane, so `TabBarBoundInfo` carries `scrollBounds`; and `leadingListItems` never counted the vertical bar's New Tab row, so scroll-to-active landed one row short in every left bar (#248)
- **ui**: the vertical bar's project and workspace rows were top-bar furniture in a 200dp column - a 28dp logo tile, 13sp text, 20dp icons - and then, once shrunk, still 36dp tall, because `BossActionButton` is a Material `TextButton` and Material sizes its content `Row` with `defaultMinSize(MinHeight = 36.dp)` from the *inside*, which the caller's own `defaultMinSize(2.dp)` cannot undo. Compact mode sets a fixed 24.dp height, which is min == max and leaves the inner minimum nothing to argue with, and 24 is the bar's own row height. Two more faults from stacking these controls: the hover hint opened downwards onto the other control, which under HARDWARE is a native window sitting in front of something about to be clicked, so compact places hints to the side; and `spacedBy(0.dp)` put their click targets in direct contact, so a click a pixel off opened a project dialog instead of a workspace menu. Its `contextMenuItems` also go from an empty list to null, since `BossActionButton` opens a menu whenever that list is non-null and an empty one meant an empty menu on top of the project dialog (#248)

## Improvements

- **tabs**: the hover drawer escapes the Compose scene, and it has to. Under `HARDWARE_ACCELERATED` a browser tab is Chromium's own native window composited *above* the Compose scene, so a drawer painted in place would be invisible over exactly the tabs people spend most of their time in - the same failure the tab tooltip, the Ctrl+Tab switcher, the toast host and the browser find bar each had to be fixed for. It routes through `OverlayCorner` with the panel's rectangle as `regionInWindow`, and is composed **only while revealed**, because a heavyweight corner swallows the clicks under itself and one composed unconditionally would leave a dead strip down every panel's leading edge. It also offers a pin rather than a collapse chevron: a drawer that exists only because the pointer is resting there has nothing to collapse, and what it lacks is a way to stay. `TabBarRevealState.isTransientReveal` decides between the two, so they can never appear together (#248)
- **tabs**: the drag system had three x-axis assumptions - reorder, edge scroll and the panel's left drop zone each read a coordinate directly - and the axis now travels with the bar's rectangle as `TabBarBoundInfo.vertical`, so none of them can disagree about it; the reorder arithmetic is extracted pure and unit-tested on both axes. Drag and drop asks a bar one question, whose tabs are under the pointer, and `groupSpans`/`splitBarAmongGroups` carve the shared column back into one rectangle per panel from the list's own layout, so reorder within a group and moving a tab across the rule both go through the paths that already existed. A group with nothing laid out is retracted rather than left claiming an area it no longer draws. A pane's favicon strip can start a drag but **registers no bounds**, which is the whole of what makes that safe: a tab's row in the window bar already registers the same `panelId:tabId` key, and a second surface writing it would leave reorder computing an insert position from whichever laid out last (#248)
- **tabs**: the selected tab gets a background rather than only a 3dp marker. Down a vertical bar, where every row is the same width and the marker sits against the bar's own edge, a sliver of colour plus a half-step of font weight is not what the eye lands on. Selected in the pane being worked in is the signal at low alpha; selected in a *background* pane is neutral, because the amber is a claim about where the user is and two panes both making it is the confusion the marker's focused/unfocused split already exists to avoid; hovered is quieter still, so hovering the selected tab does not flatten it. Alpha over the theme's colours rather than the fixed `signalWash` token, which is amber tuned for `ink`. The marker stays, drawn last so it remains a hard edge against the fill: the fill finds the tab, the marker says which pane it belongs to (#248)
- **chrome**: a left tab bar is charged to width. `mainPanelBudget` said "the tab bar has no switch - it is the one piece of chrome a tabbed browser cannot drop" and charged `tabBarHeight` to the vertical budget unconditionally, which is still true about the bar existing and no longer true about which axis it costs: with the bar on the left the budget charged the page for a row that is not there and did not charge it for the column that is. The rail's width comes from `ChromeDimens` strip width rather than a 40dp constant, and the budget charges a collapsed bar at exactly the same token, so the two cannot drift. It reads the *persisted* collapse preference, not the live one, because a panel forced to the rail by width is a per-panel fact and this budget measures a single full-width panel by construction. `MIN_TOP_BAR` is pinned against the icon-only `BossActionButton` size rather than the 22dp logo its KDoc named: 32 was the right number for the wrong stated reason (#245, #248)
- **tabs**: `BossMainTabBar` was a 650-line function holding the per-panel state, the lazy-list DSL, the containers and four dialogs at once - which is fine while every panel brings its own container, and is exactly what makes a split grow a second bar, since there is no way to get one panel's rows without also getting a bar around them. A window-level bar has to put several panes' rows in one `LazyColumn` and a lazy list's items can only be produced inside its own content lambda, so the state is hoisted into `TabBarState` and `rememberTabBarState`, moved verbatim first and verified against the TOP position before any window-bar work built on it. `TabBarState` is deliberately **not** remembered: it is a bundle of lambdas over values that change every composition, so a remembered instance would capture the first frame's and never update. The tab context menu came out to `TabMenuState.kt` for the same reason, because the panel drawing a favicon strip has no `TabBarState` to borrow, and the dialogs travel *with* the items rather than being left behind - two entries do nothing on their own but raise one (#248)
- **panel**: the reflective `getFilePath` lookup threw and caught a `NoSuchMethodException` per browser and terminal row on every recomposition, and is resolved once per class now. The rename dialog held a captured `TabBarGroup` and so could write a name for a pane closed underneath it, and holds an id it re-resolves instead; `TabGroupExpansion` never forgot closed panes. `preservedWorkspaceStates` becomes a snapshot state map and `_currentWorkspaceId` a `mutableStateOf`, because `liveWorkspaceIds` is read from composition and plain collections would have left the workspace menu showing whatever was true the last time something else recomposed it (#248)

## Known Limitations

- **Pane names are not persisted, and that is a deliberate stop.** They live in the window's `SplitViewState`, so a name lasts as long as the window does. Putting them in the split tree means adding a field to `PanelConfig`, which is a published serialized type - and the last time one gained a field it broke the bookmarks plugin outright until `@JvmOverloads` restored the old constructor. If a name should survive a relaunch, that is the ABI change to make deliberately (#248)
- **A pane that is not rendered while another is zoomed leaves composition**, so a browser in it detaches and re-attaches on exit. Its tabs survive, since the component lives in the split tree rather than in the composition, but a page does not keep playing. The same is already true of switching workspaces (#248)
- **The migration cannot tell a default from a choice.** A settings file records what a value is, never who set it, so an install sitting on the old default is indistinguishable from someone who picked top tabs and a visible top bar deliberately. Both move once, on purpose - the same limitation `WorkspaceSettingsMigrations` documents. An out-of-date file is stamped even when nothing else changes, or the step would re-run every launch and re-decide for anyone who moved back (#248)
- **Group headers, section headers and the split map are Left-position only.** A top strip has no room for groups, so TOP is untouched; section headers are dropped once several groups exist, because the rules between panes already divide the column; a lone pane grows no header, no map and no favicon strips, since there is nothing to name and no split to draw. Not taken from the Arc reference either way: the sidebar search field (Cmd+Shift+P already exists) and drag-to-add for favourites (#248)
- **Not unit tested, and worth being explicit about: the title and loading replay.** `BrowserHandleImpl` takes a live JxBrowser `Browser`, so it cannot be constructed in `desktopTest`; the existing tests around it all cover extracted pure logic. This was verified by running the app. The other three listeners - navigation, favicon and zoom - are deliberately left alone, because none keeps a last-known value to replay and fixing them means first deciding what to remember and when (#248)

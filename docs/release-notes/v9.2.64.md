# BOSS v9.2.64

**Release Date:** 2026-07-31

Three-fix release covering the browser context menu, plugin loading and the release pipeline: the context menu now describes what was actually right-clicked, plugins that merely hold a logger or a bookmark/tab-config property can load again, and the Windows ARM64 build - which failed silently during the v9.2.63 release - is restored with a test that catches the whole class of break.

## Highlights

- **The browser context menu reads its target from Chromium.** `setupContextMenuHandler` ignored the `Params` JxBrowser hands it and rebuilt the target from injected page state, so it answered for the main frame only - a click inside an iframe reported the *previous* click's link, and any click after focusing a search box reported an editable field. Images were never reported at all despite `hasImage`/`imageUrl` being in the API the whole time.
- **A single synthetic Compose field made 15 host-bundled classes incompatible with their `boss-plugin-api` counterparts.** A plugin holding a `ComponentLogger`, `Bookmark` or `TabConfig` as a *property* emitted a `getstatic` for a `$stable` field that exists in the api jar it compiled against and not in the host copy that shadows it - so `BinaryCompatibilityValidator` rejected the entire plugin and the host disabled it as binary incompatible. secret-manager 1.2.6 and 1.2.7 were unloadable on every host because of it.
- **The 30 Jul release published without a Windows ARM64 artifact.** That leg failed compiling `composeApp` while the other four platforms and `create-release` succeeded, so a partial release looked green. No PR job builds that target, so nothing caught it before release; a new `WindowsArm64SourceIsolationTest` that runs everywhere now does, and it immediately found a second live break.

## Bug Fixes

- **browser**: read the context-menu target from `ShowContextMenuCallback.Params` rather than from injected page state. The link href came from a `contextmenu` listener stashing it on `window`, the selection from `window.getSelection()` and "is this editable" from `document.activeElement` - all main-frame-only answers. The request is now answered unconditionally from a `finally` with no live-`Browser` call left on the path, so an unanswered request can no longer show no menu at all; the four blocking `executeJavaScript` round-trips that ran *before* `tell.close()` are gone, along with 140 lines of dead injected JS. Editable is still reported for the main frame only, deliberately: every action it unlocks (cut/copySelection/paste/selectAll, fillCredentials) targets `mainFrame()` and `document.activeElement`, so offering it for a subframe field would act on the wrong frame and could write a password into an unrelated input. The one lookup Chromium cannot answer runs off-thread on a dedicated thread, bounded at 500ms, and is delivered only if the tab is still alive and the plugin still registered (#78)
- **plugin-logging**: emit the Compose `$stable` field from `plugin-logging`, `plugin-bookmark-types` and `plugin-workspace-types` so their copies of the `ai.rever.boss.plugin.*` packages stay interchangeable with `boss-plugin-api`'s. `$stable` was verified with `javap`, member by member, to be the only public difference, so emitting it repairs plugins that are **already built** - no api release, no plugin rebuild. Diffing every api package the host also bundles found the field missing from **15 classes**: `ComponentLogger`/`BossLogger`/`LogEntry`/`BossLoggerConfig`/`LogSanitizer`, `Bookmark`/`BookmarkCollection`/`FavoriteWorkspace`/`WorkspacePanelTarget`, and `LayoutWorkspace`/`TabConfig`/`PanelConfig`/`SplitConfig`/`BreadcrumbConfig`/`WorkspaceSerializer` - only the logger had bitten us, but plugins hold the data types as properties routinely. `plugin-logging` takes the Compose runtime as `compileOnly` (the compiler needs it, the generated field references no Compose class, so the published POM stays clean); the other two already had it for `@Immutable` and only needed the compiler plugin. Note that already-built secret-manager 1.2.6/1.2.7 remain unloadable on hosts *without* this change - the plugin-side fix shipped separately as 1.2.8, which loads on unfixed hosts (#80)
- **build**: restore the Windows ARM64 build by moving `SelfHealingSettings.kt` out of `kernel/`. That target drops the kernel and plugin/remote sources from `desktopMain` because `boss-ipc`'s protoc ships no win-arm64 binary; every file under `kernel/` needs `boss-ipc` except this one, which was excluded by package name rather than by any dependency it had - and the settings UI, which is *not* excluded, imported three types from it. `main.kt`, `PluginStoreSetup` and `PerformanceDataProviderImpl` all reach `KernelBootstrap` through `Class.forName` precisely to avoid this; the settings screen was the one place that didn't. It moves to `ai.rever.boss.config` as `SelfHealingSettingsManager.kt` alongside `BrowserEngineSettingsManager`, and its two tests move with it and now run on Windows ARM64 too. `IpcCompatibilityTest` and `PluginStoreSetupIpcGateTest` - a second live break the new guard found immediately, importing `boss-ipc` from outside both excluded directories - are excluded there like `RemoteWidgetRendererColorTest`. Verified by forcing `isWindowsArm64Build` locally: main and test compilation reproduce each failure before the change and succeed after (#82)

## Improvements

- **build**: add `WindowsArm64SourceIsolationTest`, which runs on every platform and asserts that surviving source imports neither the excluded directories nor the dropped modules, that a file declaring an excluded package lives in the excluded directory, and that its own lists match `build.gradle.kts` - the class of break that produced a partial v9.2.63 release was previously invisible until the release job ran (#82)
- **plugins**: `BinaryCompatibilityValidator` now names the likely cause when the missing field is `$stable` - that field is Compose-synthetic, so its absence almost always means two copies of the owning class exist, one compiled with Compose and one without. `$stable: field not found` as the only clue is what made the secret-manager diagnosis take hours. Deliberately a message change and not a soft-fail: the plugin's `getstatic` sits in its own `<clinit>`, so a genuinely missing field is a hard `NoSuchFieldError` at first touch, and rejecting up front with a reason beats crashing later without one (#80)
- **build**: all three affected `plugin-platform` modules wire `AbstractPublishToMaven` to depend on their own `desktopTest`, verified with `--dry-run`. Co-location alone did nothing - `publishAndReleaseToMavenCentral` has no dependency on `check`/`allTests`, so a future release could have been published without `$stable` and nothing on that path would have objected. `LoggingStableFieldTest`, `BookmarkStableFieldTest` and `WorkspaceStableFieldTest` pin the field's presence and that it is public/static/int, as a plugin's `getstatic` requires (#80)

## Dependencies

- **plugin-logging**, **plugin-bookmark-types**, **plugin-workspace-types**: 1.0.4 → 1.0.5 - the published bytecode changed and Maven Central artifacts are immutable. The latter two must be published together: `plugin-bookmark-types` has `implementation(projects.pluginPlatform.pluginWorkspaceTypes)`, so its POM pins the sibling at the current project version, and dispatching bookmark-types alone would ship a POM requiring a `plugin-workspace-types` 1.0.5 that does not exist on Central (`all` is safe - workspace-types publishes first) (#80)

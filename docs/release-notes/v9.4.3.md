# BOSS v9.4.3

**Release Date:** 2026-08-07

BOSS becomes multi-tenant: organisations are a first-class owner of secrets, plugins and membership, with the schema, the authorization guards, the JWT claims and a set of server-rendered org web pages. The desktop half of the release is the fallout from shipping that schema - four secret RPCs gained columns and every installed build's secret panels went empty, so Supabase decoding is now lenient by construction and decode failures no longer carry the credentials they were parsing.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

> **Deployment**: the organisation edge function needs `ORG_SESSION_SECRET` set (a missing one is a 503, deliberately, rather than telling every visitor their session expired), the JWT hook needs its `supabase_auth_admin` grant on `get_user_orgs_for_hook`, and a deployment whose schema lands before its first user should call `ensure_boss_organisation()` once.

## Highlights

- **Organisations are a real tenant, and `authorize()` is deliberately not the gate.** 9 tables, the permission catalog, RLS, 26 core RPCs, invite links, handoff tokens, JWT claims and a seeded `boss` organisation every existing user is backfilled into. The existing `authorize()` answers "does this user hold the permission anywhere" and short-circuits true for global admins, so no org mutation consults it; every org-scoped gate reads the membership tables through `is_org_admin(p_org_id)` / `is_org_member(p_org_id)`, and `organisation.admin` exists only so the UI can render. Two escalation paths shaped the rest: an org whose slug derived `boss_admin` would have handed every one of its admins `role.create` and `role.assign` (reserved slugs, a pre-flight collision refusal, and a trigger refusing to map any `is_system` role), and the `<slug>_user` hierarchy edge widens delegation, so a deny-list trigger makes `role.*`, `user.*`, `api_key.*`, `rpa.*`, `plugins.admin.*` and `organisation.approve|create` structurally un-grantable to an org role - failing closed and binding global admins and `service_role` too (#138)
- **The secret panels were empty on every installed build, and the host was at fault.** Adding `secrets.org_id` and `secret_shares.shared_with_org_id` broke reading secrets the moment the migration landed: `SecretService` decoded with the bare kotlinx default, which is strict, and these RPCs return a *list*, so one unmodelled column does not drop a field - it throws and takes the whole page with it, leaving a single WARN behind. The database is migrated ahead of the desktop app by design, so this was always going to fail on the first added column. Review found the break was wider than reported: a client decodes an RPC's `RETURNS TABLE`, not a table, and the four rewritten signatures project derived fields (`org_slug`, `is_org_owned`, `can_manage`) that exist in no table at all - four broken list RPCs, of which `get_secret_shares` read as "no shares" on every secret and `search_user_secrets` failed silently. One package-level `supabaseJson` now backs every decode site, request parameter and JWT payload (#144)
- **A decode failure was printing decrypted passwords into logs users attach to bug reports.** Probed rather than assumed: schema failures were already safe, but *malformed* input makes kotlinx append the whole offending document - and for these RPCs that document holds passwords the server has already decrypted plus recovery codes. A proxy error or a gateway HTML page was enough. `sanitizeSupabaseFailure` strips the document from every `SerializationException` while keeping the diagnostic half, since "unknown key 'org_id' at path: $" is what identified this outage. The request direction leaked too: `SupabaseDataProviderImpl.rpc` parses caller-supplied parameters, so a plugin calling `create_secret` put the new password on that path - and the first fix sanitised the log line then rebuilt the returned exception from the raw message, handing the document to the plugin instead (#144)
- **A download URL is guessable from a plugin id, so the listing gate was decoration.** Both store download handlers now check `user_can_install_plugin` before the permission gate and before `recordDownload`, denying with the same 404 a missing plugin gets, because a 403 would confirm the plugin exists. Not `user_can_view_plugin`, which the plan called for: that answers the *listing* question and hides `unlisted` from ordinary members, and `unlisted` means "absent from listings, not un-installable", so gating on it would have 404'd an organisation's own members on a link they were handed (#138)

## Features

- **organisation**: the org tenancy schema, guards and core RPCs. 9 tables, the permission catalog, RLS, 26 core RPCs, invite links, handoff tokens, JWT claims and the seeded boss org that every existing user is backfilled into. The escalation guard is a permission-domain deny-list rather than the `is_system` flag it started as, because against the real catalog that flag is inverted - `role.assign`, `role.create` and `api_key.create` are all `is_system = false` while `secret.read` is true, so the original form permitted `role.assign` on an org role, the exact escalation it exists to prevent; an assertion pins `role.assign is_system = false` so a future "simplify to `is_system`" fails loudly. `organisation_roles` is authoritative, not the role name. Invite redemption checks already-redeemed before exhaustion, so re-clicking your own `max_uses = 1` link is idempotent instead of reporting an expired link that had just worked. Planned as 12 migrations; the `*_for_actor` family collapsed into one `resolve_org_actor` helper instead of ~17 duplicate RPCs (#138)
- **organisation**: org-owned secrets. Secrets have been person-owned, so they die with the account. Adds `secrets.org_id` and `secret_shares.shared_with_org_id`, a three-way `share_target_check`, and two partial unique indexes replacing `unique_user_website`, with all nine secret functions recreated against the new ownership model. A security fix rides along: `share_secret`, `unshare_secret` and `get_secret_shares` were `SECURITY DEFINER` with no `SET search_path`, a textbook definer-escalation surface, and all nine are now hardened (#138)
- **organisation**: plugins are owned by an organisation. The store's only ownership concept was `plugins.author_id` and its only visibility concept was the `published` boolean. Adds `plugins.org_id` (RESTRICT, so deleting a user cannot cascade away an org's plugins) and `visibility`, defaulting to public and backfilled, with a BEFORE INSERT trigger defaulting to the author's org, and `user_can_view_plugin_row` gating the store RPCs. `get_popular_tags` aggregated across all published plugins, so org-private plugin tags would have leaked internal project names into the public tag cloud; it is restricted to `visibility = 'public'` (#138)
- **organisation**: the org web pages as an edge function. Serves the member overview, the admin configuration page and the invite landing page at `/functions/v1/organisation`. The session is a stateless HMAC-signed cookie rather than a DB row, because the cookie is an *authentication* token and carries no privilege - authority is re-derived from `user_is_org_admin` / `user_is_org_member` on every request, so revocation is free and a removed member's live web session dies on their next click. The format is deliberately not a JWT: no `alg` field, so no negotiation, no `alg:none`, and no dependency to keep patched, with a test asserting an injected `{"admin":true}` is dropped. CSRF is cookie-bound double-submit with the nonce inside the signed HttpOnly cookie, because `SameSite=Lax` gives nothing here - `api.risaboss.com` also serves plugin-store's Swagger UI, which loads third-party CDN script, at the same origin. Order in every mutating handler is session → CSRF → live admin probe → rate limit, so a forged post costs one HMAC verification and never reaches the database. The `?t=` handoff exchanges a single-use token for the cookie and 302s to the same URL without it, so the bearer leaves the address bar and the history, and invalid and wrong-org tokens render one byte-identical page so the endpoint is not an oracle. Domain verification authorizes against the row's own org rather than the cookie's, or an admin of org A could re-point org B's domain by guessing a row id, and the DNS answer is never echoed back, or this would be an open resolver behind an authenticated endpoint. No CORS middleware, on purpose (#138)
- **organisation**: `get_organisation_detail` for the admin config page. Three settings the admin page renders round-trip nowhere else - `publish_role_id`, `auto_assign_member_role` and `max_custom_roles` - and `get_my_organisations` projects only what a picker needs. Without it the edge function would SELECT the organisations table over its service-role client, bypassing RLS and moving an authorization decision into TypeScript. Admin-only settings are absent from a member's response rather than nulled, since a nulled key still reports that the setting exists, and a missing org and a non-member org return the same "Organisation not found" (#138)

## Bug Fixes

- **secrets**: decode secret RPCs leniently so a new column cannot empty the list. All ten decode sites route through a package-level `supabaseJson` with `ignoreUnknownKeys`, and `RoleService` / `RoleCreationService` are pointed at it as well - the hazard is a property of the deployment rather than of one file, so scoping the fix to `SecretService` would have left the next migration free to repeat the outage through RBAC. The wildcard `kotlinx.serialization.json.*` import also keeps `Json.Default` in scope, so a shared instance is what stops a new call site quietly reintroducing this. `get_secret_shares` also modelled a nullable `shared_by_email` as non-null with no default - it derives from `LEFT JOIN auth.users` and one null threw for the whole array, the same outage through a door leniency does not cover. The trade is documented: additive changes become safe and renames become silent for any field with a default, which makes "additive only, never rename" a contract the database side has to keep. `SecretDecodingTest` carries each RPC's exact shipped key set; mutation-verified, strict decoding fails all six (#144)
- **secrets**: keep decrypted credentials out of decode failures, in both directions. `sanitizeSupabaseFailure` strips the offending document from every `SerializationException`, and the sanitised type carries no cause so the payload cannot be recovered by walking the chain. Applied to the *returned* exception as well as the log line, since the stated threat model is "callers log `e.message`" and here the caller is a plugin. `RoleService.decodeJWTClaims` carried the comment "JWT payload not logged to avoid exposing sensitive claims" fifteen lines above a catch that logged the raw exception, putting a whole claim set in the log. Sanitising is now uniform across 22 further sites in `RoleService`, `RoleCreationService`, `UserService` and `SupabaseConfig` rather than only where a leak was demonstrated - most are no-ops today, and that is the point. The pass-through for non-serialization failures is deliberate but bounded, recorded in the KDoc: `RestException` carries the PostgREST body, and a constraint violation can echo column values back (#144)
- **secrets**: pin the wiring, not just the behaviour. Reverting all ten `Result.failure(sanitizeSupabaseFailure(...))` calls back to `Result.failure(e)` passed all 13 tests - the behaviour was pinned and the wiring was not, which is the half that broke production. `SupabaseWiringTest` reads the source, since these services build their Postgrest client from `SupabaseConfig` with no seam to inject a fake, and it is widened past the shapes already in the tree: `Json.Default`, a locally built `Json { }`, fully-qualified use, a raw throwable under any variable name and the returned direction, recursing with `walkTopDown` so `models/` and future subpackages are covered, with exemptions as an explicit allow-list each carrying a reason. `SupabaseDataProviderLeakTest` executes for real with no live backend, because reasoning got that function wrong twice (#144)
- **secrets**: honour the role hierarchy for role-targeted shares. A secret shared with a parent role was invisible to its descendants - `get_user_secrets` matched the share role exactly instead of walking the closure. Adds `get_role_ancestors` + `effective_share_role_ids`. Note this widens read access: a parent role now sees secrets shared with roles beneath it, which is the intended hierarchy semantics but is a visibility change to review before rollout (#138)
- **store**: gate downloads on organisation visibility. Both download handlers check `user_can_install_plugin` before the permission gate and before `recordDownload`, denying with the same 404 a missing plugin gets so the endpoint does not become an enumeration surface, and the probe fails closed. Two wiring guards assert order, not just presence, since a behavioural test cannot reach this without a live database (#138)
- **organisation**: a failed domain claim committed a half-created organisation. `create_organisation_internal`'s two domain checks sat at step 8, after the organisation, both roles, the hierarchy edges, the permission grants, the founder membership and the founder `user_roles` row had all been inserted - and a plain `RETURN` from PL/pgSQL rolls back nothing. So a refused domain returned `success:false` with all eight inserts committed: an orphan organisation nothing pointed at, silently owned by the requester, whose slug then made the originating request impossible to approve on any retry. Reachable in normal operation, from two pending requests naming the same domain or a domain added to `reserved_email_domains` between submit and approve. Both checks now run before the first INSERT (#138)
- **organisation**: three information-disclosure findings reachable by any signed-in user. `user_can_view_plugin_row` took an arbitrary subject and was granted to `anon` and `authenticated`, reducing to the three predicates an earlier migration had revoked from `authenticated` for exactly this reason - one RPC call per question, about anybody. `effective_share_role_ids` had the identical hole, its comment claiming safety "because it is scoped to a single subject" when the subject is the parameter, so any user could ask for anyone else's full descendant role closure against a world-readable `roles` table. And the seeded boss-org roster was a global email directory: every user is an active member of it and `handle_new_user` keeps every future signup there, so a member-gated `list_organisation_members` with an ILIKE let any signed-in user page out every account's email. In an `is_system` organisation a non-admin now sees only themselves, enforced in the RPC *and* in RLS; real organisations are untouched, since their roster is the point (#138)
- **organisation**: the table and function grants were not the posture the migration described. Supabase's `ALTER DEFAULT PRIVILEGES` grants ALL on every new public table to `anon` and `authenticated` at CREATE TABLE time, so all nine organisation tables were fully granted without this migration ever granting them - an org admin could SELECT `token_hash` from `organisation_invites` over PostgREST, and writes were held off by RLS alone rather than by RLS and the absence of a grant. REVOKE ALL first, then grant back only the SELECTs the policies are written for; the two credential tables get nothing. The same default applies to functions, leaving 54 anon-executable - not an authorization hole, since they resolve through `resolve_org_actor` which returns NULL for `anon`, but an unauthenticated DB-reachable surface nobody intended. `verification_token` was likewise readable by `authenticated`, because the SELECT policy deliberately exposes verified rows and RLS is row-level, so the token rode along; a column-level REVOKE cannot carve a column out of a table-level grant, so the table grant is revoked and re-issued column by column. Seven tests pin the table privileges, because nothing asserted one before - which is how this survived four reviews (#138)
- **organisation**: two live-credential bugs in the invite flow. Reloading the invite-created page minted a *second* live invite, and the first link stayed live too: that page answers 200 rather than 303 because the plaintext token exists for exactly one response, so the browser's reload button re-submits the form. The response now rotates the session's CSRF nonce, making the form still sitting in the page stale and the resubmission refused by the existing gate. And a minted token could be silently discarded - if the page-data read failed after the RPC succeeded, the invite existed, was live, and its plaintext was gone forever while the admin was told it worked; the url never depended on that data, so that path renders the card alone. Also: `uses` double-counted, since `ON CONFLICT DO NOTHING` on the redemptions insert does not make the following UPDATE conditional, so the re-admit path burned a use of a capped link on somebody who had already consumed one; invite re-click after removal was a dead end, because the redemption row outlives the membership and idempotency keyed on it alone said "already a member" without re-adding them; and an out-of-range `max_uses` silently created an *unlimited* invite, `intField` returning null for invalid and absent alike (#138)
- **organisation**: the handoff exchange refused nothing cross-site. It consumes a token and issues `Set-Cookie` on a plain GET, so any page could navigate a victim to `/o/<slug>?t=<attacker token>` and replace their session with the attacker's identity - the attacker gains nothing, but the victim can be induced to type into somebody else's settings form. `Sec-Fetch-Site` is not settable by page script and the desktop app's `boss://` navigation yields `none`, so refusing `cross-site` costs the real flow nothing. The public-organisation arm of `mint_organisation_handoff_token` is also gone: it only ever produced a token that 404s, since the page refuses a non-member twice (#138)
- **organisation**: the invite link on the admin card was a bare path, and its highlight never applied. `publicBasePath()` returns a leading-slash path, correct for a `Location` header and useless for the one string whose entire purpose is to be copied out of the browser and sent to someone else - and the token is displayed exactly once, so getting it wrong costs a revoke and a re-mint. New `publicBaseUrl()` builds an absolute url from `ORG_PUBLIC_BASE_URL` or the request's own origin. The card's markup read `class="card" class="highlight"`, and a parser keeps the first attribute and discards the second, so the round-two CSP fix shipped with no visible effect - that class exists only because `style-src` is nonce-only and a nonce cannot apply to an attribute, which had silently dropped eight inline `style=` attributes including the amber border on the one-time invite card. A third recurrence of the duplicate attribute was caught by a guard that now scans every file in `views/` on disk rather than the rendered admin page (#138)
- **organisation**: `get_my_organisations` reported an unverified domain as `primary_domain`. Both its siblings filter on `verified` and this copy had drifted, so a bare claim with no DNS control surfaced as the organisation's domain in the desktop list. Relatedly, "only a verified domain may be primary" was enforced only in the edge function while `set_primary_organisation_domain` is granted to `authenticated`, so an org admin calling it straight over PostgREST skipped the check; the invariant now lives in the RPC, with the edge function keeping its copy as the friendly-error layer. An organisation's description could never be cleared, either - `field()` collapsed "absent" and "present but empty" to null and the RPC COALESCEd, so emptying the textarea reported `settings_saved` with the old text still shown (#138)
- **organisation**: a present-but-unrecognised enum was mapped to "leave unchanged" and answered with a success banner; it is `invalid_input` now, which is the rule `max_uses` already followed on identical reasoning a hundred lines away. Absent still means unchanged. Also: `attrUrl` refuses a leading slash-backslash, since browsers normalise `/\` to `//` for special schemes so it was cross-origin while passing the same-origin arm; the rotated CSRF nonce is hoisted into a variable rather than recovered by re-verifying the token just minted, whose `?? session.csrf` fallback would have rendered the old nonce against the new cookie and 403'd every form on the page right after the operator was told the invite was created; the deep link was escaped twice, so a second query parameter would have double-encoded its ampersand; and two banner keys were unreachable (#138)
- **organisation**: `download.ts` resolved an API-key caller to anonymous. `getUserFromToken` handles user JWTs only, so CI and the publish tooling had no subject for the visibility gate - harmless while every plugin is public and published, since the predicate short-circuits that case for a NULL subject, but the first org or unlisted plugin would have 404'd for them, and that 404 is deliberately indistinguishable from "no such plugin". Falls back to `validateApiKey`; an anonymous caller still reaches public plugins (#138)
- **organisation**: `get_user_orgs_for_hook` now RAISEs a warning before degrading to empty claims. A missing or revoked `supabase_auth_admin` grant - the one the deployment notes call out - would otherwise present only as the organisation switcher never appearing, for everyone, with nothing in any log to say why (#138)
- **organisation**: two type errors the narrower local check missed. `ctx.req.param("slug")` is `string | undefined`, since a handler can be reached by a path with no such segment, and `setTimeout` is typed as returning a `Timeout` object under the Node-compatible lib and a number under the Deno one depending on how the file is entered. Neither reproduced under `deno check index.ts`, which follows imports from one entry point while CI checks every file as its own (#138)

## Improvements

- **ci**: the organisation function gets its own job, so its 82 tests gate something. Each function needs its own job because `working-directory` scopes both the `find` and the `deno test`, and adding a directory to an existing job would not have run it - the same way the plugin-store suite once sat unexecuted. Lint gates here rather than being advisory, since this function starts with no grandfathered findings (#138)
- **tests**: three vacuous assertions, and the seeded org that existed in no CI run. `supabase db start` migrates a database with zero `auth.users` and `seed.sql` creates none, so the boss-org seed always took its "no users yet" branch - `plugins_org_visibility` then compared `plugins.org_id` against a row that was not there, both sides were NULL, and pgTAP's `is()` passes NULL = NULL, so the `plugins_default_org` trigger that keeps the store's publish path working was never verified. The fixture creates the organisation itself with an `isnt(NULL)` guard against degrading back. The seed is now a callable `ensure_boss_organisation()` rather than only a DO block, because migrations run once and a deployment whose schema lands before its first user would otherwise never get the organisation, silently, with `plugins.org_id` NULL forever. Deliberately *not* wired into `handle_new_user`, though it was offered: making the first signup create an organisation and two roles as a side effect of an auth trigger changes the role graph out from under everything that reads it, and broke four pgTAP suites asserting exact grantable-role sets (#138)
- **tests**: the five deferred organisation suites, plus the role-graph reconciliation. Membership (27), requests and approval (29), and handoff tokens with JWT claims, discovery and table shape (37), and three of them turned up behaviour worth pinning: an unconfirmed email address at a verified domain still has to ask to join, a pending applicant holds no organisation role at all, and discovery is not a slug oracle. Four of the new assertions were wrong and were corrected against the real behaviour rather than the other way round. Separately, `boss_plugin_admin` landing on main made two suites that enumerate the seeded graph exhaustively go stale, and exhaustive is the right assertion there - a subset check would not catch a leak - so the expectations are updated with the consequence recorded: a secret shared with the admin role is now readable by `boss_plugin_admin` holders. Neither failure was visible before a full db reset, since the local database had been migrated incrementally from a base that predated that role. 377 pgTAP, 88 + 20 Deno (#138)
- **docs**: `AGENTS.md` records both Supabase rules next to the existing material - decode through `supabaseJson` and log `sanitizeSupabaseFailure(op, e)` - along with the one leniency does not cover: declare every projected column `T? = null`, because a null in a non-nullable slot still fails the whole list. That third rule is labelled convention upheld by review, since no test enforces it and the existing models do not all follow it yet. The migration comment that caused the outage is corrected too: it said supabase-kt decodes leniently "so an older Secret Manager plugin ignores them", and the warning attached to it was right while the reassurance was wrong - the plugins do not read these RPCs, the host does, with raw kotlinx (#144)

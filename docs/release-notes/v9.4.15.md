# BOSS v9.4.15

**Release Date:** 2026-08-18

A maintenance release about diagnosis and durability: a crash report can no longer be read while it is half written, a realtime warning finally says which of the several Supabase clients it came from, and the per-OS build jobs actually skip the lint gates their comment claimed they already skipped.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **A contained crash report was written in place, so the final path could hold a partial one.** `writeOwnerOnly` deleted the target, recreated it owner-only and then streamed the report into it, which means anything reading that directory between those two steps - the next launch, a support tool, the user attaching it to a bug report - saw a truncated report at the name a complete one lives at. The report is written to an owner-only sibling temp file and published with an atomic replacement instead, the temp is restricted before any content is written on the non-POSIX path, and a failure removes it rather than leaving it behind (#189)
- **A realtime warning named no client, and three of them run against the same project.** supabase-kt tags every line `(Supabase-Realtime)` and identifies nothing further, while BOSS runs the main client, the app-update watcher and the plugin-store watcher - plus whatever an installed plugin runs, and the Toolbox runs one. So a once-a-minute `Heartbeat timeout. Trying to reconnect in 7s` said a socket was flapping without saying whose, and because the lines interleave, pairing a "Connected" with the next timeout quietly assumed both came from one client. Each client now installs a logging processor that names it, so the line reads `[app-update] Heartbeat timeout...` with the name as a structured field. This does not fix the reconnect loop; it makes the next run say which client to fix (#201)
- **The per-OS build jobs never skipped ktlint.** `-x detekt -x ktlintCheck` excluded the umbrella task, but ktlint wires a `ktlint<SourceSet>Check` task into `check` for every source set in every module - a dry run of the exact CI command still listed 351 of them. The "3x waste" the comment set out to remove was never removed, and a formatting slip failed build-test on macOS (cancelling ubuntu and windows through fail-fast) as well as code-quality, which is the confusing signal it set out to avoid. A `-PskipLint` property disables both plugins' tasks outright; the dedicated code-quality job runs them unflagged and stays authoritative (#203)

## Bug Fixes

- **crash**: contained reports are published atomically. The regression test is latch-controlled - it freezes the writer between "temp complete" and "publish" and asserts the final path is absent, the temp content is complete, and no temp file survives publication - so it fails against the previous behaviour rather than merely describing the new one. Fixes #105 (#189)
- **realtime**: these lines stop bypassing `BossLogger` entirely. They went to stdout with no category, not in the app's format, and never reached a log file - so the one message that would have identified a flapping socket was also the one message absent from the logs a user attaches to a report (#201)
- **realtime**: the supabase-kt throwable is deliberately not handed to the logger. `SupabaseWiringTest` scans this package for exactly that, and the guard is right: `BossLogger` writes `error.message` and a stack trace into the log file, and what a `SupabaseLoggingProcessor` receives is whatever the library chose to log - a `RestException` carries the PostgREST error body, which can echo column values back. Routing through `sanitizeSupabaseFailure` would have satisfied the scan and changed nothing, since it rewrites `SerializationException` and passes everything else through untouched. So the type goes into the structured fields as `errorType` and the library's own diagnostic text is already in `message`, which is what the attribution needed in the first place; the stack trace is the only loss, and it points into supabase-kt (#201)

## Improvements

- **ci**: `-PskipLint` replaces the task exclusions in the per-OS build jobs, verified against a deliberately misformatted probe file - without the flag `:composeApp:ktlintCommonMainSourceSetCheck` fails on it, with the flag that task and `:composeApp:detekt` report SKIPPED, `:composeApp:ktlintCheck` still fails on it, and a full `:server:build -PskipLint` succeeds with the violation present. `--dry-run` cannot verify this, because it lists disabled tasks too (#203)
- **realtime**: the two logging processors are near-identical copies rather than one shared class, on purpose - `plugin-repository` cannot see `composeApp` (the dependency runs the other way), and `composeApp`'s copy is `commonMain` while that service is `desktopMain`, so no source set reaches both without inventing a module for forty lines (#201)
- **repo**: `.worktrees/` is git-ignored. Every repo in this workspace keeps its feature checkouts there, so the directory showed up as untracked in `git status` on every branch, in every checkout, forever. What matters beyond tidiness is that a permanent entry in `git status` is how a real untracked file gets overlooked - a new source file that was never added looks exactly like the noise you have learned to skip past (#202)

## Known Limitations

- **The realtime reconnect loop itself is not fixed.** This release only makes the logs attributable, so the next occurrence names the client to investigate (#201)
- **The two logging processors must be kept in step by hand.** Both copies were changed together for the throwable fix; nothing enforces that they stay near-identical (#201)

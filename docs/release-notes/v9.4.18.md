# BOSS v9.4.18

**Release Date:** 2026-08-19

A release about being asked rather than assumed. BOSS no longer opens on a layout nobody chose, removing a project no longer happens on a single click with no way back, updating a plugin other plugins depend on asks and then restarts them, and reading the organisation-creation queue is its own permission instead of riding along on `organisation.approve`.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **BOSS starts with no workspace and asks when you open a project.** The default was platform-dependent and nobody had chosen it: Claude Code on macOS and Linux, browser-only on Windows, so a fresh install put a terminal running an agent - or a browser tab - in front of the user before they had said what they were doing. The default is now "Ask" everywhere, nothing is applied at startup, and selecting a project raises a picker. "None" keeps its old meaning of never apply and never ask, so a deliberate pick is not moved onto a prompt, and a one-time settings migration (version 1 → 2) moves only installs still sitting on the value their platform shipped with (#208)
- **Removing a project asks what you mean, and can take the folder with it.** The cross on a project card called `removeRecentProject` on the click - no confirmation, no undo, and no way to get rid of the directory it pointed at. Both crosses (the home-screen card and the trailing X in the top bar's project menu) now open `RemoveProjectDialog`, where forgetting is the unchecked default so pressing through does what the button always did, and "Also move the folder to the Trash" is an explicit opt-in that restates itself in the button label and turns it red. It moves to the Trash and never unlinks, so a wrong click stays recoverable outside BOSS (#209)
- **A plugin other plugins depend on can be updated from the Toolbox again, and its dependents are restarted.** `checkCanUnload` refused the unload and the Toolbox updates by uninstalling and reinstalling, so the refusal landed on the Update button - the AI Gateway was the live case. The host's own update paths had the opposite bug: `PluginUpdateBridge` and `PluginStoreVersionBridge` pass `force = true`, so they never refused and never restarted the dependents either, leaving each one holding a handle into a classloader that had just closed. Both now ask the same question, and the answer is a dialog naming the plugins rather than a refusal that named them only in the log (#210)
- **Reading the organisation-creation queue is no longer bundled with approving requests.** Migration `20260801010000` grants `organisation.approve` to both `admin` and `boss_admin`, so every boss_admin could list every pending request including the requester's email and their free-text justification. The read splits out as `organisation.request_read`, seeded `is_system = false` precisely so it stays grantable *and* revocable from the roles plugin as the policy widens, and granted to no role - `authorize()` and `user_holds_permission()` short-circuit on `is_user_admin`, so `admin` keeps the queue with no grant (#211)

## Features

- **workspaces**: selecting a project opens `SelectWorkspaceDialog` instead of silently applying a layout, and a project-shaped workspace clicked with no project open now says so rather than starting an agent in `~/BossProjects` (#208)
- **projects**: `RemoveProjectDialog` plus `ProjectRemoval`, with `trashRefusal` deciding whether trashing is possible and saying why not - no Trash on this desktop, a folder already gone, a path that is not a folder, a filesystem root, or the user's home directory. An unavailable Trash disables the checkbox rather than quietly downgrading to a delete (#209)
- **plugins**: `DependentRestartDialog` and `DependentRestartPrompt` ask before an unload that would strand dependents, `DependentRestartBus` carries the question to one window and the answer back, and `DependentRestartCoordinator` restarts the dependents once the plugin is back (#210)
- **auth**: the new `organisation.request_read` permission, applied at both sites that read the queue - `list_organisation_requests`, where the flag is both the button and the row filter so both halves move together, and the reviewer `SELECT` policy on `organisation_requests` (#211)

## Bug Fixes

- **workspaces**: selecting a project no longer clobbers a restored session. Last Session restore calls `selectProject` with the path its layout recorded, which the effect watching `selectedProject.path` could not tell apart from a user opening a project - so every launch that restored a project re-applied the default workspace over the layout just restored, and with the default now "Ask" that would have become a dialog at every launch. `isUserProjectSelection` separates the two (#208)
- **workspaces**: one list of workspaces, everywhere. The home screen listed `SplitTemplatesManager.allTemplates` while the top bar, the app menu and the default-workspace setting listed `WorkspaceManager.workspaces` - two parallel definitions of the same seven layouts, already drifted, since only the workspace copy had Browser Only and passed `{claudeContinueFlag}`. The home screen reads the same manager now, so saved workspaces appear there too (#208)
- **workspaces**: the app menu and `WorkspaceButton` each held their own `WorkspaceManager` instance, whose `currentWorkspace` never saw a switch made anywhere else (#208)
- **workspaces**: the workspace card draws the real split tree, so Code Review's bottom terminal is no longer missing from its preview (#208)
- **projects**: the list entry is forgotten even when the folder could not be trashed - the button says Remove - and the result type carries which of the two happened, so the toast reports both halves rather than only the failure (#209)
- **plugins**: `PluginRemoval` needed its own copy of the question. It calls the manager directly, so it would otherwise have kept refusing while the Toolbox asked (#210)
- **plugins**: an update that never completes no longer strands its dependents. The first live confirmed update hit a store 404, nothing loaded afterwards, and three plugins stayed stranded because the sweep only ran on the next load - hence a deadline rather than the sweep alone (#210)
- **auth**: the reviewer `SELECT` policy is switched even though nothing reads `organisation_requests` through PostgREST today, because leaving it would mean a boss_admin who lost the queue in the UI could select the same rows directly (#211)

## Improvements

- **plugins**: `dependentsOf` lists every loaded, enabled dependent and `blockingDependentsOf` is that list narrowed to the hard declarations, so the veto and the prompt cannot disagree about who depends on what. The prompt deliberately counts optional dependents the veto does not: all three of the gateway's consumers declare it optional, so its update already succeeded and left them stale (#210)
- **plugins**: every failure mode of the prompt answers false rather than hanging, including a window that closes with the dialog still open (#210)
- **projects**: the path guards live in `pathTrashRefusal`, separate from the capability half that asks AWT - AWT answers no in a headless JVM, so with one function every guard below it would pass for the wrong reason. Guards run on the canonical path, so a `..` walk or a symlink pointing at `$HOME` is caught too (#209)
- **workspaces**: `SplitTemplatesManager` is deleted (573 lines) and `WorkspacePlaceholders` keeps the placeholder substitution that was the other half of that file (#208)
- **dialogs**: the `AlertDialog` scroll fence is shared as `DialogScrollFence` rather than copied (#208)
- **tests**: `ProjectRemovalTest` (reverting the home-directory guard fails three of them), `DependentRestartTest`, `PluginDependencyResolutionTest`, `ProjectSelectionPolicyTest` and an extended `WorkspaceDefaultsTest`. The migration ships 24 pgTAP assertions where each subject is a different user and none is a global admin except the arm testing the short-circuit, verified by mutation: reverting the RPC permission fails 4, reverting the policy fails 2, flipping `is_system` fails 1 (#209, #210, #208, #211)

## Dependencies

- **boss-plugin-api**: 1.0.77 → 1.0.79, adding `PluginLoaderDelegate.unloadPluginForIntent` and `getDependentPlugins` plus the `PluginUnloadIntent` / `PluginUnloadResult` / `DependentPluginInfo` types - the update-shaped verb AGENTS.md had recorded as the fix for this. Verified a superset of 1.0.77 against the release jar rather than assumed, since `fetchApiPluginJar` has no Maven fallback (#210)

## Known Limitations

- **The prompt's dependent list and the veto's disagree on purpose.** Optional dependents are counted by the prompt and not by the veto, so an update can be confirmed for plugins that would never have blocked it - which is the point, since those are exactly the ones that were being left stale (#210)
- **`organisation.approve` still gates approve, reject and the organisations policy.** A boss_admin can still decide a request id they already knew, which is the status quo rather than something introduced here (#211)
- **Revoking a system permission from the roles plugin is still a one-way door.** That UI hides the Remove button for `is_system` permissions while its add-list does not filter them, which is why the new permission is seeded `is_system = false` instead (#211)

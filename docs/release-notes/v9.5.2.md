# BOSS v9.5.2

**Release Date:** 2026-08-27

Four changes, spanning the tags from v9.5.0 to v9.5.2. BOSS can now actually be the default handler for links, markdown, shell scripts and code files - the branded Chromium engine was quietly holding those types under a second app also called "BOSS" - a plugin's UI is given time to dispose before its classloader closes, and two release-pipeline faults that stopped main cutting a release at all are fixed.

## Highlights

- **The default web browser on a machine with BOSS installed was not BOSS.** It was `ai.rever.boss.browser`, the branded Chromium engine in `~/.boss/boss-chromium/BOSS.app`, which inherited `CFBundleURLTypes` (http, https) and `CFBundleDocumentTypes` (`public.html`) from Chromium and, being branded, is also named "BOSS". System Settings offered two indistinguishable entries and the wrong one won, so every link launched a rendering engine with no window, no tabs and no session while `isDefaultBrowser()` reported "not the default" to a user who had set it (#271)
- **A double-clicked file did nothing at all.** Nothing ever called `Desktop.setOpenFileHandler`, so BOSS appeared in Finder's Open With menu, launched, and discarded the AppleEvent. `processCommandLineArgs` was also gated on Windows, so a Linux user with BOSS as their default browser had every cold-start link silently dropped (#271)
- **Closing a plugin's tabs is not the same as disposing them.** `removeTabById` mutates the tab model on the EDT and returns; Compose disposes the subtree on a later render frame, and that frame is what runs the plugin's own `onDispose` lambdas. The loaders closed in between, so those lambdas could no longer resolve their own classes - seen in a startup API-layer hot swap, 87ms after the teardown meant to prevent it (#267)
- **main could not cut a release.** `downloadBundledPlugins` asked api.github.com for five plugin repos' latest releases unauthenticated, which is 60 requests per hour per IP on shared runner egress, and reported "No JAR asset found in release" for all five; the fix for that then added a workflow-level `GITHUB_TOKEN` eight lines above one that already existed, and a duplicate key in an Actions mapping is a `startup_failure` with zero jobs (#272, #273)

## Features

- **default apps**: `boss-file-types.json` is the single source of truth for what BOSS can be made the default handler for - five categories over the 83 extensions `EditorLanguages` can highlight. `buildSrc/BossFileTypes` generates the plist declarations from it, `FileTypeCategories` serves the runtime, and the Windows and Linux handlers derive ProgIDs and MIME associations from it. Launch Services can only make an app the default for a *type*, never an extension: 42 extensions resolve to a system UTI (31 distinct), the other 41 have only a `dyn.*` placeholder, so BOSS exports its own type for them, grouped by language into 24 declarations (#271)
- **default apps**: the per-extension answers are measured, not derived. `.ts` resolves to `public.mpeg-2-transport-stream`, `.as` to `com.apple.applesingle-archive` and `.edn` to `com.adobe.edn`, so claiming any of them would make BOSS the default application for a format it cannot open. They are recorded as `rejectedSystemType` and get an exported type instead (#271)
- **settings**: a new `Default Apps` section, plus a one-time first-run offer that claims nothing without a click and never asks twice (#271)
- **tabs**: a missing plugin no longer fails silently. `addTab` used to drop a tab with a log line when the plugin that renders it was absent, so the OS could hand BOSS a link and nothing appeared. `SplitViewState` now gates every open on `TabTypeAvailability`, which waits out plugin startup before concluding anything - otherwise every cold-start file open would prompt - then offers Install, or Enable when the plugin is on disk and `DISABLED`. The dialog has no success callback: registering the tab type completes the wait and performs the deferred open, so the file the user double-clicked appears by itself (#271)

## Bug Fixes

- **browser engine**: `build-chromium-branding.yml` deletes `CFBundleURLTypes` and `CFBundleDocumentTypes` from the engine's `Info.plist` before the re-sign - after it, the edit breaks the seal - and fails the job if either key survives (#271)
- **browser engine**: an existing install cannot be fixed by a version number, since the plist fix ships inside a rebuild of an already-published engine and `version.txt` reads the same either side. `ChromiumAutoDownloader.isChromiumInstalled` now also asks the extracted bundle what it declares, and a plist still carrying either key invalidates the directory. Bounded to one attempt per version by a marker outside the engine directory, or an engine that still declares the keys afterwards would re-fetch ~160 MB on every launch; fails closed on an unreadable or absent plist, since forcing a large download over a file we could not read is the worse mistake. `lsregister -u` was tried first and does nothing (#271)
- **default apps**: `DefaultHandlerState` is a three-way answer - `Ours` / `OurEngine` / `Other` - so an install already in the broken state is told a BOSS component holds the type and offered Repair, rather than "BOSS is not your default browser", which is the wrong story to tell somebody who did set it (#271)
- **deep links**: `CLISecurityValidator.isValidPath` rejects `..`, `$`, `&`, `;`, `|` and a backtick, which are ordinary filename characters, so `Q&A notes.md` could not be opened at all. `isValidOpenTargetPath` is the check for a file about to be read into the editor rather than typed into a shell (#271)
- **deep links**: `OsOpenArguments` returns nothing when the first non-flag argument names a `createBossCLI` subcommand, so `boss file /tmp/x.md` is not opened twice. Matching at any argv position meant an OS open request whose path was exactly `file`, `url`, `folder`, `terminal` or `workspace` was dropped instead. A directory now becomes a `boss://folder` link rather than no link at all, and `file://` URLs are decoded, which is what `Exec=%U` hands over (#271)
- **browser**: `URLHandlerService` no longer requires a dot in the host, so `http://localhost:3000` opens instead of being dropped with a log line. `Char.isDigit()` accepted non-ASCII digits, so `:٣٣` validated as a port (#271)
- **plugins**: the unload path now waits on `PluginUiMountRegistry`, which `PluginErrorBoundary` reports mounted and disposed into, so a tab, a sidebar panel and whatever is added next all count without touching their call sites. Counted rather than flagged, because one plugin can have several surfaces up at once and they dispose independently. Bounded at two seconds: nothing guarantees a frame arrives, since a minimised or fully occluded window may never draw, and hanging an unload on a frame that never comes is worse than a fault the crash boundary already contains (#267)
- **plugins**: the wait is on the set of plugins whose loaders are about to close, not on "nothing mounted at all" - sidebar panels deliberately stay up across an API-layer swap, so with any panel open the original predicate was unsatisfiable and every swap burned the full 2s and logged a warning that reads like the fix failed, on a path that runs at startup. It is also hoisted above both teardown entry points' `isEmpty()` returns, since a plugin whose only surface is a sidebar panel previously never waited at all (#267)
- **plugins**: a plugin's sidebar panels are detached from the composition before it unloads. The registration drops in `TrackingPluginContext.unregisterAll()`, which runs *inside* the unload, after the wait has returned - so a plugin with a panel on screen took the full timeout, unloaded anyway, and its panel then disposed against a closed classloader: the exact `NoClassDefFoundError` the wait exists to prevent. Suspension is what makes the removal stick, because both panel hosts call `getOrCreateComponent` during composition and a bare `removeComponent` is undone by the next frame, re-instantiating from factories that are about to close (#267)
- **plugins**: a boundary rendering the error fallback counted as mounted, so the unload waited on a surface with no plugin `onDispose` lambdas left to run and could only expire. Crash recovery paid for it worst - it closes tabs before disabling, and a quarantined plugin's boundary is on screen showing its fallback (#267)
- **build**: `downloadBundledPlugins` sends an Authorization header. Unauthenticated is 60 requests per hour per IP and GitHub-hosted runners share egress IPs, so the call 403d, the body carried no assets, and the task reported "No JAR asset found in release" for all five plugins - which sent an investigation looking for a Gradle task someone thought had been deleted rather than at a quota. `curl -s` without `-f` exits 0 on a 403, so the status code is now checked and the message names it: rate limited, token rejected, no release, or a release genuinely without a non-thin JAR. The asset download gains `-f` too, or a non-2xx wrote the error page to the `.jar` path and the completeness check counted it as present (#272)
- **build**: `release.yml` had `GITHUB_TOKEN` declared twice in one `env:` block, and Actions refuses to start a workflow with a duplicate key - `startup_failure`, zero jobs, and a run named after the file path because `name:` was never read. Three runs died that way. The token was already available to every gradle invocation, so the workflow half of #272 was never needed; the task change alone is the fix (#273)
- **tests**: three `OsOpenArgumentsTest` cases hardcoded POSIX paths and had left Windows CI red since #271. The production code is fine on Windows - it goes through `File` and `URI` throughout - but the shared test predicate saw a raw string for a bare path argument and a `File(URI)`-normalised one for a `file://` URL, so a predicate written against `/` matched the first and missed the second, on one platform only (#272)

## Improvements

- **default apps**: Windows registration is one `reg import` rather than hundreds of `reg add`s, and the status is one `reg query <FileExts> /s` parsed once. The per-`reg add` version ran on the order of 415 processes for a five-category "Set all" and 83 more to read the status, each with its own timeout, from a Settings screen. It also removes a quoting hazard rather than trying to get it right: the `shell\open\command` value both begins and ends with a double quote, and Java's Windows `ProcessImpl` passes an argument in that shape through unescaped, so `reg` would have stored only the exe path and killed the one write that makes a double-clicked file reach BOSS (#271)
- **default apps**: the three platform handlers share one fold, `DefaultHandlerState.reduce` - BOSS only when every type in the category is BOSS, and `OurEngine` outranks `Other`. Each handler had its own copy; they agreed, which is the only reason nothing was broken, and a fourth copy would not have (#271)
- **macOS**: Launch Services is reached through JNA (`utils/mac/LaunchServices.kt`), replacing a `swift <tempfile>` shell-out per call which needed Xcode installed and so could not work at all on most machines. The Swift scripts remain as a fallback for URL schemes only. Availability is hoisted above `withCFString`, removing an ambiguous nested return and two pointless CFString allocations, with a broader catch so the gate cannot itself throw (#271)
- **settings**: `DefaultAppsSettingsManager` did a synchronous read in `init` reached from a composable, and a non-atomic read-modify-write. Now `ensureLoaded` on IO behind a mutex, with `MutableStateFlow.update` (#271)
- **tabs**: a missing-handler prompt could outlive its own resolution, so the collector re-checks whether the tab type has since registered - comparing the type string rather than constructing a `TabTypeId`, whose equality includes `pluginId` and `defaultOrder`. An absent plugin also meant 15 seconds of silence before the dialog, which looked as dropped as the bug it replaces; there is a status message during the wait now (#271)
- **logging**: `URLHandlerService` logged full URLs unmasked, and `isValidOpenTargetPath` had no length bound (#271)
- **tests**: `WorkflowEnvKeysTest` scans every workflow's `env:` blocks for a key declared twice within one block, line-based rather than parsed, because **PyYAML accepts duplicate keys silently** and takes the last value - so every YAML-parses assertion in this repo shares that blind spot and the check that was run before merging #272 passed. Reverse-verified by reintroducing the duplicate (#273)
- **tests**: `EngineBundlePlistStripTest`'s ordering check compared indices across the whole file, so it constrained only the first macOS job, while the test above it exists precisely because patching one job and not the other is the expected mistake. Now per job. `FileTypeCategoriesTest` pins the extension set and the extension-to-language map against `EditorLanguages.EXTENSIONS`, so what BOSS offers to open cannot drift from what it can render. `PluginUiMountWiringTest` drives the real `PluginErrorBoundary` through a fake sandbox - the earlier tests mounted a replica of the effect and would have passed with the registration deleted from production (#271, #267)

## Known Limitations

- **`teardownPluginTabs`'s sibling gap is named rather than closed.** The empty-tabs branch of `teardownAllPluginTabs` claimed to wait for panel-only plugins and could not - `owners` comes from the same scan as tabs, so it was always an empty set and an immediate return. The dead call is gone and the gap is written down (#267)
- **The disposal wait rests on an ordering nothing enforces at the type level.** The mount count must drop *after* the plugin's own `onDispose` lambdas run, which holds because the registering effect is outermost and Compose dispatches remember observers inner-first. There is a test that fails if that ever inverts (#267)
- **A pinned id in the mount registry costs a timeout.** The map is deliberately leak-tolerant: the failure direction is a 2s wait and a warning naming the awaited plugins, which is the safe one and is visible (#267)
- **Claiming a type is per type, never per extension.** For the 41 extensions with no system UTI, BOSS exports its own - which means another application that also exports a type for the same extension is a separate claim, and Launch Services picks between them (#271)

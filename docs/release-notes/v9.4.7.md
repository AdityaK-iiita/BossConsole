# BOSS v9.4.7

**Release Date:** 2026-08-10

The Secret Manager becomes what it always was underneath - a per-user credential vault - by granting `secret.read` to the baseline `user` role, which also unblocks `Settings > AI Providers` for everyone rather than admins only. Sharing a secret with a *role* is tightened in the same migration, because a role target reaches every holder and `user` is a descendant of every role.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **Every authenticated user gets their own vault.** `secret.read` now reaches the baseline `user` role, so the Secret Manager panel opens for anyone signed in. This is a correction rather than a widening: every secret RPC is already granted to `authenticated` with no permission check, each self-scopes with `auth.uid()`, and all four RLS policies on `public.secrets` are `auth.uid() = user_id`. The permission was a client-side visibility gate over a store that has always been per-user, and the migration that created it said so - it was translating the pre-RBAC `requiresAdmin` flag forward verbatim. Server-side access widens by zero rows (#159)
- **All AI in BOSS was admin-only by accident, and is not any more.** Since provider settings moved into the secret-manager plugin, `DynamicPluginManager` skipping `register()` for an inaccessible plugin meant a non-admin got no AI provider settings, no way to add their own key, and a null `PluginContext.llmProvider` in every other plugin. Nothing had decided that; it fell out of a permission grant written for a different reason (#159)
- **Role shares now require `secret.share.role`, granted to admin and boss_admin.** `share_secret` gated role targets on `can_manage_secret` alone, so any owner could share a credential with any global role - including `user`, which is a descendant of everything and therefore means every account in the deployment, with no undo. That was survivable only while non-admins could not reach the panel, which is exactly what this release stops being true. The check runs before the role lookup, so the error cannot be used as a role-existence oracle. User targets are unchanged, and organisation targets already require membership of the target org (#159)
- **`Settings > AI Providers` names the permission to ask for instead of claiming it is still loading.** "Isn't loaded yet" was reported for three different causes, and for the permission one it was simply false - it will never load. The section now reads the `getInaccessiblePlugins` diagnostics that already existed and names what is missing (#159)

## Features

- **rbac**: `secret.read` on the `user` baseline, joining `user.read/write/update/delete`, `organisation.create` and `organisation.read`. Each of those is a deliberate kill switch - a deployment that wants the vault locked down revokes `secret.read` from `user`, which is a supported operation. The explicit admin and boss_admin grants stay: they are redundant once `user` holds it, since both are ancestors, but removing a grant is destructive and buys nothing. The permission also stays `is_system` and stays on the org-grantable allowlist, its meaning shifting from "who may use the vault" to "who may still use it" (#159)
- **rbac**: a new `secret.share.role` permission, `is_system` so `delete_permission()` refuses to drop it, and deliberately *not* on `is_org_grantable_permission`'s allowlist - so an organisation admin cannot attach it to an org role and mint a sharer of global roles. An org admin's sharing power is over their own organisation, which the `p_target_org_id` branch already serves (#159)

## Bug Fixes

- **settings**: AI provider settings reported a loading state for a permission problem. `LlmProviderAPIAccess.rememberMissingPermissions()` observes `pluginStates` - the public flow, written on exactly the transitions that matter, since a plugin moving into or out of `hiddenPlugins` updates its state - and the section distinguishes "you do not have access, ask an administrator to grant X" from the genuine not-loaded case (#159)
- **tests**: two pgTAP failures from the first CI run, both real. `like(...)` is a SQL operator rather than a pgTAP function, so the two pattern assertions aborted the file with "function like(text, unknown, unknown) does not exist" and it reported 17 of a planned 19; pgTAP spells it `alike`, and the 17 that did run all passed. Separately, `secret_role_share_hierarchy_test`'s fixture owner holds only the baseline `user` role and shares with `finance_admin`, which the new gate refuses - so the share silently did not happen and four downstream visibility assertions failed. That suite is about who can *see* a role share rather than who may create one, so its owner gains `boss_admin`; the refusal for a plain owner is covered in the new suite instead. Worth stating plainly: the second failure was the gate working, since an existing test creating a role share as a non-admin is the call this migration set out to stop (#159)

## Improvements

- **wizard**: Secret Manager moves out of "Admin Tools" into Productivity, and is described as "Your encrypted credential vault, and where you add AI provider keys" rather than "Securely manage API keys and secrets". It is a per-user vault whose every RPC is `auth.uid()`-scoped, and since provider settings moved into it, the only place anyone adds their own AI key. `isDefault` is unchanged (#159)
- **tests**: a new 19-assertion pgTAP suite covers both halves - the baseline grant and the role-share gate - and checks the `secret_shares` table rather than the RPC's success flag, since a gate that errors while still writing the row would pass a message-only assertion. `plugin_create_permission_test` asserted `boss_plugin_admin` holds no `secret.*` at all; it now inherits `secret.read` like every role, so the assertion pins the absence of `secret.share.role` instead, which is the fact that still has teeth (#159)
- **docs**: `RBAC_GUIDE.md` documents the `user` baseline as a set of revocable kill switches, records `secret.share.role` and why a role target is the one secret capability that is not everyone's, and corrects the `boss_plugin_admin` entry that said it holds no `secret.read` (#159)
